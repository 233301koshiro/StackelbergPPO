研究の方針と、それに対する検証や行動が伴っているかを、リポジトリを見られない別のモデルに見せるための一式を作る。
決まり・周期・履歴は [外部の方針レビュー記録.md](../../docs/研究応用/方針/外部の方針レビュー記録.md)。受け取った回答の処理は `/review-in`。

## なぜこのコマンドがあるか

方針を決めた者と実行した者が同じ（Claude）なので、ずれに気づきにくい。
11-28 の初回では、本命の 8 本の予測を形を固定した計算で出したのに、run はリンク長も動かす設定で、投入直前まで誰も気づかなかった。
方針の説明だけを読んだ Gemini の「判断できない事項」で見つかった（系譜 9-369）。
だから一式には、方針だけでなく**行動の側（実験の設定・予測の計算の前提・結果）を記録から写したもの**を入れる。

## 手順

### 0. 素材を集める（記憶で書かない）

```bash
python3 scripts/policy_review_material.py          # 前回の記録の日から。--since YYYY-MM-DD で変えられる
```

コミット・足された段・読みと判定・起動した run とその起動時の指定・動いているキューが出る。
まだ起動していない run の設定は、動いているキューの script（`PLAN` や起動行）と cfg（`design_opt/cfg/*.yml` の `body_params`・`geom_params`・`actuator_params`）を開いて読む。
前回の一式（`out/review_<前回>/`）と、前回の仕分けの記録（外部の方針レビュー記録.md の表の列）も読む。

### 1. 方針の説明を書く（`out/review_<MMDD>/方針の説明.md`）

前回の方針の説明を土台にして、今の方針に直す。節は前回と同じにする（1. 目的と成功の条件 2. これまでの結果 3. 受けた指摘の芯 4. 決めた方針 5. 制約）。

- **リポジトリの用語を開く。** 系譜の番号・run 名・ファイル名・cfg 名・環境変数を書かない。相手はリポジトリを見られない
- **数値は系譜の段から写す。** 自分の言い換えで丸めない
- **実験ごとに「学習が何を最適化するか」を書く。** 設計変数（どの長さ・太さ・ギア比を動かすか、範囲）・物理・seed の数・学習量。予測を計算で出したなら、**その計算が何を固定し何を動かしたか**も同じ粒度で書く。11-28 はここが抜けていた
- Claude の見立て（どの方針が弱いか）は書かない。相手の読みを引っ張る。事実としての未着手・未確認は書く

### 2. 方針と行動の対応表を書く（`out/review_<MMDD>/方針と行動の対応表.md`）

方針ごとに 1 節。各節に次の表を置く。素材（手順 0）の行を、どれかの方針に必ず割り当てる。

| 項目 | 書くこと |
|---|---|
| 決めたこと | 方針の中身と、決めた日・決めた理由（指摘・計算の結果・ユーザーの判断） |
| 前回からしたこと | 日付つきで。計算・実装・学習の起動・記録の直し |
| 予測と、その計算の前提 | 事前に書いた予測。計算なら何を固定し何を動かしたか |
| 実験の実際の設定 | 起動時の指定と cfg から写す。設計変数・物理・seed・学習量・比べる相手 |
| 結果と判定 | 出たもの。まだなら、いつ出る見込みか |
| まだしていないこと | 決めたのに手を付けていないもの |

表の後に、2 つの節を置く。
- **どの方針にも紐づかない行動**: 素材のうち、割り当てられなかったもの（資料の直し・検査の追加なども正直に）。かかった時間がわかれば書く
- **前回のレビューで採用した指摘のその後**: 1 件ずつ、反映したか・どこに・まだなら理由

「予測の計算の前提」と「実験の実際の設定」は、**同じ語・同じ粒度で並べる**。食い違いがあれば、表を書いている途中で見える。見えたら依頼の前にユーザーへ言う（一式を作ること自体が 1 回目の点検になる）。

### 3. 依頼文を作る（`out/review_<MMDD>/依頼文.txt`）

[セカンドオピニオン.md の E](../../docs/リポジトリ説明/05_レビューと監査/セカンドオピニオン.md) の雛形を写し、`[ ]` を埋める（前回の日付・審査までの残りの時間など）。雛形の本文は変えない（毎回同じ問いで比べられるように）。

### 4. 渡す前に機械で確かめる

```bash
D=out/review_<MMDD>
grep -nE '9-[0-9]{3}|系譜|single_run|scripts/|\.yml|\.py|CNOID_|_vp|_ag\b|_fl\b|cfg' $D/方針の説明.md $D/方針と行動の対応表.md
```

出たら開いた言葉に直す（数値の `9-` などの誤検出は残してよい）。

### 5. 記録して渡す

- [外部の方針レビュー記録.md](../../docs/研究応用/方針/外部の方針レビュー記録.md) の表に行を足す（日付・モデル・一式・対象の期間。仕分けの列は「⏳ 回答待ち」）。コミットする（`out/` は git に入らない）
- ユーザーには `out/review_<MMDD>/` の 3 ファイルのパスを示す。`/tmp` のパスは示さない
- 渡し方: 依頼文を貼り、2 つの md を添付する

### 回答が来たら

`/review-in` で仕分ける。回答の全文は `out/review_<MMDD>/回答_<モデル>.md` に保存する。仕分けの記録（系譜の段・方針の md）と、効いた指摘を記録の表の行に書く。
