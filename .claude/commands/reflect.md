直前の作業について、**CLAUDE.md §4-2「記録のトリガーと反映先」の反映漏れを潰す**。

## なぜこのコマンドがあるか

§4-2 は「トリガーを踏んだらその場で書く」と定めているが、**実際に何度も漏れている**。

| 日付 | 漏れ |
|---|---|
| 2026-09-02 | 配布資料3件（中間発表原稿・論文2枚・論文6枚）が「E2E は未実施」のまま。1 例通っていた |
| 2026-09-02 | B1 の結果を一次記録には書いたが、進捗・引き継ぎ・実験一覧・パイプラインMD・第3章・scripts/README の 6 件が漏れた |
| 2026-09-02 | 描画基準を変えたとき実寸表だけ直し、プロンプト側の比のロックを放置。B1 が壊れる寸前だった |

**漏れる理由は構造的**である。§4-2 の表は「どこに書くか」を定めるが、
**表に載っていないファイル**（配布資料・凍結スナップショット・スクリプトの索引）は
その場では思い出せない。だから毎回このコマンドで機械的に洗う。

## 手順

### 0. 他セッションの差分を取り込む（**最初に必ず**）

**別端末・別セッションで並行開発されていることがある。** 自分のコンテキストに無い
コミットが入っていると、**古い解釈のまま喋る**。

```bash
git log --oneline -20 --format="%h %ad %s" --date=format:'%m-%d %H:%M'
git status --short          # 未コミットの変更も見る
```

**とくに危ないのは、結論や解釈を書き換えたコミット**である。これらは
「数値は変わっていないが読み方が変わった」型なので、数値を見ても気づけない。

```bash
git log --oneline -30 | grep -iE "訂正|取り下げ|反証|撤回|誤り|解釈|限界"
```

該当したら **`git show <hash>` で本文を読む**。要約だけで済ませない。

⚠️ **2026-09-03 に実際に踏んだ。** 別セッションが 4 時間前に
「A1 は 9-11 の反例ではなく傍証だった」と解釈を訂正していたのに、
それを確認せず**古い「反例になりうる」という読みをユーザーへ話した**。
`git log` を見れば分かったことだった。

**知見の現在地は [知見総括表.md](../../docs/研究応用/知見総括表.md) を見る。**
とくに **E 節「反証・取り下げた主張」**に、いま言ってはいけない読みが集めてある。

### 1. 踏んだトリガーを判定する

直前の作業を見て、次のどれに当たるかを**すべて**挙げる（複数可）。

| トリガー | 必ず書く | 併せて確認する |
|---|---|---|
| 実験が完走した / 結果を調べた | `研究応用/実験系譜.md`（一次記録＝SSOT） | `進捗.md` の run 表、`実験一覧_詳細.md`、該当する修論章 |
| 形態・収束値を実測した | `研究応用/形態比較.md` | 実験系譜の該当段 |
| バグを見つけた / 直した | `デバッグ戦記.md`（Bug 番号を採番） | 影響を受けた過去の結論が無いか |
| コードを変えてコミットする | 該当する `リポジトリ説明/*.md` | `scripts/README.md`、`評価スクリプト.md`、`進捗.md` のファイル一覧 |
| 会話で重要な知見が出た | 最も近い専門MD | 方針に関わるなら `研究方針.md` |
| 方針を決めた / 変えた | `研究応用/研究方針.md` と `CLAUDE.md` | 進行中の実験計画と矛盾しないか |
| 審査で突かれそうな点に気づいた | `研究応用/想定問答.md` に Q を追加 | 対応する限界節（5.6.2 / 6.4.2） |
| **限界・未達の状態が変わった** | 変わった限界を述べている**全ファイル** | **配布資料3件を必ず含める** |

### 2. 反映先を実際に開いて確認する

**「書いたつもり」で済ませない。** `grep` で当該の語がそのファイルに入っているかを見る。

```bash
for f in docs/進捗.md docs/研究応用/引き継ぎ_再起動後.md docs/実験一覧_詳細.md \
         docs/中間発表原稿.md docs/研究応用/論文2枚.md docs/研究応用/論文6枚.md \
         scripts/README.md; do
  printf "  %-40s %s\n" "$f" "$(grep -c '<今回のキーワード>' $f)"
done
```

### 3. とくに漏れやすい5箇所を明示的に見る

- **配布資料**（`中間発表原稿.md` / `論文2枚.md` / `論文6枚.md`）
  — PDF ビルドにも `check_docs_consistency.py` にも掛からないので構造的に漏れる
- **`scripts/README.md`** — スクリプトの挙動を変えたのに索引が古いまま
- **同一ファイル内の別箇所** — 第4章 4.5.3 を直して 4.6 の要約を忘れた例がある
- **凍結スナップショット**（`要旨_詳細版.md`）— 古いままでよいが、その旨の注記が要る
- **修論の限界節** — 限界が1つ消えたのに「残された改良点」と書いたままになりやすい

### 4. チェッカーを3本とも走らせる

```bash
python3 scripts/check_docs_consistency.py   # 数値・状態語をログと突き合わせ
python3 scripts/check_citations.py          # 引用と参考文献の双方向一致
python3 scripts/check_stale_claims.py       # 事実と食い違う主張・IME 誤変換
```

**週に1回は棚卸しも走らせる**（CLAUDE.md §4-2 定期棚卸し）。

```bash
python3 scripts/check_docs_inventory.py    # 孤立ファイル・壊れリンク・archive の注記漏れ
```

### 5. 漏れがあれば直し、無ければ「無し」と報告する

**取り繕わない。** 漏れが無かったならそう言う。あったなら、
**なぜ漏れたか**（どのファイルが §4-2 の表に無かったか）まで報告する。
表に無いせいで漏れたなら、§4-2 の表自体を直す。
