# デバッグ戦記

**目的**: 調査中に発見したバグ・不具合を記録し、次に行き詰まったときに「報酬設計や学習アルゴリズムのせい」と誤認しないための再現性ある方法論をまとめる。

---

## 方法論：原因を特定するための3ステップ

次に「armが動かない」「報酬が上がらない」で行き詰まったとき、**すぐ報酬やハイパラに手を入れる前に**この順序で確認する。

### Step 1: まず物理・環境層が正しく動いているか疑う

学習の停滞は、アルゴリズムや報酬より**物理エンジンや環境実装のバグ**が原因のことが多い。「ポリシーが悪い戦略に収束した」という説明は、物理バグとほぼ区別がつかない外見をしている。

**確認すべき仮定（チェックリスト）**:
- [ ] 物理エンジンが XML/YAML に書かれた damping を実際に適用しているか
- [ ] joint_range（可動域制限）が実際に動力学計算に反映されているか
- [ ] qpos（状態変数）が実際のリンク位置（body_xpos/body_xmat）と一致しているか
- [ ] 観測値（observation）に極端な値やNaN混入がないか（`normalize_obs` 警告を確認）
- [ ] 報酬値のログ（fwd_cube/fwd_contact）が物理的に意味のある値を示しているか

### Step 2: 2つの独立した測定値を並べて矛盾を探す

同じ物理状態を2通りの方法で計算し、**矛盾がないか**を確認する。矛盾があればどちらかが嘘をついている = バグ。

例:
- `qpos`（MuJoCo互換の状態ベクトル）と `body_xmat`（Choreonoidが計算したリンク回転行列）
- `ctrl_norm`（制御出力）と `tip_dist`（アーム先端の実際の軌跡）
- YAMLに書かれた `joint_range` と 実際のqposの取りうる値

### Step 3: 制御実験で「1変数固定」して物理応答を直接確認する

- ランダムポリシーや複雑な報酬ではなく、**自分で決めた単純な入力**（例：既知のトルクパルスを数ステップだけ与えて、その後ゼロにする）を与える
- 物理的な**予測**（減衰があれば速度は指数的に減るはず、可動域があれば90°で止まるはず）と**観測**を比較する
- 予測と観測が一致しなければ実装バグ

### Bug 1: Choreonoid AIST が prismatic joint の damping を無視する

**発見日**: 2026-06-25  
**影響**: cube が damping=2.0 と設定されているにも関わらず、ゼロ減衰でドリフトし続ける。動画で「アームが触れていないのに cube がジリジリ進む」現象として顕在化。

#### 症状
- ゼロアクションテスト（ctrl=0）でも cube が `delta = +0.0009 m/step` で一定速度 drift し続ける
- v2-2・v5 でまったく同一パターン → 報酬や学習と無関係な物理バグと判断

#### 根本原因
Choreonoid の AIST シミュレータが `.body` ファイルの `joint_damping` を **prismatic（slide）ジョイントに対して dynamics 計算に適用しない**。設定値は読み込まれるが無視される。加えて cube の質量を計算する `make_shape` 関数が per-geom の `density` 属性を無視しており、`0.135 kg`（正しくは `2.7 kg`）になっていた。

#### 発見方法
- `eval_cnoid_visual.py` で動画を生成し「アームが静止しているのに cube が動く」を目視確認
- ゼロアクションテストスクリプトで ctrl=0 のまま cube が drift することを数値で確認 → 学習結果でなく物理バグと確定

#### 修正内容
`khrylib/rl/envs/common/mujoco_env_choreonoid.py` の `step()` 内で、毎物理ティックごとに **明示的に粘性減衰を `j.dq *= decay_factor` として適用**するキャッシュ方式を導入（`_extra_joint_decay` リスト）。API 呼び出しコストを避けるため事前にキャッシュ。cube damping を 2.0 → 10.0 に変更。

#### 教訓
「設定ファイルに書いた値が物理エンジンに反映されている」という前提を疑わなかった。**YAML/XMLに値を書くだけでは不十分で、エンジンが実際に使っているか確認が必要。**

### Bug 2: 同修正が「extra body（cube）のみ」に適用され、ロボット本体の hinge joint が対象外だった

**発見日**: 2026-07-01  
**影響**: ロボット自身の関節（肩・肘）が damping・joint_range ともに無視され、**一度でもトルクをかけると関節が永久に無制限回転し続ける**。これまでの全実験（v2〜v5-4）がこの壊れた物理の上で行われていた。`[normalize_obs] extreme-value rows clamped` 警告がずっと出続けていた原因でもある。

#### 症状
- epoch387まで学習しても cube が一度も動かない（全 run で変位ゼロ）
- 「ポリシーが止まる戦略を学習した」という解釈をしていたが、物理バグだった可能性が高い
- バグ修正後、初めてアームが制御された動き（ctrl 非ゼロが200ステップ継続、tip_dist が単調に減少）をするようになった

#### 根本原因

**3層の問題が重なっていた**:

1. **`mujoco_xml_to_body()` で hinge joint に damping が渡されていなかった**  
   prismatic 分岐は `damping=` を明示的に渡していたが、hinge 分岐は省略していた。そのため YAML に `joint_damping` フィールドが書き出されなかった。
   ```python
   # 修正前（hinge）
   add_link(..., axis, rng_deg, ..., shape)  # damping 省略
   # 修正後
   damping = float(j_el.get('damping', default_damping))
   add_link(..., axis, rng_deg, ..., shape, damping=damping)
   ```

2. **Bug 1 の修正が `entries[1:]`（extra body = cube のみ）に限定されていた**  
   `_build_sim_body_entries()` の減衰キャッシュ構築ループが `entries[1:]` だったため、`entries[0]`（ロボット本体）のアーム関節には一切適用されていなかった。

3. **`joint_range` をクランプする処理が存在しなかった**  
   YAML に `joint_range: [-90, 90]` は書き出されていたが、それを読んでシミュレーション中に強制する処理がなかった。AIST は revolute joint の range を自力では強制しない。

#### 発見方法

**起点：ユーザーの一言「動いているようには見えないけど動いているってこと？」**

3フレームサンプリング（step1/100/200）では視覚的に静止して見えていたが、この疑問から細かく再調査した。

**Step 1（粒度を上げる）**: 毎5ステップのdense diagnosticを実施
```
step  20: qpos1=0.209  tip_dist=0.83633  ctrl1≈0.00000
step 100: qpos1=1.630  tip_dist=0.83633  ctrl1≈0.00001  ← 矛盾！
step 195: qpos1=3.317  tip_dist=0.83633
```
`qpos1` は 3ラジアン以上変化しているのに `tip_dist` が小数点5桁以下まで完全に固定。**2つの独立測定値が矛盾**している。

**Step 2（控制実験）**: 環境を直接構築し、肩関節に8ステップだけ既知のトルクパルスを与えて zero ctrl に戻す制御実験を実施
```
step  7: ctrl=1.00  qpos0=7.96  qvel0=47.86  real_angle=1.678
step  8: ctrl=0.00  qpos0=9.88  qvel0=47.86  ← qvel が一切減らない！
step215: ctrl=0.00  qpos0=406.2 qvel0=47.86  ← 65回転以上
```
- `qvel` が ctrl=0 にしても 207ステップ全く減衰しない → **damping 無効の直接証明**
- `qpos0` が 406 rad（65 回転以上）→ **joint_range 無効の直接証明**
- `real_angle`（body_xmat から直接計算）が `qpos0` と完全一致 → 表示バグではなく実際に物理的に回転し続けている

#### 修正内容
`mujoco_env_choreonoid.py` の3箇所を修正:
1. hinge joint にも damping を渡すよう `process_one_joint()` を修正
2. `_load_body_defs()` の解析ループから `if i > 0:` 制限を撤廃し、ロボット本体も含む全 body の `joint_damping` と `joint_range` を解析
3. `step()` 内で毎ティック、全 joint に対して減衰（`j.dq *= factor`）と range クランプ（`j.q` を `[lower, upper]` に制限、超えた場合は `j.dq=0`、`calcForwardKinematics()` で実リンク姿勢を同期）を適用

詳細: タスク設計と報酬関数.md セクション11

#### 教訓
1. **Bug 1 の修正を入れたとき、「同じ問題が別の箇所にないか」を確認しなかった**。今後同種の修正を加えるときは、同じパターンが他の場所でも発生していないかを必ずスコープ確認する
2. **「ポリシーが最適戦略として止まることを学習した」はデフォルト仮説にしない**。Stop は報酬設計問題にも見えるし物理バグにも見える
3. **制御実験（1変数固定）が最も確実**。ランダムポリシーや複雑な報酬ではなく、自分で決めた単純な入力を与えて物理応答を直接確認する

### Bug 3: Choreonoid exit 後もプロセスが残り続ける（choreonoid Qt イベントループ問題）

**発見日**: 2026-06-30  
**影響**: `eval_cnoid_visual.py` / `choreonoid_train.py` など `choreonoid --python` 経由で動かすスクリプトが、スクリプト終了後も Qt のイベントループが残りプロセスが終了しない。`timeout` コマンドの SIGTERM も効かず、最大3日間プロセスが生き続けてメモリをリークしていた。

#### 症状
- 動画生成後 `[visual] Done.` が出てもプロセスが終了しない
- `timeout 300` を設定しても Kill されない
- 複数のゾンビ的プロセスが蓄積し、メモリが枯渇

#### 発見方法
定期的にメモリをチェックしていて `free -h` で空き容量が急減 → `ps` で漏れているプロセスを特定 → `eval_cross_env.py` に同問題が既に存在しており `os._exit(0)` で解決済みだったことを確認

#### 修正内容
`eval_cnoid_visual.py` / `eval_cnoid_numerical.py` / `eval_cnoid_viewer.py` / `choreonoid_train.py` の末尾に `os._exit(0)` を追加

```python
# スクリプト末尾に追加
os._exit(0)  # choreonoid では sys.exit が TypeError になるため強制終了
```

#### 教訓
`choreonoid --python` 経由で動かすスクリプトは、すべて末尾に `os._exit(0)` が必要。**新しい choreonoid 用スクリプトを作るときは最初から入れる**。

### Bug 4: `get_body_com()` がサブツリー全体の重心を返す（個別リンクの重心ではない）

**発見日**: 2026-06-29  
**影響**: `compute_reach_bonus()` でリンク長を `||get_body_com(bodies[1]) - get_body_com(bodies[0])||` で計算しようとしたところ、`bodies[0]`（初期形態ではほぼ質量ゼロのルートリンク）と `bodies[1]` のサブツリーCOMがほぼ一致し、`L1` が常に 0 になった。

#### 発見方法
デバッグ出力で `L1=0.000` が全サンプルで一致 → 計算式の前提が間違いであることに気づく

#### 修正内容
リンク長は `body.bone_offset`（設計パラメータのベクトル、ノルムが長さ）を直接読む。ショルダーのワールド座標は `data.body_xpos[body_name]`（フレーム原点、サブツリーCOMではない）を使う。

#### 教訓
MuJoCo スタイルの `get_body_com` は「そのボディを根とするサブツリー全体の重心」を返す。個別リンクの情報が欲しいときは `body.bone_offset` または `data.body_xpos`（フレーム原点）を使う。

### Bug 5: config.py の `reward_specs` / `env_specs` が Hydra FLAG を無視する

**発見日**: 2026-06-24  
**影響**: `+reward_specs.use_target_reward=true` などコマンドライン引数で渡した設定が学習中に無視され、デフォルト値で動いていた。`+env_specs.cube_x_offset=0.5` も効いておらず、v2-2/v5 が意図しない設定で数十エポック学習していた。

#### 発見方法
`.hydra/config.yaml` に `cube_x_offset: 0.5` が記録されているのに、`check_strategy.py` で `cube 初期: x=1.000m (offset=0.0)` と表示 → 設定と実際の挙動が一致しないことで発覚

#### 修正内容
`design_opt/utils/config.py` に `self.env_specs.update(FLAG.get('env_specs', dict()) or {})` を追加（`reward_specs` は既に修正済みだったが `env_specs` が漏れていた）

#### 教訓
`.hydra/config.yaml` に記録されていても、コード側で読んでいなければ意味がない。**設定が実際に使われているかは `check_strategy.py` 等で実機確認が必要**。

### Bug 6: 学習済み形態が cube に初期接触してインパルスで cube を飛ばす（initial contact exploit）

**発見日**: 2026-07-01
**影響**: curriculum_v1（cube_x_offset=0.1）で epoch11 に fwd_cube が初めて非ゼロになった。しかし動画でアームが動いていない、ステップごとのデータでアームの link.p が全く変化しないことを確認。ゼロアクション×学習済み形態でも cube が動くことが判明。

#### 症状
- `fwd_cube > 0` にもかかわらずアームが視覚的に静止
- ステップ0から `cube_vx = 0.266 m/s` が発生（アクションより先に速度がある）
- `qpos0 = 1.571 = π/2` が全ステップで不変（shoulder が joint_range 上限に張り付き）
- `elbow_x = -0.4934`, `tip_x = 0.0047` が全ステップで不変（アームは1mmも動いていない）

#### 根本原因
Leader（形態設計）が reach_bonus の最大化として「arm_safe_init 補正後の先端が cube の左面（x≈0.97m）にぴったり触れる形態」を学習。エピソード開始直後に物理エンジンが接触解消インパルスを発生 → cube が飛ぶ。アームは能動的に何もしなくていい。

arm_safe_init は「joints=0 の時のアーム方向が cube を向かないよう +90° 回転」で初期貫通を防ぐ設計だったが、**形態の成長（bone_offset の方向・長さが変わる）によって +90° 回転後の先端位置が再び cube に当たる形態を学習できてしまった**。

#### 発見方法（デバッグ戦記の方法論に従い）

**Step 1（矛盾を探す）**: fwd_cube 非ゼロなのに動画でアームが静止 → qpos と link.p の両方を記録する dense diagnostic → elbow_x, tip_x が全ステップ不変（qpos1 は変化しているのに物理的には動いていない）

**Step 2（対照実験）**: ゼロアクション × デフォルト形態 → cube 静止（Bug ではない）。ゼロアクション × 学習済み形態 → `cube_vx = 0.266 m/s` 発生（形態依存の initial contact と確定）

#### 修正内容
`transit_execution()` の `reset_state()` 直後に `_check_initial_contact()` を呼び出し。arm tip の world 座標（arm_safe_init +90° 補正後）が cube のバウンディングボックス内に入る場合はエピソードを即終了（`return False`）。Leader は再設計を余儀なくされ、このexploit形態を学習できなくなる。`+env_specs.check_init_contact=false` で無効化可能。

#### 教訓
- **「cube が動いた」は「アームが動いた」ではない** — step-by-step の dense diagnostic でアームの link.p（世界座標）を確認しないと騙される
- **reach_bonus の最大化と initial contact exploit は表裏一体** — Leader に「arm をcube に近づけよ」というインセンティブを与えると、「そもそもエピソード開始時点で触れている」という搾取解が最適になりうる
- **ゼロアクション対照実験の対象は「デフォルト形態」だけでなく「学習済み形態」でも行うべき**

## 早期発見のためのシグナル一覧

以下が観測されたとき、報酬設計より先に物理・環境実装のバグを疑う：

| 観測シグナル | 疑うべき原因 |
|---|---|
| `[normalize_obs] extreme-value rows clamped` が多発 | qpos などの状態変数が異常値になっている |
| cube や arm が「触れていないのに動く」「触れているのに動かない」 | 物理エンジンの damping/接触計算がおかしい |
| ctrl=0 にしても関節速度が全く変わらない | joint damping が適用されていない |
| qpos と body_xpos/body_xmat から計算した値が一致しない | 状態変数と実際の物理状態がデシンクしている |
| 設定ファイルの値と `check_strategy.py` 等の表示値が一致しない | config の読み込みバグ |
| `timeout N` が効かずプロセスが生き続ける | choreonoid Qt ループ問題（`os._exit(0)` 不足） |
| 学習曲線がある時点から全く動かなくなる（ゼロ横ばい） | 上記いずれかのバグが原因で観測値が破損している可能性 |

## 対照実験ルート（cube が動かない原因調査、2026-07-01）

### 背景

物理バグ（Bug 2）修正後も cube 変位ゼロが続いていた。「報酬設計の問題か、別のバグか」を切り分けるため、3つの対照実験ルートを設計した。

**原則**: 確定している事実まで戻り、一変数ずつ検証する。

---

### Route C: ゼロアクション健全性チェック（最小コスト、即実施）

**目的**: ポリシー・報酬と完全に切り離して物理層のみを確認する。ctrl=0 で 200ステップ流し、アームと cube が静止するかを見る。

**手順**:
1. `PusherEnv` を直接構築（fix_skeleton=true, cube_x_offset=0.5, arm_safe_init=true）
2. 設計フェーズをゼロアクションで通過して execution ステージへ
3. 200ステップ ctrl=0 で実行し、qpos/qvel/cube_x/cube_vx を毎ステップ記録

**2026-07-01 実施結果（Bug 2 修正後）**:

```
step  0: qvel1 = -0.006722  （リセット時の初期ノイズ）
step  1: qvel1 = -0.002650  → 指数減衰
step  4: qvel1 = -0.000162
step 20: qvel1 = -0.000000  ← 完全ゼロ。以後200stepまで静止
cube_vx = 0.000000 （全ステップ通してゼロ）
```

**判定: ✅ PASS（物理層は正常）**

肘関節の初期 qvel が非ゼロに見えたが、これはリセット時の速度ノイズが正しく指数減衰している正常な動作（damping 修正が機能している証拠）。cube は完全静止。

**この結果が意味すること**: 物理エンジンに残存バグはない。cube が動かない原因は**報酬設計か学習ダイナミクス**（物理エンジンではない）に絞られた。

---

### Route A: 現状継続（フル装備 + 物理修正）【結論済み: 失敗】

**設定**: v5-5 / rrbot_arm2_cnoid_v2（2026-07-01 起動、同日停止）

**結果**: 探索ギャップ問題（arm_safe_init 構造的欠陥）で fwd_contact=0 のまま停滞 → Route B に移行。

---

### Route B: 速度ベース報酬に戻す【結論済み: bat tactic 確認 → B/C/D 実験へ】

**設定**: `use_target_reward=false`（速度ベース `Δx/dt`）+ 大 cube（1m）

**結果**: バットタクティック（スイング押し）が出現。fwd_cube > 0.1 の成功基準を ep50 で達成（実験 B）。ただし joint limit で 3 ステップ後に固定 → 継続押し戦略を学習させるため joint range 拡張 + 速度制限（実験 D）へ。

---

### ルート選択フローチャート（2026-07-03 時点で全ルート結論済み）

```
Route C（ゼロアクション）✅ 完了: 物理は正常
         ↓
Route A ✅ 完了: 探索ギャップ → 失敗（arm_safe_init 廃止へ）
         ↓
```

### Bug 8: pgrep/pkill の自己マッチによる監視デッドロックと誤 kill（2026-07-09、ops）

**症状**: K1/K2 完走（13:22）を検知して L2 を自動起動するはずの `L2_launcher.sh`（⚠️ **現存しない**。当時の使い捨て）が 2.7 時間動かず、完走監視ループも永遠に「実行中」のまま通知が来ない。

**原因**: `pgrep -f "hydra.run.dir=...K"` の `-f` はプロセスの**コマンドライン全文**にマッチする。監視ループを `bash -c '<パターンを含むスクリプト>'` として起動すると、**監視シェル自身のコマンドラインがパターンを含む**ため pgrep が自分にマッチし続け、「K がまだ生きている」と誤認し続けた。さらに別プロセス（L2_launcher）の pgrep も**この監視シェルに**マッチするため、相互に偽陽性を生む。後始末の `pkill -f "L2_launcher.sh"` も同様に**発行元シェル自身を kill**し（exit 144）、後続コマンドが実行されないまま静かに死んだ。

**確認方法**: `ps aux | grep <キーワード> | grep -v grep` でコマンドライン全文を目視し、「マッチしているのは誰か」を確認（pgrep の数字だけ見ていると自分自身と気づけない）。

**教訓**:
1. 監視・後始末で `pgrep -f` / `pkill -f` を使うときは、**パターンが自分のコマンドラインに含まれない**ことを保証する（スクリプトファイル化して `bash file.sh` で起動する／`pgrep -f "^完全な先頭一致"` を使う／`ps | grep -v grep | grep -v $$` で除外する）
2. pgrep は「pgrep 自身」は除外するが、**呼び出し元シェルは除外しない**
3. 完走検知は プロセス監視より **`training done` のログ grep** の方が自己マッチの余地がなく安全

### Bug 9: 初期接触棄却の全滅 →「All episodes are filtered」assert 死（F4・L2・TP1 で3回再現）

**症状**: 学習が序盤（ep13〜18）で突然死。stdout 末尾に `AssertionError: All episodes are filtered`（genesis_agent.py:446）と `[EP-FILTER] dropped 8336 episodes`。直前の T_sample が異常に長い（365s、通常 20s — 棄却→再サンプルの空回り）。**main 死亡後もワーカー4個/run が孤児として残り、計 ~15GB の RAM を占有し続ける**二次被害つき。

**根本原因（死のスパイラル）**:
1. `_check_initial_contact()` は初期接触形態のエピソードを「exec 0 ステップで打ち切り」にする
2. EP-FILTER は follower=0 のエピソードを**丸ごと捨てる** → **Leader にも勾配が渡らない**
3. Leader の設計分布が棄却領域（tip が cube に触れる形態）に入っても、「そこが悪い」という学習信号が存在しない → 分布が留まる/深入りする
4. 全エピソード棄却 → assert 死

**トリガー条件**: `ctrl_cost_coeff` が大きい（F4=0.1、L2/TP1=0.2）と Follower の初期学習が遅く、Leader が実タスク報酬の勾配を得る前にランダムドリフトで棄却領域に到達しやすい（ctrl コスト 1e-4 の I2 は 683ep 無事故 = 同条件で Follower が ep13 時点で既に押せていた）。

**修正（2026-07-10）**:
1. **pusher.py**: 初期接触時、棄却ではなく「物理を進めず 1 exec ステップ + `init_contact_penalty`（デフォルト 1.0）の負報酬」でエピソードを成立させる → EP-FILTER を通過し **Leader が棄却領域の悪さを勾配として学習できる**。exploit（接触インパルス）は物理を進めないため不可能のまま
2. **genesis_agent.py**: 全滅エポックは assert 死でなく更新スキップ + 警告に変更（10連続で初めて異常終了）— 多重防御

**教訓**:
1. **「データから捨てる」ガードは、捨てた領域から抜け出す勾配も捨てる**。エピソード棄却型のガードを入れるときは「Leader（またはポリシー）がその領域を避ける学習信号は何か」を必ず問うこと。ペナルティ化が原則
2. assert による即死はワーカー孤児（RAM リーク）を生む。学習ループの防御は「スキップ + 上限つき」で
3. 同じ死に方が2回目に出たら（F4→L2）偶然ではなく構造。3回目を待たない

**追記（2026-07-10 午後）: 修正第1版（penalty=1.0）自体に欠陥があった**。
ctrl_cost=0.2 下では正直に動くエピソードの序盤リターンが ≈-16 のため、**「接触して1ステップで終わる（-1）」方が正直に動くより得** — Leader は正しく最適化して全設計を接触形態に収束させた（L2/TP1 再走 ep8-10 で train_R_eps≈-1.05 に張り付き・eval=-1.00 を実測）。しかも全エピソードが同じ -1 になると advantage の対比が消えて脱出勾配も出ない。
→ **ペナルティは「正直な1エピソードの最悪リターンより確実に悪い」こと**が設計原則（懸念3「早期終了が得」の変種）。init_contact_penalty デフォルトを 50（≈ ctrl コスト満額 + マージン）に変更し再々起動。
**メタ教訓: ペナルティ・報酬の定数は「比較対象となる正直な行動の実測リターン」と並べて桁を決める**（-1 は直感的には十分な罰に見えるが、報酬系全体の中では報酬だった）。

**追記（2026-07-13 夕）: 最悪条件での設計検証に成功 — penalty=50 は「接触圏スタートの seed」でも脱出勾配として機能した**。
TP2_s2（seed=1）は初期形態が接触ペナルティ圏から開始し、ep0-2 は eval=-50.00 に張り付いた（= penalty=1 世代なら死んでいた条件）。しかし **ep3 で -17.45 → ep4 以降 -0.3〜-0.7 の正直な値に離陸**し、train_R_eps も -49.4→-30.7 と改善継続。棄却（Bug 9 原型: 勾配ゼロで assert 死）→ penalty=1（張り付き）→ penalty=50（3エポックで脱出）という3世代の対照が偶然にも同一タスクで揃い、**「棄却でなくペナルティ・大きさは正直な最悪リターン未満」の設計原則が最悪条件込みで実証された**。修論の考察 5.2.4 の実証例として使える。

### Bug 10: checkpoint 再評価時の転用フィルタ事故 — TP/K 系の形態抽出が全てアーティファクトだった（2026-07-15 発覚）

**症状**: TP2_s2 の best checkpoint を決定論再評価すると全エピソードが初期接触ペナルティ(-50)になるのに、学習ログの eval は +0.48。矛盾を追うと、プローブが再現する形態（tip=(0.84,0.24)）と学習中の実形態（tip=(0.55,1.00)）が全く別物だった。

**根因**: `load_checkpoint()` は `cfg.control_prior=true` のとき **(a) policy/value を control_ プレフィクスだけに絞って読み込み（Leader = skel_/attr_ ネットはランダム初期化のまま）、(b) obs_norm も読み込まない**（転用時の仕様としては正しい）。再評価ツールは保存済み `.hydra/config.yaml` から cfg を作るため、**転用で起動した run（TP1/TP2/TP2_s2/K1/K2）の再評価では control_prior=true が残り、この転用フィルタが自分自身の checkpoint に適用されていた**。形態はランダム Leader の出力 = アーティファクト。

**なぜ気づけたか**: 「学習ログの eval」と「checkpoint 再評価」の矛盾を放置せず突き合わせた（-50 vs +0.48）。**学習ログと再評価の値が合わないときは、まず重みの読み込みを疑う**。

**修正**: 全再評価ツール（visualize_morph_changes / compare_morphology / eval_reach_hover / probe_cube_trace / probe_L0_intervention）で cfg 構築後に `control_prior=False; morph_prior=False` を強制（コミット fabff75）。完走 run 自身の checkpoint には全重み + obs_norm が保存されているため、これが正しい読み込みである。

**無効化された測定（要再測定・再測定済みは順次訂正）**: TP1「短腕×低gear の第3クラスタ」形態・TP1 持続押しトレース・「ペナルティ境界拘束」知見・TP2/TP2_s2 中間形態・K1/K2 の形態（K2 異常収束 L11=0.868/gear371 を含む）。**無効でないもの**: 学習ログ由来の数値（exec_R_eps・離陸判定・仮説④の判定値）、prior なしで起動した run（B/C/G/H/I/J/L 系）の全形態抽出・G1 判定・J1 介入実験。

**メタ教訓**: 再評価ツールは「学習を再現する」のではなく「学習済み状態を復元する」もの。**訓練時と評価時で意味が変わる設定フラグ（転用・正規化リセット等）は、再評価パスでは明示的に無効化する**。ツールを書いた時点で prior 付き run を評価する予定がなかったため、フィルタの存在自体を忘れていた。

**再発（2026-07-17）**: 動画生成の `eval_cnoid_visual.py` 等が修正5本から**漏れていた**。症状は TP1 の実行動画が2フレーム（1秒未満）で終わる — 乱数 Leader の出力形態が cube に初期接触し、初期接触ペナルティ(-50)の1ステップでエピソード終了していた。学習ログは正常（exec_R_eps 0.32〜0.36、NaN ゼロ）なので**学習の失敗ではなく再評価アーティファクト**。`Config(FLAGS, ...)` で保存 config を読むスクリプトを grep で全列挙したところ、再評価系 12 本中 **7 本が未修正**だった（eval_cnoid_visual / eval_morphology / check_strategy / eval_cnoid_numerical / eval_cnoid_viewer / eval_cross_env / save_morphology_urdf）。全てに同じ2行（`cfg.control_prior = False; cfg.morph_prior = False`）を追加。TP1・TP2 の動画は 201 フレームで正常再生成済み。教訓: **バグ修正の対象は「同じ cfg 読み込みパターンを持つ全スクリプト」を grep で列挙してから直す**。個別に思い出した5本だけ直すと、こうして2日後に再発する。

### Bug 12: 転用起動が一度も重みをロードしていなかった — 転用実験（I/K/TP 系）は全て実質ゼロスタートだった（2026-07-17 発覚）

**症状**: tripo TP のコールド起動が平坦なのを機に転用レシピを確認したところ、「I1 からの全転用」のはずの run の学習初期値がゼロスタートと区別できないことに気づいた。

**根因**: `train.py` は `FLAGS.epoch` を checkpoint 指定として使い、`checkpoint=0 なら load_checkpoint を呼ばない`（`genesis_agent.py:56`）。`epoch` のデフォルトは `'0'`。そして**転用起動の全 run（I1・K1・K2・TP1・TP2・TP2_s2）は `epoch=best` を一度も渡していなかった**（overrides.yaml 全件確認）。`+restore_dir=... control_prior=true reset_epoch=true` はロードが走らない限り**全て no-op**。restore_dir はパス検証しかされず、エラーも警告も出ない。

**証拠（4点独立）**:
1. コードパス: `epoch='0'` → `load_epoch=0` → ロードなし。`epoch=` を渡した run は履歴上ゼロ（launch スクリプト・docs 全 grep）
2. 全学習ログに `loading model from checkpoint` の行が**一件もない**（このログはロード時に必ず出る）
3. **I1（H1 全転用のはず）の ep0 exec_R_eps = 5.32 ≈ I2（ゼロスタート）の 5.28**。転用元 H1 の final は 127〜135 — 全転用なら ep0 から 3 桁のはず
4. **TP1 と TP2 の ep0 がビット単位で一致**（train_R_eps -44.47 / exec -0.57）— 同 seed のゼロスタート同士だから当然の一致
5. 陽性対照: `epoch=best` を付けた実証プローブ（probe_real_transfer、I1 best から全転用）で史上初の `loading model from checkpoint` 行を確認し、**ep0 exec_R_eps = 221.44**（転用元 I1 の final 202.7〜best 238.7 とほぼ同水準）。真の転用は ep0 から転用元の水準で始まる — 偽転用の 5.32 との差は 40 倍

**無効化される結論（重大）**:
- **転用実験の結論すべて**: 「K1（制御転用）> K2（形態転用）」「I1 の中盤加速」「短期は制御のみ転用が最良」は、**同 seed 同条件 run 同士の実行揺らぎを比較していただけ**。修論第6章の主柱が崩れる
- I1 vs I2 が「同じ解に収束」したのは転用が行き先を変えなかったからではなく、**同一条件の run だったから**
- TP2 の「Pusher からの制御転用で探索の立ち上げを賄う」というレシピ記述（target_pusher.yml コメント・実験系譜）

**無効でないもの（重要）**:
- **TP2/TP2_s2 の成績・行動そのもの（0.450/0.490、押して止める）は有効** — むしろ「コールドスタートで達成した」ことになり、レシピが簡素化される（転用不要でタスク成立）
- L 系・M 系・B/C/G/H/PJ 系（転用フラグなしの run）の全結論
- タスク識別（形態+行動の3クラスタ）の主張は全て無傷

**修正方針**: 転用を主張するときは必ず `epoch=best` を明示する。転用の再実験（真の転用 I1'/K1'/K2'）は epoch=best 付きでやり直せば第6章は再建可能（各 200ep ≈ 実測 5〜20h）。恒久対策として「restore_dir が指定されているのに checkpoint=0」の組み合わせを起動時に fail-fast させるガードを入れるべき。

**メタ教訓**: **フラグを渡したことと、フラグが効いたことは別**。転用 run の ep0 が転用元の final に近いかを一度も確認していなかった。「開始直後の数値が転用元と繋がっているか」は転用実験の必須チェック項目。

### Bug 13: `_check_initial_contact()` が rrbot（2関節）専用にハードコードされていた（2026-07-21、網羅監査で発覚）

**症状**: ユーザーの依頼で cube damping・関節可動域の確認後さらに「他に前提や不備がないか」を監査中、`design_opt/envs/pusher.py` の cube 初期接触判定関数を再点検。

- tripo_arm_v3（4関節）: 先端位置を **59.6%** 過小評価

**教訓**: 「ハングしている」ときは真っ先に**当該プロセス自身の生ログ**（stdout・専用ログファイル）を見る。プロセスの状態（wchan・%CPU）や周辺の別の既知問題から推測するのは、直接証拠を確認したあとにすべき — 今回は取得しやすい状況証拠（worker パス衝突）に飛びついて15分ほど無駄にした。

### Bug 14: `ChoreonoidWorkerPool` の worker 一時ディレクトリが並列 run 間で衝突していた（2026-07-21 発覚）

**症状**: tripo を3並列（v2c の Reach/Pusher/TP）で走らせたところ、Reach だけ正常進行し Pusher・TP が起動28分後も ep0 に到達しない。CPU使用率5%・`anon_pipe_read` で停止という「ハング」状態だった（実際の真因は Bug 13 の自己バグだったが、調査中にこちらも実在する独立した問題として発見）。

**根因**: `design_opt/utils/worker_pool.py` の `ChoreonoidWorkerPool._launch_workers()` が各 worker を `CNOID_WORKER_ID=0..n-1` の**run 内連番だけ**で識別しており、これを使って `/tmp/cnoid_worker_{i}.log`（ログ）と `worker_sampler.py` 内の `Config(..., f'/tmp/cnoid_worker_{WORKER_ID}')`（job_dir = log/models/tb の出力先）を組み立てていた。この ID は**起動した run に関係なく常に 0〜3** になるため、複数 run を並列起動すると全 run の worker0 同士・worker1 同士が同じ一時パスを取り合う。log ファイルは `open(path, 'w')`（truncate モード）で開くため、後発の run が先行 run のログを黙って上書きする実害も確認。

**修正**: worker 起動時に親プロセスの PID を混ぜた `worker_tag = f'{os.getpid()}_{i}'` を新設し、`CNOID_WORKER_TAG` 環境変数として worker に渡す。`worker_pool.py` の log_path と `worker_sampler.py` の `Config` job_dir をこのタグで一意化（`CNOID_WORKER_ID` 自体は seed 計算に使うため維持）。

**メタ教訓**: 「run 内では一意」なIDを「グローバルに一意」なパスの構成要素として使うと、単一 run では何年も気づかれない。並列実行を試す机上検証（今回のような3並列の実験プランニング）は、こうした「暗黙に1 run 前提だった」コードを可視化する副産物になる。

**症状**: gear を設計変数から外した cfg（`actuator_params: {}`）で起動すると `get_attr_design()` の `np.stack` が行長不一致で即死。

**根因**: `xml_robot.py` の `Body.get_params()` が、無関節の root ボディに**固定の `np.zeros(1)`**（= gear 1 次元の代役）を追加していた。gear を外すと関節ボディの寄与が 0 次元になり root だけ 1 次元余る。デフォルト構成でしか通っていないコードパスは、構成を変えた瞬間に壊れる（Bug 10 と同型の教訓）。

**修正**: プレースホルダ次元を「関節ボディが実際に寄与する次元数」（axis 有無 + gear 有無から計算）に動的化。素の pusher 構成で回帰なしをスモーク確認済み。

**副産物の設計知見（M2 の学習不能）**: gear のみ可変・リンク長凍結の条件は全エピソード -50（初期接触ペナルティ）に張り付く。**デフォルト形態（先端 0.55m）は大 cube（左面 0.5m）に最初から貫通しており、脱出手段がリンク長変更しかない**ため。gear 単独ではタスクが開始できない = 「リンク長の可変性はこの環境でタスクを成立させる必要条件」という ablation の部分回答が、起動前に確定した。gear の押し性能への寄与は M2b（arm_safe_init=true で非接触スタート）で分離測定する。

### Bug 16: `_check_initial_contact()` / `compute_reach_bonus()` が平面（Z軸のみ回転）アーム専用の`[:2]`切り詰めをしており、縦型4関節（tripo_arm_v3）で先端位置を常にゼロベクトルへ誤計算していた（2026-07-24 発覚）


と**Z成分を切り捨てている**。水平3〜4関節版（tripo_arm_v2/v2b/v2c、全関節がZ軸=ヨー軸で腕がX-Y平面内を動く）ではこの近似が正しいが、`tripo_arm_v3.xml`は根本がヨー軸（Z軸）・以降3関節がピッチ軸（Y軸）の縦型構造で、静止姿勢（全関節角0°）における各リンクのジオメトリは`fromto="0 0 0  0 0 <長さ>"`——**長さの全成分がローカルZ軸に乗っている**（X, Y成分は常にゼロ）。したがって`[:2]`を取ると、v3では形態に関わらず`link_vec`が恒常的に`(0,0)`になり、**先端位置が肩関節の真上（ほぼ原点）にあると誤認**し続ける。cubeとの距離判定が常に「接触している」扱いになり、Reachはep2以降ずっと-50に張り付いていた。Bug 13の修正時（2026-07-21）は水平3〜4関節版でのみ検証しており、縦型（軸構成が混在するケース）は見落とされていた。

**スモークテスト結果（2026-07-27、3epochのみ）**: 上記の訂正の通り、このReach設定では`_check_initial_contact()`（修正箇所）自体が`check_init_contact=false`で無効化されており、観測された-50は`_check_floor_penetration()`由来だった。3epochとも-50に張り付いたままで（`_arm_tip_pos`のz座標が-0.160と実際に床下に貫通していることを`probe_v3_contact_check.py`で確認）、Leaderがこの3epoch以内に床貫通を避ける形態を学習できるかは未確認（他のペナルティ脱出事例では数十epoch以上を要したものもあり、3epochでの評価は時期尚早）。

### Bug 17: viewer.py実行中、物理は正しく進むのにScene表示だけが一切更新されない — 原因はAISTSimulatorItemの録画モード既定値（2026-07-31発覚）

**症状**: `eval_cnoid_viewer.py`でtripo_arm_v2c_pusherを再生すると、起動直後の形態組み立てフェーズ（`attribute_transform`、後述）はパラパラ漫画のように激しく変化するが、その後の実行フェーズに入るとScene上でアーム・cubeの見た目が一切動かなくなる。ログ上は`reward=298.4 実行ステップ=1000 cube移動=12.044m`と正常な値が出ており、シミュレーション自体は破綻していない。マウス操作の有無・マルチモニタ環境・CPU負荷（学習4本並行稼働）・カメラの画角外への逸脱など複数の仮説を検証したが、いずれも再現しなかった。

```cpp
if(!isRecordingEnabled){
    const double time = frame / worldFrameRate;
    for(auto& simBody : activeSimBodies){
        simBody->impl->updateFrontendBodyStatelWithLastRecords(time);
    }
}
```

という実装で、**`isRecordingEnabled == false`の時だけ、毎flushでフロントエンド（Scene表示に使われるBodyItemの見た目のボディ状態）を更新する**という条件分岐になっていた。録画モードが有効（デフォルト）だと、`tickRequest()`で物理は毎ステップ正しく進み内部バッファには記録されるが、**画面表示への反映だけがスキップされる**。学習（`--no-window`）では表示自体を見ないため誰も気づかなかった。

**副産物: 「起動直後のパラパラ漫画」の仕組み**（バグではなく仕様、調査の過程で判明）: `pusher.py`の`step()`は`skeleton_transform`→`attribute_transform`→`execution`の3段階で進む。`attribute_transform`段階（`skel_transform_nsteps`＝5ステップ程度）は`eval_cnoid_viewer.py`側で`time.sleep()`を挟まず早送りされる。この段階でLeaderが形態パラメータ（bone_offset/gear）を1ステップずつ確定していくが、環境側は`load_model()`を呼ぶたびに`_clear_bodies()`（既存BodyItem全削除）→新しい`.body`を再読み込みという処理を行うため、Itemsパネルと Sceneが数ステップの間に何度も「消えて作り直される」。これが早送り実行と重なって「パラパラ漫画」のように見える。**Bug 17の表示更新が直らなくても、この区間だけは動きが見えていた**理由は、`_clear_bodies()`/`addChildItem()`によるアイテムの構造変更自体はSimulatorItemの録画バッファを経由しない別の更新経路（Itemツリーの直接的な追加・削除）のため、Bug 17の影響を受けなかったからだと考えられる。

### 検証: body[1]（肩リンク）の形態が1000エポック通じて不変に見える点はバグではない（2026-07-29 確認）

**疑問**: 第5章表5.3.1で K2_v2・I1_v2・H1 の body[1] が全て `0.539m/gear400` と完全一致していた点について、「Leaderが実は形態を探索できていない（凍結している）のでは」という疑いが生じ、調査した。

**検証方法**: `scripts/probe_k1_trajectory.py`に`EVAL_EPOCH_STEP`/`EVAL_DECIMALS`/`EVAL_MAX_EPOCH`環境変数を追加し、bone_offsetの生のx,y成分も出力するようにした上で、H1（転用なしの独立training）とK2_v2について10エポックおき・小数点以下6桁の高精度でep10〜100の形態推移を再取得した。

**発覚した副次バグ（プローブスクリプト側）**: 拡張時に2点実装ミスがあった。(1) ループ末尾の`os._exit(0)`直前に`sys.stdout.flush()`がなく、出力行数が少ない条件では Python の内部バッファが OS へ書き出される前にプロセスが強制終了し、標準出力が丸ごと消えていた。(2) `EVAL_EPOCH_STEP=10`に変更した際、元のサンプリング条件`e % step == 10`が`step=10`では恒偽になる（`e % 10`は0〜9しか取らない）というオフバイワン。前者は`print(..., flush=True)`+明示的`sys.stdout.flush()`、後者は条件を`(e - min(eps)) % step == 0`に修正して解消した。

**結果**: body[1]のoffsetは(x,y)=(-0.200,-0.500)、gearは400に、**H1自身の独立trainingでもep20〜30までに収束し、以降ep100まで完全に同一の値で固定**されることを確認した（K2_v2でも同一値）。y成分とgearは設計空間の上限（`design_opt/cfg/pusher.yml`: offset ub=[0.5,0.5]、gear ub=400）に張り付いており、既存の「肘/肩ギア比が上限に収束する」という報告済みの傾向と整合する。x成分（-0.200、境界ではなく設計空間の内部）も、境界に張り付いているわけではないのにH1・K2_v2・I1_v2の3者で完全に同一の値へ収束している。対照的に、body[11]（肘リンク）のoffset/gearはep100時点でもなお明確に変動し続けている（H1: gearが27→400へ単調増加の途中、K2_v2: gearが367〜400の間でエポックごとに揺れている）。

**結論**: body[1]の「1000エポック不変」は転用（K2/I1）由来のバグではない。重み転用のない独立training（H1）でも同じ値に収束することから、**肩リンクの形態パラメータに対する報酬勾配がごく早期（epoch 20〜30程度）に単一の安定解へ収束し、以降は事実上ゼロになる**という、この環境・タスク自体の性質だと考えられる。肘リンク側がより長く変動し続けるのは、肘の形態がタスク性能（打撃速度等）への感度が高く、Followerの制御方策の変化と共適応しながら遅くまで探索が続くためと考えられる。転用元(H1)と転用先(K2/I1)で完全に同一の収束値へ落ち着くこと自体は、形態最適化の再現性・安定性を裏付ける結果であり、Leaderが探索できていないことの証拠ではない。「なぜ肩リンクだけこれほど早く・厳密に収束するのか」という力学的な理由は本調査では未検証（修論のスコープ上必須ではないため据え置き）。

**メタ教訓**: 「値が全く変化しない」という観測は、必ず**転用なしの独立trainingで同じ現象が起きるかを比較する**まで「バグ」と決めつけないこと。今回はH1という理想的な対照（同一環境・同一報酬・転用なし）が既に存在したため、1回の追加probeで即座に切り分けられた。

### Bug 21: 形態診断が「3秒で終わっているのに 30 分かかっている」ように見えていた — Choreonoid 経由だと出力後もプロセスが終了しない（2026-08-07 発覚）

```
[11:08:25] tripo_pj_short 開始
[11:38:25] tripo_pj_short 完了
[12:08:25] tripo_pj_mid 完了      ← 全部ちょうど 1800 秒
```

30 分は `timeout -s KILL 1800` に指定した値そのものである。つまり
**毎回タイムアウトで kill されていた**。

**実際にかかっている時間**: 出力ファイルの mtime を見ると、どれも開始の **3 秒後**だった。

```
開始 11:08:25 → tripo_pj_short.txt mtime 11:08:28
```

**なぜ重要か（見逃すと研究の主張がぶれる）**:
- 診断のコストは論文の主張に直結する。「学習 30 エポック（約4時間）に対して診断は数秒」

  6条件で 3 時間待ったのは全て無駄。

### Bug 22: 診断が返す拡大倍率が**切り捨て**られ、助言どおりに直しても届かない形態になっていた（2026-08-07 発覚）


**原因**: 必要倍率の表示が `f'{need:.2f}'`、すなわち**四捨五入**だった。
実際に必要なのは 0.800 / 0.4031 = **1.9846** 倍だが、これが「1.98」に丸められる。
下方向に丸まるため、**助言どおりに直すと 2 mm 足りない**。

Pusher 側（2.1086 → 「2.11」）は**たまたま切り上がっていた**だけで、同じ欠陥を抱えていた。

**修正**: `math.ceil(need * 100) / 100` で切り上げる。さらに下限ちょうどでは
腕を伸ばしきった特異姿勢でしか目標に触れられないため、**余裕 10% を含めた推奨値を主として示し、
下限を括弧で併記する**形に改めた（`scale_advice()`）。

```
→ 腕全体を **2.19 倍**に伸ばしてください。
  （1.99 倍で計算上は届きますが、腕を伸ばしきった姿勢でしか触れられないため余裕を含めた値を示しています）
```

**なぜ長く気づかなかったか**: 診断の検証が「不適合を**検出**できるか」で止まっており、
**「助言に従ったらどうなるか」を一度も実行していなかった**。

「システムとしての評価」へ組み替える過程で閉ループを組んだ瞬間に露見した。

**教訓**: **助言を返す機能は、助言に従った結果を実際に作って再入力するまで検証したことにならない。**
出力の正しさ（不適合を検出できたか）と、出力の**有用性**（従えば解決するか）は別物である。
反実仮想説明・実行可能な救済（第2章 2.4）を名乗る以上、後者の検証が要る。

**影響範囲**: 「1.98 倍以上」を引用していた本文・記録 8 箇所を「2.19 倍（下限 1.99 倍）」へ同期した。

### Bug 23: スケール XML 生成器が `body pos` を伸ばさず、生成した形態の実効リーチが公称の 6 割しかなかった（2026-08-10 発覚）

|---|---|---|---|
| `tripo_pj_short` | −396.92 | 0.3969 m | 0.3969 m ✅ |

| `tripo_pjr_min_s2` | −296.24 | 0.2962 m | **0.2962 m ✅** |

**形態を生成する道具は、生成物を別経路で検算するまで信用しない。**

### Bug 24: 診断の第1層が非平面アームのリーチを過大評価する — 「総リンク長＝到達半径」は平面アームでしか成り立たない（2026-08-10 発覚・修正）

**発覚の経緯**: Bug 23 の修正後、`tripo_v3_reach`（非平面4関節での Reach）を起動する前に
目標位置を決めようとして、手計算と診断の出力が食い違うことに気づいた。

```
診断（修正前）: 総リーチ 1.002 m → 目標 0.800 m は ✅ 余裕 20%
手計算        : 水平到達限界は 0.797 m → 目標 0.800 m は ❌ 届かない
```

**原因**: 第1層はリンク長の総和をそのまま到達半径として使っていた。これは
**全関節が同一軸を向いた平面アーム**でしか成り立たない。`tripo_arm_v3` は
根元がヨー（z軸）、以降がピッチ（y軸）で、**根元の 0.202 m はヨー軸に平行な鉛直支柱**である。
この支柱はヨー回転では水平方向に伸びず、肩の高さを上げるだけなので、
水平に伸びるのは残り 3 リンクの 0.800 m しかない。目標高さ z=0.15 m（肩は 0.222 m）では
さらに sqrt(0.800² − 0.072²) = **0.797 m** に減る。

**影響**: 実験結果への影響はない（v3 で完走しているのは Pusher のみで、Pusher の判定は
cube 位置を使う別経路）。ただし**あと一歩で 1000 エポックを無駄にするところだった**。
標準の target_x=0.8 のまま起動すれば、余裕 0% = Bug 23 で無効化された条件と同じ
「原理的に届かない実験」になっていた。

**修正**: 各リンクを**自分自身の関節軸**と比べ、軸に平行なリンク（＝その関節では振れない）を
水平リーチから除外する。目標高さでの水平到達限界を計算し、非平面アームではその値で判定する。

⚠️ **実装上の落とし穴**: geom の `fromto` は**そのボディのローカル系**で書かれている。
最初は世界座標の z 軸と比較する実装にしたが、v3 は全リンクが静止姿勢でローカル z を向いているため
「全リンクが平行」と誤判定して警告が出なかった。**比較相手はそのリンク自身の関節軸でなければならない。**

**残る限界**: この修正が正しいのは「ヨー支柱 + 同一軸のピッチ鎖」という構成までである。
関節軸が3種類以上混ざる一般の腕では、正確な到達範囲は関節可動域込みの順運動学が要り、
第1層（学習不要・1秒）の範囲を超える。**第1層は「平面アーム、またはヨー＋単一平面ピッチ鎖」
に限って厳密**であり、それ以外では上限の目安として読むべきである。

**教訓（Bug 23 と同じ形）**: 幾何の判定器は、**どの構成までを前提にしているかを明示しない限り、
前提の外で静かに間違える**。総和・平均・単純和で済ませている量を見たら、
「この式が成り立つ形はどれか」を必ず書き添える。

### Bug 28: 根元リンクのローカル原点が形状の外にあり、台座が自分の外側を公転していた（2026-09-02 発覚・修正）

**症状**: A1 の URDF を Choreonoid で見ると、**台座（リンク0）が回転中心を自分の中に持たず、
オブジェクトごと大きく振り回されて回る**。

**原因**: `glb_to_links.py` が根元リンクのローカル原点を **XY=(0,0) 決め打ち**にしていた。

```python
frame_origins = [np.array([0.0, 0.0, z_min])]   # ← XY が (0,0) 固定
```

GLB の原点が台座の真下にあるとは限らない。A1 では台座が x ∈ [−0.332, −0.157] にあり、
**原点が形状の 0.157 m 外**に出た。URDF の `world_to_base` は Z 軸まわりの回転なので、
台座は自分から 0.16〜0.33 m 離れた軸のまわりを**公転**する。

| 形態 | base の x 範囲（ローカル） | 原点 x=0 | 第1関節 J1 の XY |
|---|---|---|---|
| `tripo_arm_v2c` | [−0.114, +0.114] | 内側 ✅ | (+0.0004, −0.0002) |
| `e2e_a1` | [−0.332, −0.157] | **0.157 m 外側 ❌** | (−0.2428, −0.0094) |

**Bug 27 と同じ構図**: 「GLB は原点中心に鉛直な腕が立っている」という暗黙の前提があり、
**A1 が初めてその前提を破った**。v2c では J1 の XY がたまたま原点と一致していたため露見しなかった。

**影響範囲は可視化のみ。学習には影響しない。**
学習用 MuJoCo XML は台座メッシュを使わず、`<body name="0">` は
`pos="0 0 0.15"` の球で、リンクはすべてカプセルである。さらに `FIXED_BASE=1` により
台座は可動リンクから除外され `topology.json` に入らない。
実際、修正の前後で `topology.json` は**バイト単位で変化しなかった**（確認済み）。
したがって**再実行は不要**。

**修正**: 根元リンクの原点に**第1関節の XY**（＝ヨー軸が通る位置）を使う。
台座は第1関節の真下にあるはずで、実測でも両者の XY のずれは A1 で 3.6 mm、v2c で 0.5 mm しかない。
関節が1つも無い場合は形状の XY 重心へフォールバックする。

**修正後**: 台座 STL は x ∈ [−0.089, +0.085] となり原点が内側に入った。
URDF の `joint_to_upper_arm` の原点も `(−0.2428, −0.0094, 0.2195)` から
`(0, 0, 0.2195)` になり、第1関節が台座の真上に来る。
副次的に、台座の `link_length`（＝台座高）も 0.3276 m → **0.2195 m** と正しくなった
（従来は水平方向のずれを含んだ斜め距離だった）。

### Bug 30: マーカーの Z クラスタリングが、リンクの短い腕で隣り合う球を融合していた（2026-09-02 発覚・修正）

**症状**: B1（短くずんぐりした腕）を通したところ、**関節が 3 個ではなく 2 個しか検出されなかった**。

**原因**: `_detect_joint_z` は**マーカー頂点の Z 座標だけ**を見て、隣接値の差が
0.05 m を超えた位置で区切っていた。マーカー球は有限の大きさを持つため、
**リンクが短く腕が傾いていると隣り合う球の Z 範囲が重なり、2 個が 1 個に融合する。**

B1 の実測: 球の Z 方向の広がり約 0.14 に対し、関節間の Z 差が **0.127**。重なっている。
A1 では Z 差が 0.23〜0.28 あり余裕で分離できていた。

**修正**: **3 次元の連結成分**でクラスタリングする（`_detect_joints_3d`）。
球どうしは 3 次元では必ずリンク長ぶん離れている（B1 で 0.24〜0.26、球の半径 0.07）ため確実に分離できる。
実測では連結半径 0.01 / 0.02 / 0.03 のいずれでも同じ 3 個を返し、**閾値に鈍感**であることを確認した。
連結半径はメッシュの外接寸法に対する相対量で与えるためスケール不変。

| | 旧（Z のみ） | 新（3D 連結成分） |
|---|---|---|
| B1 | ❌ 2 個（J2 と J3 が融合） | ✅ **3 個**（0.5310 / 0.7601 / 0.8867） |
| A1 | ✅ 3 個 | ✅ 3 個（0.2196 / 0.4960 / 0.7258、**退行なし**） |

旧方式は `--cluster-mode z` で使える。

**この改良は第3章 3.8 節が「この閾値を関節間隔やメッシュの外接寸法に対する相対量として
定義し直すことは、本手法の適用範囲を広げるうえで残された改良点」と述べていた箇所に対応する。**

### Bug 31: Bug 27 の是正が先端リンクを除外していたが、短い腕では +52.6 % 過大だった（2026-09-02 発覚・修正）

**経緯**: Bug 27 の是正では、bone_offset を OBB 主軸長から**関節間距離**へ置き換えた。
ただし**先端リンクは子関節が無く関節間距離が定義できない**ため OBB のまま残し、
「A1 で実測誤差 +0.7 % と小さい」ことを根拠にしていた。

**症状**: B1 では先端リンクの OBB が **0.4316 m**、実際の J3→先端の距離は **0.2828 m**。
**+52.6 % 過大**だった。総リーチが 0.938 m となり、第1層が「✅ 余裕 15 %」と誤って通した。

**原因**: 分割面が球の中心を通るため、上半球が**全方向へ**張り出す。
腕が傾いていると OBB の主軸がその張り出しを拾う。
A1 で誤差が小さかったのは**リンクが球に対して十分長かった**からで、
性質として安全だったわけではない。**根拠にした A1 の +0.7 % は、たまたま条件が良かっただけだった。**

**修正**: 先端リンクの長さを「**最後の関節から最も遠い頂点までの距離**」とする。
これは運動学的な寄与そのものである。

| | 修正前（OBB） | 修正後（最遠点） | 実距離 |
|---|---|---|---|
| B1 先端 | 0.4316 m | **0.2828 m** | 0.2828 m |
| A1 先端 | 0.2763 m | 0.2743 m | 0.2743 m |

**A1 への影響は 2 mm（0.2 %）で、学習中のため再生成していない。**
B1 は修正後の値で生成した。

**教訓**: 「実測で誤差が小さいから除外してよい」という判断を、**1 例だけ**で下していた。
その 1 例が条件の良い側だったため、条件の悪い入力が来るまで露見しなかった。
Bug 27・28・29 と同じく、**A1 が満たしていた前提を B1 が破った**構図である。

**✅ 修正後の再生成で解消を確認（2026-09-03）**:

### Bug 35: コンテナを止めるとキューが「中途半端に進んだ run」で無言のまま固まる（2026-09-04 発覚・修正）

**発覚の経緯**: 「コンテナを止めたら学習スケジュールも止まるが、それは引き継ぎに書いてあるか」
と聞かれて調べたところ、**書いていないだけでなく、書いても防げない**ことが分かった。

**症状（起きるはずだったこと）**: コンテナを止めると学習プロセスもキューも死ぬ。
そこでキューを起動し直すと、**期限まで無言で待ち続けて何も投入せずに終わる。**

**原因**: 実施済み判定が「ログが空でないか」の 2 値だった。

```bash
if [ -s "single_run/$1/log/log_train.txt" ]; then log "$1 は既存。スキップ"; continue; fi
```

コンテナ停止で死んだ run は **ログが空でないのに `training done!` が無い**。

1. キューは「既存」と見て**再投入しない**
2. 次の段が `done_p` で**その run の完走を待つ**
3. 誰も走らせないので**完走しない** → 期限まで `sleep 300` を回して終了

**Bug 32 ② と同じ穴である。** あのときは「ディレクトリの有無」で判定していたのを
「ログが空でないこと」へ直した。**2 値である限り、状態が 3 つ以上あれば必ずどれかが潰れる。**

| run の状態 | 旧判定 | 正しい扱い |
|---|---|---|
| 完走済み | 既存 → スキップ | スキップ ✅ |
| **稼働中** | 既存 → スキップ | スキップ（キュー二重起動でも二重投入しない） |
| **途中で死んだ・checkpoint あり** | **既存 → スキップ ❌ 固まる** | **そこから再開** |
| **途中で死んだ・checkpoint なし** | **既存 → スキップ ❌ 固まる** | 退避して最初から |

**修正**: 判定を 4 状態に分けた（`queue_e2e_a1.sh`）。

- `done_p` … `training done!` があるか
- `alive_p` … **`hydra.run.dir` で照合**する。`[c]` で grep 自身を避け（Bug 19）、
  末尾を `( |$)` で閉じる（閉じないと `e2e_a2v_reach` が `e2e_a2v_reach_s2` にも当たる）
- `latest_ckpt` … `models/epoch_NNNN.p` の最大値。`+restore_dir` + `epoch=<N>` で再開する
  （**`reset_epoch` は付けない**。epoch カウンタを継続させる）

**教訓**: **「やったか / やっていないか」の 2 値で実験を管理しない。**
実験は「完走・稼働中・死んだ（再開できる）・死んだ（再開できない）」の 4 状態を持つ。
2 値に潰すと、**潰した先で必ず無言で止まる**。Bug 32 と合わせて**同じ失敗を 2 回**している。

### Bug 40: `joints.json` は**全体座標**、分割済みメッシュは**リンク局所座標**（2026-09-11 発覚）

**出荷されたバグではない。** M4 の是正（9-75）を測っている最中に踏んだ**計測側の誤り**だが、
**同じ取り違えを次の人も必ずやる**ので残す。

#### 症状

先端リンクのボーン軸が**実物 5 例すべてで 24.7〜74.1° ずれている**という測定結果が出た。
「手先は平たいから直方体が斜めを向くのだろう」と読んでしまい、**その誤った数字を口にした。**

#### 原因

| データ | 座標系 |
|---|---|
| `joints.json` の `frame_origins` / `joint_positions` | **GLB の全体座標** |
| `data/test/*/meshes/*.stl`（分割済み） | ⭐ **リンク局所座標。自分の関節が原点** |

先端リンクの軸を「最遠点 − `frame_origins[先端]`」で出していたが、
**最遠点は局所系、`frame_origins` は全体系**である。**引き算が成立していない。**

⚠️ **中間リンクは無事だった。** 「次の関節 − 自分の関節」は**全体系どうしの差**なので、
平行移動が打ち消える。**だから半分だけ正しく、半分だけ壊れるという気づきにくい形で出た。**

#### 直し方

**先端リンクは局所系の原点（= ゼロ）から測る。**

```python
if i + 1 < len(names):
    d = frame_origins[names[i+1]] - frame_origins[names[i]]   # 全体系どうしの差
else:
    d = V[np.linalg.norm(V, axis=1).argmax()]                 # 局所系の原点から
```

直すと先端のずれは **1.5〜21.5°** になった。

#### 見分け方

**局所系なら、各メッシュの原点最近傍頂点がリンク半径くらいの距離にある**（関節は本体の中）。

```bash
python3 -c "
import trimesh,numpy as np
V=np.asarray(trimesh.load('data/test/B1/meshes/hand.stl').vertices)
print('原点最近傍', np.linalg.norm(V,axis=1).min())"   # 0.079 m ≒ リンク半径 → 局所系
```

⚠️ **`glb_to_links.py` は全体系のまま計算しているので正しい。** 取り違えが起きるのは
**分割後の STL を読む側**（`mesh_to_params.py` とその周辺の計測スクリプト）である。

## Bug 52: 初期姿勢の式が、存在しない形状を記述していた（2026-10-02、系譜 9-196・9-197）

⛔ **なのに式は `tip_y = R·sin(90°) = 1.0425` と主張していた。**

### ⛔⛔ 教訓 — **机上検算は「そのモデルの中で」正しかった**

9-193 で「窓 [15.8°, 25.6°] → 初期肩角 20.7°」を机上検算し、**正しいと確認して投入した。**
