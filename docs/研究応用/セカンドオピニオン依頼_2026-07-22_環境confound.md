## なぜこの依頼を作ったか

2026-07-21〜22の1日で、tripo_arm（Tripo3D生成メッシュ由来の3〜4関節アーム）に関する環境confoundを4件、Claude自身が発見・修正した:

1. cube の damping が rrbot の1/5だった（環境間の物理不整合）
2. 関節可動域が rrbot にも実測にも一致しない値だった
3. 初期接触判定コードが2関節専用ハードコードで3〜4関節では機能不全だった（Bug 13）
4. 並列学習時のworker一時ディレクトリ衝突（Bug 14）

さらに遡って、修論第4章（重み転用）と第5章（M系ablation）にも「200epoch打ち切りに十分性の根拠がない」という同型の問題が見つかった。

**この「発見→修正」のサイクル自体が全て同一セッション内でClaude単独の判断によるもの**であり、外部の目が一度も入っていない。見落としや過剰反応（本当は些細な問題を過大評価している、または逆に見えていない別の問題がある）がないか、独立した視点で検証してほしい。

### 1. cube damping confound

tripo_arm_v2（水平3関節）で Pusher タスクを完走したところ、exec_R_eps が 844.25 を記録した。
これは同条件の rrbot_arm（2関節）での確立済み結果（102.16 / 145.35）の6〜8倍だった。

検証のため、学習済みモデルで cube の軌跡を実測するプローブを実行した:
- rrbot: cube 最終到達距離 4.393m、peak速度 11.09 m/s
- tripo: cube 最終到達距離 30.142m、peak速度 21.49 m/s

速度比は1.94倍だが距離比は6.86倍で、速度の2乗則（3.75倍）でも説明できない超過があった。

環境定義ファイル（MuJoCo XML）を比較したところ、cube の質量は両環境で同一（2.7kg）に
調整されていたが、slide joint の damping（速度に比例する粘性減衰）が rrbot は10.0、
tripo は2.0（1/5）だった。理論上、停止距離は「初速×質量÷damping」に比例するため、
damping の違いだけで9.7倍の差が出る計算になり、実測差（6.86倍）はこの範囲に収まっていた。

原因は、tripo環境をパイプラインで生成した際、cube のサイズを Tripo3D 由来の
スケールに合わせて縮小し、density を調整して質量を揃えたが、damping パラメータの
調整を忘れていたことだった（生成コミットの diff で確認）。

対応として、damping のみ rrbot に合わせた修正版（tripo_arm_v2b）と、
関節可動域も含めて完全に rrbot 準拠にした修正版（tripo_arm_v2c）を作成し、
元のバージョン（tripo_arm_v2、damping=2.0）は履歴として保持しつつ、
数値を rrbot と直接比較しないよう注記した。

### 2. 関節可動域の不一致

tripo_arm_v2/v2b の関節可動域（肩±60°・肘±90°・手首±45°）は、rrbot（全関節±180°）にも、
実際のメッシュ生成元ロボット（3関節とも±90°）にも一致しなかった。

調査の結果、この値は環境生成パイプラインを手動実行した際、パイプラインスクリプトの
ヘルプコメントに記載されていた「例示値」をそのまま使い回したものであり、
物理的な必然性や意図的な設計判断の記録は見当たらなかった。

この可動域の制限下で tripo_arm_v2 の Pusher 高得点が達成されていたため、
可動域も rrbot 準拠（全関節±180°）にした tripo_arm_v2c を作成し、
damping のみ修正した v2b と合わせて3系統（v2→v2b→v2c）で
「damping単体の効果」と「可動域を含めた効果」を分離して比較できるようにした。

### 3. 初期接触判定のハードコード（Bug 13）

Pusher/Target-Pusherタスクには、学習開始時にアーム先端がキューブに
既に接触している「初期接触」形態を検出し、ペナルティを与えて
Leaderの探索から排除する機構がある。この判定コードは以下のようになっていた:

```python
bo1 = bodies[1].bone_offset   # 1本目のリンクのみ
bo11 = bodies[-1].bone_offset # 最後のリンクのみ
link_vec = bo1 + bo11         # 中間リンクは無視
```

rrbot（2関節）ではこの2本の合計が全リンクの合計と一致するため問題なく機能していたが、
tripo（3〜4関節）では中間リンクが計算から漏れ、アーム先端位置を
3関節構成で37%、4関節構成で59.6%過小評価していた。加えて、
キューブの半径として使われるフォールバック値も rrbot 専用の値（0.5m）が
ハードコードされており、tripo の実際のキューブ半径（0.15m）とは
2.5倍以上の乖離があった。

この判定は Pusher/Target-Pusherタスクではデフォルトで有効（Reachタスクのみ
明示的に無効化されていた）であるため、tripo の Pusher/Target-Pusher系の
run すべてに影響していたと考えられる。

修正として、全ての非ルートリンクの bone_offset を合計する方式に一般化し、
キューブ半径は環境定義ファイルから正規表現で実測する方式に変更した。
rrbot（2関節）では数値上の変化がないことを確認した。

### 4. 並列学習時のworker一時ディレクトリ衝突（Bug 14）

学習の並列実行時、あるrunのサブプロセス群（4並列のworker）が
起動28分後も最初のエポックの記録を出力しない現象が発生した。
プロセスのCPU使用率は5%程度で推移しており、待機状態にあることが疑われた。

調査の結果、各workerが使う一時ディレクトリ（ログ・チェックポイント保存先）が
「そのrun内でのworker番号（0〜3の連番）」のみで構成されており、
run をまたいで同じパスになっていた。複数runを並列起動すると、
全runのworker0同士・worker1同士が同じ一時ファイルを取り合っていた。

修正として、workerの一時ディレクトリ名に親プロセスのPIDを含めることで
run間で一意になるようにした。

なお、この症状の直接の原因は上記のworkerパス衝突ではなく、
Bug 13修正の実装中に混入した別の実装ミス（バイト列と文字列の型不一致による
例外発生）だったことが後に判明した。この例外はシミュレータが
握りつぶす仕様のため、外部からは「ハングしている」ように見え、
プロセスの状態（待機理由）から間接的に原因を推測しようとして
別の実在する問題（worker パス衝突）に先に行き当たり、
それを主因と誤認しかけた。最終的にはworkerプロセス自身の出力ログを
直接確認して真因を特定した。

### 5. 修論第4章・第5章での同型の問題

上記の環境確認と並行して、修論の既存章にも「エポック数の打ち切りに
十分性の根拠がない」という同型の懸念が見つかった。

第4章の重み転用実験は、当初「制御方策のみ転用」「形態のみ転用」
「両方転用」の3条件を200エポックで比較し、転用条件間で明確な順位が
出たと報告していた。しかし転用起動時に指定すべきチェックポイント読み込み
オプションが実際には一度も指定されておらず、3条件とも実質的に
ゼロからの学習だったことが判明した（別の日に発覚した既知の問題）。
`epoch=best` を明示して再実験したところ、全転用条件はエポック0時点で
転用元の性能水準に達し、部分転用条件は低い値から始まった
（半分のネットワークがランダム初期化のままのため、物理的に妥当）。

第5章のablation実験（リンク長のみ可変・ギア比のみ可変の2条件、
各200エポック）は、「両方可変」条件との性能差からそれぞれの寄与率を
46%・19%と算出していた。この算出は既に「エポック数を揃えていない
比較は寄与率に学習量の差を混入させる」との注記があったが、
今回改めて学習曲線の末尾を確認したところ、ギア比のみ条件は
200エポック時点でもまだ明確に性能が上昇中であり、収束していなかった
（リンク長のみ条件は安定していた）。したがって19%という寄与率は
過小評価の可能性がある。

この2件はいずれも1000エポックでの再実験を計画したが、計算資源の
制約から一部は実行中、一部は着手待ちの状態にある。
