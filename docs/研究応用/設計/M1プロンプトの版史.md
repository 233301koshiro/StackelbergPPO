## 各版の詳細

### 版 0.5 が一番大きい — **基準の誤りを実測で見つけた**

「Tripo3D が画像サイズでスケールを決めていないか」を実測で確かめた結果、
**GLB 4 件すべてでバウンディングボックスの最長辺がきっかり 1.0000** だった。

**したがって効くのは絵の中の比率だけである。**
画素サイズ・トリミング・定規で測った絶対寸法は**スケールに効かない**。

```
絶対リーチ ≒ 腕の長さ ÷ 絵全体の最大寸法（台座込み）
A1 で検算: 1.0076 ÷ 1.0 = 1.0102 m  → XML 実測と一致
```

⚠️ **この事実は「解像度が違う入力を混ぜてよいか」にも答える。**
2026-09-10 の 9-68 で v1 だけ 1760×2428、他が 742×1024 だったとき
「M2 の交絡になる」と書きかけたが、**スケールには効かない**。
残る懸念は**メッシュの細かさ**であって、縮尺ではない。

### 版 B の教訓が §4-2 の規律になった

**同じ性質の 2 つのプロンプト（参照画生成用と M1 用）で、片方にしかない制約は疑う。**
Bug 33 はまさにそれで、参照画側に最初からあった 3 行が M1 側に無かった。
CLAUDE.md §4-2「2 箇所に同じことを書く構造」の実例のひとつ。

### 版 C の限界が 9-68 で露出した

版 C は「今後の入力ではこの例外が効く」と書いた。**効かないことがある。**
同じ写真・同じプロンプトで 4 回生成し、**1 本が鉛直から 42.5°** で出た。

| 出力 | 傾き | 判定 |
|---|---|---|
| v1 | 5.4° | ✅ |
| **v2** | **42.5°** | ❌ **寝ている** |
| v3 | 23.4° | ✅ |
| v4 | 7.6° | ✅ |

⚠️ **これは温度を下げても直らない類の欠陥である。** プロンプトが曖昧なら
低温では**一貫して間違える**だけで、むしろ気づきにくくなる。**版 E が要る。**

## 版 E をどう作り、どう示すか（2026-09-10 決定）

**方針**: [研究方針.md](../方針/研究方針.md) の「M1・M2 の API 化」を参照。

1. **API で seed と temperature を固定**し、運用のばらつきを最小化する
2. その条件で**版ごとに n 回**生成し、**仕様遵守率**を測る
3. **「この最終プロンプトなら仕様を満たす」を実験で示す節**を修論に置く

✅ **API の実在は 2026-09-10 に確認済み**（[研究方針.md](../方針/研究方針.md)）。
**M2 Tripo は `model_seed` で同一出力を公式に保証し、`model_version` も固定できる。**
**M1 Gemini は seed があっても決定性を保証しないと公式が明記している。**
→ **M2 を固定できるので、残る揺れを M1 に帰属できる。** Web UI では不可能だった切り分けが成立する。

⚠️ **「温度 0 にしたので出力は変わらない」とは書かない。** 低温でもばらつきは残る
（画像生成で効くのは主に seed であり、テキストでもビット再現はしない）。
**主張は「ばらつきを抑えたうえで、仕様の遵守率が版を追って上がった」**にする。

### 測る指標（ばらつきの大きさではなく**遵守率**）

| 指標 | 見るもの |
|---|---|
| 向きの遵守 | 鉛直からの傾き（`check_glb_pose.py` の Z の広がりでも可） |
| マーカー数 | 関節ごとに球が 1 個ずつ、計 3 個 |
| 禁止物 | 寸法線・文字・複数ビューが無いこと |
| 比の保存 | ⚠️ **画像からは測らない**（遠近で歪む、9-22③）。**XML まで通して測る** |
