## 1. 研究の一言要約

「手描きスケッチ → co-design（Stackelberg PPO）でロボット形態のタスク適性を判定するシステム」の修士研究（2月修論・10月中間発表）。

**コア主張（rrbot 2関節、確定）**: シンプルな報酬のみで、3タスク × 2 seed において co-design はタスクごとに異なる形態と行動類型に収束する（タスク識別 = YES）。

**tripo アーム（3〜4関節、Tripo3D生成メッシュ由来）での検証は 2026-08-03 時点で大きく進んだ**: 水平3関節版(v2c)で3タスク完走・タスク識別の再現を確認し、さらに「同一タスクで良い/悪いスケッチ形態を判別できるか」（PJ実験）も tripo 系で実証した（第4章4.3.3.2）。これは研究の最終目標に対して最も本質的に残っていたギャップだった。その後 2026-08-04 に**判別解像度とマトリクス判定も決着した**——到達可能な形態同士（0.887 m 対 1.451 m）でも 3.6 倍のスコア差が付き、さらに Reach と Pusher で**順位が反転**した（第4章 4.3.3.3）。現在も未決着なのは縦型4関節版(v3)の本走のみ（完走見込み 8/7）。

## 2. これまでの経緯（要点のみ。現在地は冒頭の枠を見ること）

### ⚠️ tripo_arm の damping・関節可動域 confound と修正の経緯（最重要、必読）

tripo 系に v2 / v2b / v2c / v3 という複数世代が存在する理由がこれ。**新しく tripo 系の数値を扱うときは必ず読むこと。**

1. **2026-07-17〜21**: tripo_arm_v2（水平3関節）で3タスクを完走。Pusher が exec_R_eps **844.25** と rrbot L2（102〜145）の6〜8倍を記録
2. **発覚①**: cube damping が rrbot(10.0) の1/5(2.0)しかなく、これが主因と判明（`probe_cube_trace.py` で軌跡実測）
3. **発覚②**: 関節可動域も rrbot（全関節±180°）と不一致（肩±60°等）と判明
4. **対応**: 一度に2つ直すと交絡するため**段階的に分離**した — `v2`（旧・履歴として維持）→ `v2b`（damping のみ修正）→ `v2c`（damping+可動域とも修正）。縦型 `v3` は別系統（後述）
5. **発覚③④（Bug 13/14）**: 調査の過程で `_check_initial_contact()` の2関節ハードコード、worker 一時ディレクトリの並列衝突が判明。両方修正済み

**✅ 決着（2026-08-03、実験系譜.md 9-1）**: v2b_reach の完走により切り分け完了。Reach の best は TA −1.34 / v2b −1.92 / v2c −8.27 で、**TA→v2c の差は damping ではなく関節可動域の拡大が主因**（悪化幅 0.58 対 6.35）。
なお **`tripo_arm_v2` の Pusher 844.25 は damping confound 込みの数値なので、rrbot と直接比較しないこと**（この注記は今も有効）。

### tripo 系の世代の違い（v2系 と v3 は別物）

- **v2 / v2b / v2c**: 自動パイプライン経由。`FIXED_BASE=1` で台座を関節から除外し、`mesh_to_params.py` が全関節軸を Z（ヨー）に固定するため、**3関節・水平面内の平面アーム**になる
- **v3**: パイプラインを通さず、colorful2 URDF の実測値を人手で書き起こしたもの。**4関節・縦型**（根本ヨー＋肩肘手首ピッチ）で、静止姿勢では腕が天を向く

詳細は [メッシュXMLパイプライン.md](設計/メッシュXMLパイプライン.md) §8-3。

### ⚠️ コンテナを止めると、学習もキューも止まる

**学習プロセスもキュー（`scripts/queue_e2e_a1.sh`）もコンテナの中で動いているので、
コンテナを止めると両方消える。** キューは自動では復活しない。**手で入れ直す。**

```bash
cd /userdir/StackelbergPPO
nohup bash scripts/queue_e2e_a1.sh > /dev/null 2>&1 & disown
tail -f single_run/queue_e2e_a1.log     # 判定を確認する
```

**入れ直せば、途中で死んだ run は checkpoint から自動で再開される**（2026-09-04 以降。Bug 35）。
ログには次のどれかが出るので、**意図と合っているか必ず読むこと**。

| ログ | 意味 |
|---|---|
| `... は完走済み。スキップ` | 何もしない |
| `... は稼働中。スキップ` | 既に走っている（キューを二重起動しても二重投入しない） |
| **`... は epoch N まで進んで止まっている → そこから再開する`** | **コンテナ停止からの復帰はこれ** |
| `... は checkpoint も無い → ... へ退避し最初から投入する` | 起動直後に死んだ場合 |

⚠️ **2026-09-04 より前は、この状況でキューが期限まで無言で待ち続けて何もしなかった**（Bug 35）。
古いキューを流用しないこと。

⚠️ **止める前に**: `single_run/` は層①の原本なので消さない。
再開に使う checkpoint は `single_run/<run>/models/epoch_NNNN.p`（10 epoch ごと）。

**キューを書き換えるときは、先に PID 指定で止めてから**。
bash は実行中のスクリプトを読み進めるので、走っている最中に書き換えると壊れる。

```bash
ps -eo pid,args | grep "[q]ueue_e2e_a1.sh"   # PID を特定
kill <PID>                                    # ← パターンではなく PID（Bug 19）
```

## 4. 落とし穴（新セッションが踏みがちなもの）

- **⚠️ 稼働待ちを `pgrep -f 'hydra.run.dir=single_run/<run>'` で書かない（Bug 19）**。そのコマンドライン自身が
  文字列を含むため、`experiment_queue.sh` の同じ `pgrep` に検出され「まだ稼働中」と誤認させてキューを止める。
  ブラケット記法は自己マッチしか防げず、他人のウォッチャーからは見える。実際に 8/6 に約6分キューを止めた。
  稼働 run を調べたいときは **run 名をコマンドラインに書かず**全列挙する:
  ```bash
  ps -eo pid,cmd --no-headers | grep -oP 'hydra\.run\.dir=single_run/\K[a-zA-Z0-9_]+' | sort | uniq -c
  ```
- **`pgrep` でスクリプト名を探すときは `-f` が必須**。`pgrep -c '[e]xperiment_queue'` はプロセス名（`bash`）としか
  照合しないので常に 0 を返す。`pgrep -cf` が正しい（8/6 に「キューが死んだ」と誤判定した）
- **学習曲線を解析するときは `single_run/<run>/log/log_train.txt` を読む。`stdout.log` は再開で先頭が消える**
  （Bug 18、2026-08-06）。実際に M2b は stdout が ep390 からしか無く、順位確定エポックを誤読した。
  best 値だけなら末尾に出ることが多く影響しにくいが、**曲線の形や序盤の順位を見る解析は必ず log_train.txt**。


- **Bug 8**: `pgrep/pkill -f` は自分自身にマッチする。ブラケット記法（`pgrep -f "foo_[b]ar"`）を使い、kill 系は単独の Bash 呼び出しで実行
- **学習の起動形式**: `nohup env USE_CHOREONOID=1 OMP_NUM_THREADS=1 /choreonoid_ws/install/bin/choreonoid --no-window --python scripts/choreonoid_train.py cfg=... hydra.run.dir=single_run/<name> > .../stdout.log 2>&1 &`（bash -c で包まない）
- **Bug 12（転用の必須引数）**: 転用起動は `+restore_dir=... epoch=best` の**両方**が必要。`epoch=best` を忘れると重みはロードされず無言でゼロスタートになる。転用 run を起動したら ep0 の exec_R_eps が転用元 final に近いことを必ず確認する
- **Bug 13（新アーム形状の env コード前提）**: `env_specs.get(key, <ハードコード値>)` パターンは、その値が特定アーム専用でないか要確認。新アーム追加時は学習中欠陥チェックリスト.md の②を実施
- **Bug 14（並列実行時のworkerパス衝突）**: 修正済みだが、新しい共有一時リソースを追加するコードを書くときは複数run同時起動でも衝突しないか確認する
- **ハングに見えるクラッシュ**: Choreonoid は `--python` スクリプト内の例外を握りつぶし Qt ループだけ残すため、CPU使用率が低いまま止まって見える。真っ先にプロセス自身の生ログ（stdout・`/tmp/cnoid_worker_*.log`）を確認する（状況証拠より先に）
- **並列本数と ETA**: 3並列を超えると CPU 競合で ETA が大きく悪化する（9並列で1本のETAが14日まで悪化した実測あり）。並列起動前に `uptime`/`free -g` を確認し、必要なら優先度の低い run を止める
- **epoch数の妥当性**: 「200epで十分」に根拠はない。I1 vs I2 は ep200→240→600 で順位が2回反転した実測があり、単一epoch数での判定は避ける（詳細: 実験系譜.md）
- **eval スクリプト**: `timeout -s KILL` 必須（Qt が例外を握って hang する）、`torch.set_default_dtype(torch.float64)`
- **判定指標**: 形態の良し悪しは決定論 eval 単発で判定しない。学習曲線の順位（running best）で見る。所要エポックは候補間の隔たり次第で、明確に異なる候補なら 30ep、拮抗しうるなら 120ep（`python3 scripts/rank_settle.py` で再測定できる）
- **md の信頼度**: 一次データ（log/overrides）> 実験系譜（監査済み）> 進捗.md の古い節・現在地ロードマップ（07-15付けで停止、tripo関連は本ファイルの方が新しい）
- **ユーザーの文体好み**: md は平易な日本語（ゼロスタート・頭打ち等）+ 用語は実験系譜.md 冒頭の辞典に集約。修論ドラフト本文のみ学術文体（だ・である）。コミットは内容別に分ける
- **ファイル参照の形式**: マークダウンリンクはこの環境ではクリックできない。ファイルパスを伝えるときはコードブロック内の生パス（相対パス）で書く
