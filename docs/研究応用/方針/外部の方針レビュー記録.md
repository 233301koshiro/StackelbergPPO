# 外部の方針レビューの記録

研究の方針と、それに対する検証や行動が伴っているかを、リポジトリを見られない別の会社のモデル（いまは web の Gemini）に定期的に見せる。この md はその決まりと履歴を持つ（2026-11-28、ユーザー「定期的に gemini に研究の方針とそれに対する検証や行動が伴っているかを依頼するための仕組みを作ろう」）。

## なぜやるか

方針も行動も Claude が書き、Claude が実行している。自分の決めた方針と自分の行動のずれは、同じ文脈を持つ者には見えにくい。

初回（11-28）の実例: 本命の 8 本（系譜 9-366・読み 65）の予測は形を固定した計算だった。一方、run はリンク長も動かす設定で、Claude もユーザーも投入直前まで気づかなかった。方針の説明だけを読んだ Gemini が「計算と学習で設計変数が一致しているか、この文書では判断できない」と書き、確かめたら一致していなかった（系譜 9-369）。
効いたのは批判の表ではなく、**「判断できない事項」の欄**だった。依頼文はこの欄を重く求める。

## いつ回すか

| きっかけ | 理由 |
|---|---|
| **週に 1 回**（前回から 7 日を超えたら） | `python3 scripts/check_docs_inventory.py`（週 1 の棚卸し）の冒頭に経過日数が出る |
| 1 日以上かかる学習の束を、新しい方針の下で投入する前 | 11-28 の穴はこの時点で見つけると安い（投入後なら 1.5 日を捨てる） |
| 指導教員の指摘で方針が大きく変わったとき | 指摘の芯が方針で本当に塞がるかを見てもらう |

## 手順

1. Claude が `/review-out` で依頼の一式を `out/review_<MMDD>/` に作る（方針の説明・方針と行動の対応表・依頼文）。下の表に行を足す
2. ユーザーが依頼文を貼り、2 つの md を添付して Gemini に渡す。Claude の見立ては渡さない
3. 回答をこの会話に貼る → `/review-in` で一次記録に当てて仕分ける。回答の全文は同じフォルダの `回答_<モデル>.md` に置く。下の表の行を埋める

依頼文の雛形は [セカンドオピニオン.md の E](../../リポジトリ説明/05_レビューと監査/セカンドオピニオン.md)。
