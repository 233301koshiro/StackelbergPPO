# 外部エージェントへ渡すプロンプト（2026-09-13 作成、期限 09-19）

> **用途**: 別モデルのクレジットを使って、このリポジトリの難易度の高い作業を任せる。
> ⚠️ **このリポジトリは規律が厳しい**（CLAUDE.md）。**規律を知らないエージェントは
> 必ず「動くコード」ではなく「間違った結論」を残す。** プロンプトに規律を埋め込んである。
>
> ⚠️ **コピーしてそのまま貼る。** 途中を削ると、削った規律の事故がそのまま起きる。

## 共通の前置き（**どのタスクでも先頭に付ける**）

```
あなたは修士研究のリポジトリ /userdir/StackelbergPPO で作業します。
このリポジトリには厳しい作業規律があり、破ると「動くコード」ではなく
「間違った結論」が残ります。まず次を必ず読んでください。

1. CLAUDE.md を全部読む。特に §5-2（局所解を防ぐ作業規律）と §4-2（記録のトリガー）
2. docs/研究応用/引き継ぎ_再起動後.md（現在地・稼働中の実験・落とし穴）
3. docs/研究応用/執筆/知見総括表.md の E 節（反証・取り下げた主張＝言ってはいけない読み）
4. git log --oneline -20 で他セッションの差分を確認する

絶対に守ること:
- 変更前に4点を出す（根本原因 / 研究の問いとの整合 / 波及範囲 / 代替案）。
  出さずに手を動かさない。CLAUDE.md §5-2 ②
- 変数は一度に1つしか変えない
- 結果を見る前に「どの結果だったらどう読むか」を書く（事前登録）。CLAUDE.md §5-2 ⑤-2
- 学習結果を論じる前に必ず再生して軌跡を図にして見る。ログの値だけで判断しない。§5-2 ⑤-3
- 1エピソードで判定しない。5話実行して頭2話を捨てる
- スコアを物理が違う run 間で比べない
- pkill -f を使わない（自分のシェルごと落ちる。Bug 19）。必ず PID を特定して kill
- single_run/ と data/test/ は消さない（一次証拠。権限で禁止してある）
- 学習は同時2本まで（4本だと逆に遅くなる）
- 作業後に必ず回す:
  python3 scripts/check_docs_consistency.py
  python3 scripts/check_stale_claims.py
  python3 scripts/check_docs_inventory.py
- 得た知見は docs/研究応用/台帳/実験系譜.md に新しい段として書く。
  ⚠️ 数値の原本は single_run/*/log/log_train.txt であり、台帳はそこからの転記である

⚠️ このリポジトリは過去に「誰も選んでいない既定値が結果を支配する」事故を3回
起こしています（armature / 接触の反発係数 / 報酬の飽和）。
新しく何かを測るときは python3 scripts/audit_implicit_physics.py を先に回し、
「書かれていない値」を確認してください。
```

## タスク A（**最優先・推奨**）: 段1b「トルクに質量を払わせる」の実装と検証

**なぜ難しいか**: MuJoCo に「関節の質量」という概念が無い。body の慣性として入れるか
密な geom を置くかを自分で決める必要があり、**どちらが既存の設計変数の処理と衝突しないかは
未確認**である。さらにトルク密度に崖があり、下回るとどの減速比でも腕が自重を支えられない。

```
【タスク】
docs/研究応用/台帳/実験系譜.md の「9-83」に、段1b「トルクに質量を払わせる」の設計が
書いてあります。⚠️ まずその段を全部読んでください。設計は済んでいます。実装と検証が仕事です。

やること:
1. 9-83 の設計どおり、関節へ `gear / トルク密度` の質量を加える実装を入れる。
   実装箇所は khrylib/robot/xml_robot.py の Actuator.sync_node() で、段1a（反射慣性）が
   既に同じ場所に入っている。段1a を壊さないこと。
   ⚠️ MuJoCo に「関節の質量」は無いので body へ加える必要がある。<inertial> を明示する案と
   密な球 geom を置く案があり、どちらが xml_robot.py の他の処理（設計変数の読み書き、
   bone_offset の同期、geom の型判定）と衝突しないかは未確認である。実装前に調べること。

2. ⚠️ 既定では無効にすること。cfg に該当キーが無ければ何もしない形にする。
   既存110本の run と物理を変えてはいけない。段1a と同じ方式（param_specs から読む）に揃える。
   実装後、既存 cfg 全部で無効であることを機械で確認する（段1a の確認方法が 9-81 にある）。

3. 投入前に3点を測る。9-83 に手順が書いてある。
   ① トルク密度の感度（余裕 = 密度 / 18.7 で、18.7 を割るとどの減速比でも自重を支えられない）
   ② 動力学（質量が350倍になった後に先端加速度がどれだけ残るか）
   ③ 3 epoch のスモークで NaN と発散を見る

4. 段1a と段1b の「両方」を入れた条件で 200 epoch 回す。
   ⚠️ 9-83 が「段1b 単独では減速比を動かさない。1a と逆向きに効くので両方で内点解になる」と
   計算で示している。だから回すのは「両方」の1本でよい。対照は既存の e2e_a1v_pusher と
   e2e_a1v_actuator_pusher（どちらも完走済み）。

5. 完走したら scripts/compare_morphology.py に COMPARE_EPOCH を渡して
   同じ epoch どうしで収束した減速比を比べる。
   ⚠️ 見るのは減速比の位置であってスコアではない。物理が違うのでスコアは比較できない。

6. 結果を実験系譜.md に新しい段として書く。⚠️ 事前に決めた読み（9-83 の末尾にある）を
   守り、結果を見てから読み方を変えないこと。

【停止条件】
・実装中に「既存の処理と衝突して段1a が壊れる」と分かったら、無理に通さず報告する
・スモークで発散したら、トルク密度を上げるか floor を上げて再測定する
・3回直して症状が消えなければ止めて報告する（CLAUDE.md §5-2 ④ 3ストライク）
```

## タスク B（**GPU を使わない。A と並行できる**）: 第1層の到達判定を非平面で厳密にする

**なぜ難しいか**: 現状は零姿勢の平面チェーンを格子で走査し、順運動学のリプシッツ定数から
「棄却の側だけが確実」になるよう作ってある。**縦型（根元ヨー＋以降ピッチ）の実際の運動学と
可動域で同じ保証を作るのは、幾何として難しい。**

```
【タスク】
scripts/diagnose_morphology.py の第1層（到達判定）を読んでください。
docs/研究応用/台帳/実験系譜.md の「9-78」と「9-72」に、いまの実装の設計と限界が
書いてあります。⚠️ まず両方読んでください。

現状: planar_chain_reach() が、零姿勢で上を向く平面チェーンを関節可動域の格子で走査し、
目標への最小残距離を出す。順運動学のリプシッツ定数（関節を δ 動かすと先端は高々 R·δ 動く）
から格子の隙間で届きうる余地を見積もり、最小残距離がその余地を超えたときだけ棄却する。
つまり「棄却の側だけが確実」という非対称な保証になっている。

やること:
1. 縦型モード（根元ヨー＋以降ピッチ、bone は +Z）の実際の運動学で、同じ
   「棄却の側だけ確実」な保証を作れるか検討する。根元のヨーが可動平面自体を回すので、
   平面チェーンの仮定が使えない。
2. 作れるなら実装する。作れないなら、なぜ作れないかを幾何として説明する。
   ⚠️ どちらでも成果である。「できない」と分かることも結論になる。
3. 実装した場合、既存の14形態×2タスクで判定が1件も変わらないことを確認する。
   ⚠️ 変わったら、それは実装の誤りか、いまの判定が間違っていたかのどちらかである。
   どちらかを特定してから進めること（9-78 では実際にこれが起きた）。
4. scripts/test_layer1_reach_filter.py に検査を足す。

【やってはいけないこと】
・閾値を足して「弾ける件数」で良し悪しを判定しない。CLAUDE.md §5-2 ⑤-4 に理由がある
・較正していない閾値を導入しない。9-69 で「閾値が検出器として成立しない」事例がある
```

## タスク C（余力があれば）: Target-Pusher の報酬の飽和を解消する

**なぜ難しいか**: 報酬の天井を動かすと既存の TP の run と比較できなくなる。
**天井を上げつつ、何と比較可能なままにするかの設計判断**が要る。

```
【タスク】
docs/研究応用/台帳/実験系譜.md の「9-88」を読んでください。
Target-Pusher の報酬が理論上限 0.5 に対して実測 0.450〜0.490（上限の90〜98%）で
飽和しており、成功した形態どうしを区別できないことが分かっています。

やること:
1. 飽和を解消する設計を出す。⚠️ 報酬項を足すのではなく、既存の仕組みの中で解く道を
   先に探すこと（9-65 で「報酬の複雑化」を却下した経緯がある）。
   目標距離を延ばす案がまず考えられるが、それが何を壊すかを調べてから決めること。
2. 新しい条件として足す。既存の TP の run の設定は変えない。
3. 天井を計算し、実測がどこに来るかを見積もってから投入する。
   ⚠️ CLAUDE.md §5-2 に「指標を順位づけに使う前に天井と床を計算する」とある。
4. 形態を2つ以上比べて、順位が付くか（帯が重なるか）を見る。
```

## ⚠️ 渡すときの注意

| | |
|---|---|
