## 1. ⭐⭐ RobotAssembler のパーツで作れないか — **本命**

> ⭐ 豊橋技術科学大学 垣内洋平 准教授（IRSL）らが開発。アクチュエータモジュールを組み合わせて
> ロボットモデルを直感的に設計・構成できるシステム。
> ⭐ **先生の狙い: 軸トルクの範囲の制約・軸の向き・sim-to-real gap の 3 つに同時に取り組める。**

### ⭐⭐ 事実 — **既にこの環境に入っている**

| | |
|---|---|
| ⭐ 同梱 | `/choreonoid_ws/src/choreonoid/ext/robot_assembler_plugin/` |
| ⭐ ビルド済み | `libCnoidRobotAssemblerPlugin.so` |
| ⭐ Python バインディング | `pybind11/PyRobotAssembler*.cpp`（4 ファイル） |
| ⭐⭐ **出力形式** | **`RobotAssemblerBody` が `choreonoid.body` を出力する** — ⭐ **本 repo が必要とする形式そのもの** |

### ⭐⭐⭐ パーツ定義のスキーマに先生の 3 点がそのまま載っている

```yaml
actuators:
  - actuator-type: fixed/linear/rotational/(sphere)
    axis: x,y,z,-x,-y,-z, or [0,0,1]   # ⭐ ② 軸の向き
    limit:   [-270, 270]                # 可動域（KXR 設定に実値あり）
    vlimit:  [,]                        # 速度制限
    tqlimit: [,]                        # ⭐ ① 軸トルクの範囲
mass-param:
    mass: 26.4                          # ⭐ ③ 実部材の質量（g。KRS-3301 サーボ）
    center-of-mass / inertia-tensor
```

### ⭐⭐ 研究上の意味 — **4.6 とは質的に違う**

| | 現行 4.6（軸5） | ⭐⭐ RobotAssembler |
|---|---|---|
| 設計空間 | **連続**。実部材から**範囲**を導出 | ⭐ **離散**（パーツの組み合わせ） |
| 出てきた解 | ⛔ **実在パーツで作れる保証が無い** | ⭐⭐ **定義上、必ず作れる** |
| 助教の指摘との対応 | ⭐ **指摘10 に答える** | ⭐⭐⭐ **指摘9 に答える** |

⭐⭐⭐ **「作れる設計しか探索しない」。これが sim-to-real gap の本質的な解決にあたる。**

### ⛔ 重い点 3 つ

| ⛔ | 中身 |
|---|---|
| ⛔⛔ **設計空間が離散になる** | Stackelberg PPO は**連続な設計パラメータを勾配で更新する**手法。⛔ **組み合わせ最適化へ定式化し直すことになり、原論文の枠組みを出る** |
| ⛔ **`tqlimit` に実値が無い** | スキーマはあるが KXR 設定では `[0,0]`（自由関節）のみ。⚠️ **データシートから入れる作業が要る** |
| ⚠️ **既存 171 run と比較不能** | 設計空間が変わるため |

### ⚠️ スケールの不一致 — **確認が要る**

| | 基準 | スケール |
|---|---|---|
| 現行 4.6 | **UR5e**（産業用協働ロボット） | 大 |
| ⭐ RobotAssembler の KXR | **近藤科学のホビーサーボ**（26.4 g） | ⛔ **2 桁小さい** |

⚠️ **どちらを「実機」とするかで設計空間が全く変わる。**⭐ **先生の想定を確認すること。**

## 4. ⚠️ 事前学習は要らないのか — **前提に誤解がある。ただし懸念の核は正しい**

> ⭐ 先生の問い: **ネットワークが見込み達成度を出すなら「このロボットならこれくらいできる」ということだから
> 事前学習が要るのでは？ 原論文がそれをしているなら自分はファインチューニングしなくていいのか？**

### ⛔ 誤解の部分 — **達成度を予測するネットワークは無い**

⭐ **本研究の判定は「実際に co-design 学習を回して、収束した結果を読む」方式である。**
⭐ **原論文（Stackelberg PPO / BodyGen）も from scratch** で、事前学習済みの能力予測器は持たない。

### ⭐⭐ 設計フェーズの報酬の実体（コードで確認、2026-10-02）

```python
if self.stage == 'skeleton_transform':    reward = 0.0
elif self.stage == 'attribute_transform': reward = 0.0   # 例外は下記
```

| | 中身 |
|---|---|
| ⭐ **即時報酬** | **0**。設計行動そのものには報酬が無い |
| ⭐ **設計行動の評価** | ⭐ **同じエピソードの実行フェーズで実際に得られたリターン**が、割引を通して遡って帰属する |
| ⚠️ **例外** | `compute_reach_bonus()` — **Leader 専用の一回限りのボーナス**（リーチの円環が対象を幾何的に覆う形態に加点）。⭐ **幾何だけで決まるので学習に依存しない** |

### ⭐⭐⭐ 懸念の核は正しい — **ただし「報酬」ではなく「価値関数」に当たる**

⭐ **報酬そのものは実測であり、予測ネットワークの出力ではない。**
⛔⛔ **だが設計行動の優劣を決める advantage は、価値関数 `V(s)` の推定に依存する。そして `V` は学習で獲得される。**
⛔⛔ **したがって学習の初期では、設計フェーズの「見込み達成度」は意味を持たない。**

### ⭐⭐ そしてこれは既に測ってある — **4.5.3（R4）**

> **確定エポックは 2 から 116 まで 50 倍以上開いており、単一の絶対値では表せない。
> 支配するのは候補間の隔たり。**

⭐⭐ **「見込みが意味を持つまでに何エポック要るか」を較正したのが R4 である。**
⚠️ **ただし現状 4.5.3 は「順位が確定するまでのエポック数」としか書いておらず、
「見込み達成度が学習に依存するから較正が要る」という因果の説明になっていない。**
⭐ **そこを繋げて書くと R4 の存在理由が強くなる。**（⏳ **執筆の TODO**）

### ⭐ ファインチューニングに相当するもの — **warm-start は実装済み**

| | |
|---|---|
| 中身 | ⭐ 学習済みの制御方策・形態ネットワークを**初期値として転用**する |
| 効果 | ⭐ **判定に要する学習量を減らす**（4.5.3・付録D.3） |
| ⭐ **つまり** | ⭐⭐ **これがファインチューニングに当たる。既にある** |
