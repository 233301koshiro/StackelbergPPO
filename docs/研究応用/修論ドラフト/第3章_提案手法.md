## 3.5 システム全体像

提案システムは、手描きスケッチを入力とし、その形態の対象タスクへの適性判定と、不適合であった場合の修正方向を出力する。処理は次の 7 工程をこの順に通過する一方向のデータフローである（図 3.1）。

**自動化の範囲について先に述べる。** M3 以降（関節検出からモデル生成・学習起動まで）は単一のシェルスクリプトで自動化している。**M1（画像整形）と M2（三次元形状生成）は外部の生成 AI サービスに依存し**、本研究ではその API 経路も実装した（3.13 節）。⚠️ **ただし第4章 4.5 節が報告する end-to-end 実走 5 件は、API 実装前に対話的インタフェースを介して実施した。** したがって本章で「人手を介さない」と述べる範囲は、**M3 以降の決定論的処理と M6 の学習**であり、生成物の取得工程は含まない。

**図 3.1**: 提案システムの全体構成

```
手描きスケッチ
  → [M1] 画像整形（関節マーカー規約の適用）        … 生成 AI（プロンプト固定）
  → [M2] 三次元形状生成（image-to-3D）             … 既存技術（Tripo3D）
  → [M3] 関節検出とリンク分割                      … 色検出 + 幾何処理（決定的）
  → [M4] 形態パラメータ抽出                        … 関節間距離と断面（決定的）
  → [M5] シミュレーションモデル生成                … テンプレート変換（決定的）
  → [M7 第1層] 幾何による事前判定                  … 不適合なら拡大倍率を返す（学習前）
  → [M6] 形態-制御 co-design による評価・補正      … Stackelberg PPO
  → [M7 第2・3層] 収束形態と行動の診断             … 報告のみ
  → 判定（タスク適性スコア・補正後形態・修正指示）
```

設計思想は 3 点である。第一に、可動構造の抽出に学習ベースの推定を用いず、上流（M1）での入力規約と下流（M3）での決定論的な色検出に置き換える。生成モデルの出力の不確実性をパイプライン内部で補償するのではなく、入力を拘束することで構造推定の不良設定問題を回避する。第二に、M3〜M5 を乱数や学習を含まない決定論的処理とし、失敗時の原因特定と再現性を担保する。第三に、M5 が既存の co-design フレームワークと互換な MuJoCo 互換 XML を出力することで、学習系の内部コードを改変せずに接続する。

## 3.6 M1: 画像整形と関節マーカー規約

入力スケッチは、画像生成 AI（Gemini）によって後段の三次元化と色検出に適した「機械設計図スタイル」の画像へ変換される。この際、本システムの中核である**関節マーカー規約**を固定プロンプトとして課す。規約は生成モデルに構造の推定を委ねるのではなく、**構造の境界の宣言を強制する**。要点は次の 3 つである。

1. **すべての関節接続部に純マゼンタ（#FF00FF）の球を 1 個ずつ描く**。マゼンタは自然画像・工業製品に稀な色相であり、色検出の分離性を最大化する
2. **各リンクを彩度の高い単色で塗り分け、グラデーションとマゼンタの使用を禁止する**
3. **関節の位置を場所として列挙し（「台座と上腕の間」等）、描画後に球の個数を自己検査させる**。列挙を欠くと先端側の関節が機械要素として描き分けられ、マーカーが欠落する（3 関節の指示に対し 2 個）

これにより M3 の関節検出は、精度保証のない推定問題から閾値つきの色マッチングという決定的問題に変わる。プロンプトの全文は付録A に示す（ゼロから生成する版 A.1 と、手描きスケッチを整形する版 A.2。4.5 節の end-to-end 実走 5 件はすべて A.2 を用いた）。

### 3.6.1 プロンプト規約の遵守における非決定性

本工程は API 経由で実行し（モデル `gemini-3-pro-image`、サンプリング温度 0）、リンクは「両端が平らな円柱」として指示する（丸い端は関節球と紛らわしく、マーカーが省略されるため）。⚠️ **温度を固定しても規約は確定的には満たされない。**マーカーの個数は初回で得られるが、向き・寸法線等の禁止・比の保存は個数ほど安定しない（5.3 節 (B)）。腕が傾いて出力されると関節が近い高さに並び、Z 座標を境界とする分割が通らなくなる。このため M1 の出力は人手で確認してから次段へ渡す。

## 3.7 M2: 三次元形状生成

整形済み画像は image-to-3D サービス（Tripo3D）により三次元メッシュ（GLB 形式、Y-up 座標系）へ変換される。API 経由で seed を固定して呼び出す（3.13 節）。入力画像の純マゼンタ (255, 0, 255) は生成過程で概ね (211, 75, 169) へ暗色化するが、リンク本体色とは分離した独立クラスタとして保存されるため、検出目標色を自動で較正することで検出は成立する（3.8 節）。

### 3.7.1 スケールの決まり方

**生成サービスは出力メッシュのバウンディングボックスの最長辺を 1.0（= 1 m）に正規化する**（手元の GLB 4 件すべてで 1.0000）。したがって絶対寸法は入力画像の画素数や添えた寸法に依らず、**絵の中の比率だけで決まる**。手描き入力 A1 では、線画上の腕の長さと絵全体の最大寸法の比が 1.01 であり、生成モデルの総リーチの実測は 1.0102 m であった。利用者が絶対寸法を数値で指定する手段は無く、必要なら生成後に一様な倍率を掛ける（リンク間の比は保たれるので形態の識別には影響しない）。

## 3.8 M3: 関節検出とリンク分割

M3 は GLB メッシュから関節位置を検出し、メッシュをリンク単位に分割する（`glb_to_links.py`）。

1. **頂点色の復元**: UV テクスチャを頂点色に焼き込む
2. **マーカー頂点の抽出**: 目標色 $c_0$ と許容幅 $\tau$ に対し、各チャネルで $|c_i^{(k)} - c_0^{(k)}| \le \tau$ を満たす頂点を抜き出す。$c_0$ と $\tau$ は、マゼンタの色相域（285〜345°）にある頂点クラスタの中央値と広がりから自動で較正する。該当クラスタが無ければ検出失敗として停止する
3. **関節位置**: マーカー頂点を**三次元で**連結成分に分け、各成分の重心を関節とする。全マーカー頂点の 2 % 未満の成分は色滲みのノイズとして捨てる。連結の半径（外接寸法に対する相対量 0.02）と 2 % はいずれも相対量なのでスケールに依らない（予備実験に基づく経験値）
4. **リンク分割**: 関節の Z 座標を境界として、各ポリゴンを重心の Z で区分する。境界の間にポリゴンが無ければ関節位置の異常として停止する（フェイルファスト）
5. 各分割片をリンクのローカル座標へ平行移動し、STL として出力する。エンドエフェクタの向きが意図と異なる場合（平たい面が押す向きを向く等）は、指定リンクを骨の軸まわりに回す補正を手動で与えられる

## 3.9 M4: 形態パラメータ抽出

分割された各リンクから、co-design の設計変数の初期値を求める（`mesh_to_params.py`）。

- **リンク長** $L$: **関節と関節の距離**（M3 が保持する関節座標から求める。先端リンクは最後の関節から最も遠い点まで）
- **カプセル半径** $r$: **骨の軸に垂直な断面**の 2 方向の幅の平均の半分

**いずれも OBB（有向外接直方体）を用いない。**OBB の最長辺は分割片に含まれるマーカー球の半分を拾って系統的に長く出る。OBB の短辺から半径を求める計算は最長辺が骨の軸と一致することを前提とするが、先端が太い形状ではこの前提が崩れる。骨の軸は M3 の関節座標として既知なので、それを直接用いる。

抽出の妥当性は、**カプセルが元のメッシュを覆えているか**で評価した（「正しい半径」は柄とも先端とも解釈できるが、被覆は一意に定まる）。手描き入力 5 例・20 リンクで、カプセル外に出る頂点の割合は平均 21.4 % であり、OBB の短辺から求めた場合の 29.7 % より小さく、悪化するリンクは無かった。残る被覆誤差の主因は、傾いた腕を水平な面で分割することにある。分割面がリンク軸に対して斜めになるため、先端の分割片に関節より後ろ側の部分が入り込み、半径も小さめに出る。B1 の手先は頂点の 70.9 % が外に出るが、はみ出し量の中央値は 5〜10 mm である（鉛直に立った A1 の手先は 8.9 %）。限界として 5.3 節に記す。

関節可動域とギア比の初期値はスケッチの幾何から一意に定まらないため、既定値（ギア比 100、可動域 ±90°）を用いる。設計空間の探索範囲（bone_offset は初期値相対 ±0.5 m、ギア比は [20, 400]）は co-design 側の設定で与える。⚠️ この範囲は中心的な実験の設定であり実在の部材から導いたものではないため、4.6 節では実在材料と実在アクチュエータ（UR5e 級）から導き直した範囲でも検証する。

## 3.10 M5: シミュレーションモデル生成

topology.json は MuJoCo 互換 XML へ変換される（`topology_to_xml.py`）。各リンクをカプセルで近似し、子リンクの `<body>` を親の中に入れ子にして、その位置を親の骨の長さに置く（＝親の先端に取り付ける）。関節（回転軸・可動域）とアクチュエータ（ギア比）を付与する。学習側では読み込み時に Choreonoid のモデル形式（.body）へ変換される。形態を可変長のグラフとして扱う Transformer 方策のため、3 関節メッシュ由来のモデルは**学習系のコードを変えずに**受理された。⚠️ ただし前段（M1〜M3）を 3 関節以外で実行した事例は無く、**本論文が扱った形態はすべて 3 関節である**（5.4 節）。

関節軸は関節ごとに座標軸 x・y・z のいずれかを割り当てる。既定として、全関節をヨー軸としボーンを X 軸方向へ並べる**平面モード**と、根本をヨー軸・以降をピッチ軸としボーンを Z 軸方向へ積む**縦型モード**を用意する。**本論文が報告する実験の大半は平面モードによる。**付録D の非平面 4 関節アーム（`tripo_arm_v3`）は、縦型モードの追加前に生成メッシュから人手で書き起こしたモデルであり、パイプラインの出力ではない。⚠️ **軸の割り当ては入力形状から推定するものではなく、利用者が与える。**形状からの軸推定は今後の課題とする（5.4 節）。

## 3.11 M6: co-design による評価・補正と判定

生成されたモデルを初期形態として Stackelberg PPO による形態-制御 co-design を実行する。エピソードは骨格変換（本システムではスキップ: トポロジーはスケッチが決める）、属性変換（Leader が bone_offset・太さ・ギア比を編集）、実行（Follower が制御してタスク報酬を得る）の 3 フェーズから成り、Leader の目的関数には Follower の実行リターンが継承される。したがって学習の進行に伴い、(i) 実行リターンの推移が**その形態系列のタスク達成度の評価**を、(ii) Leader による設計パラメータの更新が**スケッチ由来の初期値の補正**を与える。判定は学習曲線の順位で読む。所要学習量は 4.5.3 節で較正する。判定を速めるため、同一タスクの学習済みモデルから重みを転用して開始することもできる（形態ネットワークを含む転用が有効。付録D）。

## 3.12 M7: 形態診断

### 3.12.1 判定から診断へ

M6 が返すのは「このスケッチはこのタスクに向くか」という順位ないしスコアである。しかし想定する利用者はロボット設計の専門知識を持たないため、「向かない」とだけ告げられても次に何をすべきか判断できない。**不適合の原因と修正の方向を言語化して返す**必要がある。M7 は追加の学習を要さず、M6 が生成する既存の成果物（初期 XML・収束形態のチェックポイント・行動トレース）のみを入力とする。診断に生成 AI は用いず、閾値との比較で選んだ定型文に実測値を差し込んで返す。

### 3.12.2 三層構造

M7 は計算コストの異なる三つの層から成り、上の層ほど安価かつ確定的である。

**第1層（幾何診断・学習不要）**: 初期 XML のみを解析し、最大リーチと関節可動域のもとで到達しうる範囲を、目標位置・対象物位置と比べる。所要は数秒以内で、シミュレータの起動も学習も不要である。検出する事象は (i) 目標が最大リーチの外にあり到達不能、(ii) 静止姿勢で先端が対象物に貫入する、(iii) 関節軸の向きがタスクの想定と一致しない、の三種である。(i) では**判定を覆すのに必要な最小の拡大倍率**を数値で返す（例: 「腕全体を 1.99 倍に伸ばしてください」）。倍率は切り上げる（四捨五入では提示値が必要量を下回り、従っても判定が覆らない場合がある）。最小の変更のみを返すことは、反実仮想説明・実行可能な救済の要件と一致する（2.4 節）。

最大リーチの算出には二つの前提がある。リンク長の総和が到達距離に等しいのは各関節が直前のリンクの先端にある場合に限られるため、関節位置の連鎖から求めた到達距離と食い違う XML は不整合として棄却する。また総和がそのまま水平の到達半径になるのは平面アームに限られるため、非平面アームでは旋回軸に平行なリンクを除いた水平限界で判定する。関節可動域による到達判定は可動域を格子状に走査して行い、格子の粗さに由来する余地を順運動学のリプシッツ定数で見積もって、**「届かない」側だけが確実になる**ように構成する。リンク長が最適化対象に含まれる設定では最大リーチが学習中に伸びうるため、第1層は「到達できない」という否定的判定のみを行う。

**第2層（収束形態の診断）**: co-design が収束させた設計パラメータを読み、探索範囲の境界への張り付きを検出する。ギア比が上限に張り付いていれば出力不足、下限に張り付いていれば省エネ方向への収束を意味する。ただし後者の解釈はタスクに依存する。到達タスクでは弱く細い設計が確率的方策のもとで静止精度を保つ正常な最適解でもあり、到達可能な形態と不可能な形態が同一の署名を示した（4.3.3.1 節）。したがってこの署名を到達タスクでは警告に留め、強い出力が有利なはずの押しタスクでのみ不適合の兆候として報告する。

**第3層（行動の診断）**: 収束した方策を決定論的に 1 エピソード実行し、その軌跡から戦略を分類する（押しタスクでは「一撃で吹き飛ばす」「穏やかに押す」「触れられていない」、到達タスクでは「目標で静止する」「ずれて止まる」「到達できない」）。あわせて各関節が可動域のうち実際に使った割合を報告し、10 % を下回る関節については固定すれば質量と制御の自由度を減らせる可能性を指摘する。第1層の「腕を N 倍に伸ばせ」とは逆の、**設計を減らす方向の指摘**である。利用者の意図と異なる戦略に収束している場合（例: 狙った位置に止めたいのに吹き飛ばしている）は、形態ではなく**タスク選択の誤り**として代替タスクを提示する。

### 3.12.3 診断の妥当性検証の位置づけ

三層の診断が実測順位と一致するかは、診断の設計ではなく実験の問題である。検証の条件と結果は 4.4.1 節に示す。本節以降では、診断の設計上の性質を述べる。

### 3.12.4 第3層の閾値は判定規則ではなく候補生成器である

第3層の閾値（可動域の 10 %）は実験によって較正されていない（5.3 節 (D)）。**ただし閾値が決めるのは「固定を試す価値のある関節」であって、「固定すべき関節」ではない。**採否は、助言どおり固定した形態を学習させ、**元の形態と成績の範囲が重なるかどうか**で決める。この基準は本研究が形態の順序づけ全般に用いるものと同一である（4.3.3 節）。

**表 3.2**: 第3層の助言に対する採否の判断（いずれも 2 シード）

| 関節の使用率 | 元の形態 | 助言に従い固定した形態 | 範囲の関係 | 採否 |
|---|---|---|---|---|
| 閾値から離れている（7 % / 41 %） | [−6.30, −5.83] | **[−5.32, −3.85]** | 重ならず、固定側が良い | **採用** |
| 閾値の近傍（10 %） | [340.39, 348.56] | [224.41, 432.47] | **固定側が元の形態を包含** | **採用しない** |

閾値近傍の候補は範囲の比較によって落ちるので、閾値が不正確でも誤った助言は採用されない。⚠️ 逆に、真に有効な助言を閾値が見落とす可能性は残る。また採否の判断には学習が 2 シード分必要である（1 条件あたり約 8.5 時間）。本手法が秒で返すのは候補であって、採用の結論ではない。

### 3.12.5 診断の範囲外とした事項

第1層の「腕全体を N 倍以上に伸ばしてください」は、判定を覆すのに必要な最小の変更を利用者が操作できる変数の上で示した反実仮想説明である（2.4 節）。**第2層・第3層では同種の出力を構成できていない。**収束した設計や行動から「何が起きたか」は報告できるが、「設計をどう変えればその結果が変わるか」は学習をやり直さなければ分からない。第1層でそれが可能なのは、幾何が支配する層では必要な変更が運動学から解析的に求まるからである。また、意図から報酬関数を自動設計する機能は範囲外とした（報酬の複雑化が探索シグナルを消す事例がある、4.3.2.5 節）。

### 3.12.6 考察: なぜ三層に分ける必要があったか

**層の分け方はコストではなく確定性で決まる。**第1層が用いるのはリンク長と目標位置という運動学的な量のみであり、「最大リーチ 0.403 m の腕は 0.800 m 先の目標に届かない」は学習の結果にも乱数シードにも依らない。一方、第2層・第3層が用いるのは学習の帰結であり、シードや打ち切りに依存する。ここから設計原則が導かれる。**確定的な層は断定してよく、確率的な層は断定してはならない。**実装では第1層だけが「この形ではタスクを達成できません」という総合判定を出し、第2・3層は観察の報告に留める。

**収束形態は「達成」と「断念」を区別しない。**目標に届かない短腕ではギア比と太さがともに探索下限に収束したが、目標にサブミリ精度で到達した中間の腕でも同じ署名が出た。到達タスクでは、届かない形態は報酬が改善しないので最も弱い設計に落ち、届く形態も到達後の静止のために弱い設計を選ぶからである。co-design が返す収束形態は「報酬を最大化した結果」でしかなく、その報酬の高低を含まない。形態パラメータだけから成否は判断できず、報酬の水準・幾何・行動のいずれかと組み合わせる必要がある。これが三層構成を採る直接の理由である。

**幾何が学習を代替できる範囲は、タスクの要求が運動学的な量に還元できる場合に限られる。**第1層は到達タスクの順位（中間 ＞ 長腕 ＞ 短腕）を学習なしで予測したが、押しタスクの中間と長腕の優劣は予測できない。押しの要求は先端速度であり、アクチュエータ出力と制御の習熟が絡むためである。したがって第1層は不適合の検出に留め、適合と判定した形態には学習で性能を確かめるよう明示的に促す。


## 3.13 実装環境

再現性のため、実装に用いた計算環境を記す。ホスト OS は Ubuntu 24.04.4 LTS、Python 3.12.3 上に構築する。M3・M4（メッシュ処理・パラメータ抽出）には trimesh 4.12.2 を用い、GLB の読み込み・頂点色復元・OBB 計算を行う。M6（co-design 学習）の方策・価値ネットワークは PyTorch 2.7.0（CUDA 12.8 ビルド）で実装し、数値計算に NumPy 2.4.6 を用いる。物理シミュレーションには Choreonoid 2.3（AIST シミュレータ）を用い、M5 で生成した MuJoCo 互換 XML を内部形式へ変換して実行する。設定管理には Hydra を用いる。

外部生成 AI サービスのうち **M1 の Gemini は API 経由で実行する**（モデル `gemini-3-pro-image`、温度 0）。**M2 の Tripo3D も API 経由で実行する**（`scripts/tripo_api.py`、seed 固定）。M1 で使用した固定プロンプトの全文は付録A（A.1 および A.2）に示す。手描きスケッチを入力とする end-to-end 実走（4.5 節）では、M1 の画像整形に Gemini 3.1 Pro の拡張機能を用いた。ただし本論文が報告する `tripo_arm_v2c` 系のモデル生成は 2026 年 7 月に実施しており、その際に用いた生成モデルのバージョンは記録していない。外部サービスはバージョンが更新されうるため、当該モデルの生成過程を厳密に再現することはできない。これは実装上の限界であり、以降の生成についてはサービス名とバージョンを記録する運用としている。
