## 3.1 システム全体像

提案システムは、手描きスケッチを入力とし、その形態の対象タスクへの適性判定を出力する。処理は次の6モジュールをこの順に通過する一方向のデータフローであり、モジュール間の受け渡しに人手を要しない。

```
手描きスケッチ
  → [M1] 画像整形（関節マーカー規約の適用）        … 生成 AI（プロンプト固定）
  → [M2] 三次元形状生成（image-to-3D）             … 既存技術（Tripo3D）
  → [M3] 関節検出とリンク分割                      … 色検出 + 幾何処理（決定的）
  → [M4] 形態パラメータ抽出                        … OBB 近似（決定的）
  → [M5] シミュレーションモデル生成                … テンプレート変換（決定的）
  → [M6] 形態-制御 co-design による評価・補正      … Stackelberg PPO
  → 判定（タスク適性スコアと補正後形態）
```

設計方針は3点である。第一に、可動構造の獲得を学習ベースの推定に委ねず、**上流（M1）で規約を課し、下流（M3）を決定的な検出に置き換える**。生成 AI の出力の不確かさをパイプライン内部で吸収するのではなく、生成 AI への入力を統制することで問題自体を消す。第二に、M3〜M5 を**乱数や学習を含まない決定的処理**とし、失敗時の原因特定と再現を容易にする。第三に、M6 は既存の co-design フレームワークをモデル生成側が「話せる」形式（設計パラメータ付きの MuJoCo 互換 XML）に合わせることで、co-design 側のコード変更なしに接続する。

以下、データの流れに沿って各モジュールを述べる。

## 3.2 M1: 画像整形と関節マーカー規約

入力スケッチはまず画像生成 AI（Gemini）により、後段の三次元化・検出に適した「機械設計図スタイル」の画像へ整形される。このとき本システムの中核的な工夫である**関節マーカー規約**を、固定プロンプトとして課す。規約の要点は次の3つである。

1. **すべての関節接続部に純マゼンタ（#FF00FF）の球を1個ずつ描くこと**。マゼンタは自然画像・工業製品に稀な色相であり、後段の色検出の分離性を最大化する
2. **各リンクを彩度の高い単色（赤・青・緑等）で塗り分け、グラデーションを禁止すること**。またマゼンタをリンク本体色に使うことを禁止する
3. **関節の位置を場所として列挙し（「台座と上腕の間」等）、描画後にマゼンタ球の個数を自己検査させること**。位置の列挙を欠くと、生成 AI は先端側の関節をヒンジ金具等の機械要素として描き分けてしまい、マーカーが欠落することが実測で確認されている

この規約は「生成 AI に構造推定をさせる」のではなく「生成 AI に構造の**宣言**をさせる」設計であり、M3 の関節検出問題を、精度保証のない推定問題から閾値つき色マッチングという決定的問題に変換する。実際に使用したプロンプト全文（3関節アームの例）を次に示す。

```text
以下の仕様に従い、3関節ロボットアームを機械設計図スタイルで描いてください。

【形状・姿勢 — 最重要】
- 固定台座から垂直に伸びるシリアルチェーンアーム（根元が下・先端が上）
- リンク1（上腕）: 台座から伸びる中太の円柱カプセル
- リンク2（前腕）: 上腕より細く1.5倍長い円柱カプセル
- リンク3（先端）: 平たいパドル・へら形状

【関節マーカー — 最重要・省略厳禁】
すべての接続部に、純マゼンタ (#FF00FF) の球を1個ずつ描くこと。具体的には以下の3箇所:
1. 台座と上腕（赤）の間
2. 上腕（赤）と前腕（青）の間
3. 前腕（青）と先端パドル（緑）の間 ← ここも省略しないこと
- 3箇所すべて同じ様式（リンクより太いマゼンタの球）で統一すること。
  先端側の関節だけを金具・ヒンジ・ブラケット等の機械要素で描くのは禁止
- 描き終えたら、マゼンタの球がちょうど3個あることを確認すること

【色分け — グラデーション禁止・各色を単色で塗ること】
- ベース台座: 濃いグレー (#333333)
- リンク1（上腕）: 鮮明な赤 (#FF2222)
- リンク2（前腕）: 鮮明な青 (#2222FF)
- リンク3（先端パドル）: 鮮明な緑 (#22CC22)
- 関節球: 純マゼンタ (#FF00FF)
  ※ マゼンタはアーム本体色（赤・青・緑・グレー）には絶対に使わないこと（自動検出用のため）

【スタイル】
- 白背景
- CADソフトウェアのレンダリング風（プラスチック質感・影あり・幾何学的）
- 斜め45度視点（3/4アングル）、ロボット全体が収まる構図
```

Gemini は Web インタフェース上で対話的に利用し、API 呼び出しによるサンプリングパラメータ（temperature 等）の指定は行っていない。関節個数の誤描画（初期プロンプトでは関節球が2個しか描かれない事例があった）に対しては、関節位置を場所として明示的に列挙し個数の自己検査を課す文言を追加することで解消した。この改訂後のプロンプトでは、検証した生成事例において規約適合画像が初回の生成で得られている。

## 3.3 M2: 三次元形状生成

整形済み画像は image-to-3D サービス（Tripo3D）により三次元メッシュ（GLB 形式、Y-up 座標系）へ変換される。本モジュールは Tripo3D の Web インタフェースを介して呼び出しており、モデルのバージョンやサンプリング設定は同サービス側の既定値に依存する。このモジュールは既存技術をそのまま用いるが、2点の実測知見が後段の設計に反映されている。第一に、**テクスチャの色変換**である。入力画像の純マゼンタ #FF00FF = (255, 0, 255) は、生成過程で概ね RGB (211, 75, 169) へ暗色化する。ただしリンク本体色（実測: 赤 (216,61,54)・青 (63,46,184)）とは明確に分離した独立クラスタとして保存されるため、検出目標色を実測値に合わせることで検出は成立する。第二に、出力メッシュのスケールは概ねメートル単位であり、スケール補正を要しなかった。

## 3.4 M3: 関節検出とリンク分割

M3 は GLB メッシュから関節位置を検出し、メッシュをリンク単位に分割する（`glb_to_links.py`）。処理は次の手順による。

**(1) 頂点色の復元。** Tripo3D の GLB は色情報を UV テクスチャとして持つため、まずテクスチャを頂点色に焼き込む（`to_color()` 変換）。この工程を欠くと頂点色が常に空となり、検出が無条件に失敗する。

**(2) マーカー頂点の抽出。** 目標色 $c_0 = (r_0, g_0, b_0)$ と許容幅 $\tau$ に対し、頂点 $i$ の色 $c_i$ が各チャネル独立に

$$|c_i^{(k)} - c_0^{(k)}| \le \tau \quad (k \in \{R, G, B\})$$

を満たすものをマーカー頂点とする。座標系を Y-up から Z-up へ変換（$(x,y,z) \mapsto (x,-z,y)$）した上で処理する。目標色 $c_0$ と許容幅 $\tau$ は自動キャリブレーションにより決定する: マゼンタの色相域（hue 285–345°）かつ十分な彩度・明度を持つ頂点クラスタを探し、その色の中央値を $c_0$、クラスタ内の色の広がり（99 パーセンタイル偏差）から $\tau$ を定める。これにより三次元化に伴う色変換（3.3 節）へ人手の再測定なしに追従する。マゼンタ域のクラスタが存在しない場合（実測: 金色マーカー版の負例）は検出失敗として明示的に停止し、関節位置の手動指定へフォールバックする。

**(3) 関節位置のクラスタリング。** マーカー頂点の Z 座標を昇順に走査し、隣接値の差が閾値（0.05 m）を超えた位置で区切る 1 次元クラスタリングを行う。各クラスタの Z 平均を関節高さとする。このとき、頂点数がマーカー頂点総数の 2% に満たないクラスタは棄却する — テクスチャの色滲みが生む少数の迷い頂点（実測: 1 頂点）が偽の関節を作ることを防ぐためである。関節の XY 位置は、当該 Z 近傍のマーカー頂点の重心として求める。実証実験では 3 関節すべてが自動検出された（Z = −0.298, 0.001, 0.298）。

**(4) リンク分割。** 検出した関節 Z を境界とし、各フェースをその重心の Z 値で区分してメッシュを分割する。境界間にフェースが存在しない場合は関節位置の異常としてエラーを返す（フェイルファスト）。分割片は各リンクのローカル座標に平行移動され、STL として出力される。最下段の分割片は固定台座として扱い、可動リンクから除外できる。

**(5) 姿勢の補正（オプション）。** エンドエフェクタの面の向きが運動方向と不整合な場合（実測例: ヘラの面法線がスイング平面と垂直で、薄い側面が押し方向を向く「チョップ」姿勢）、指定リンクをボーン軸まわりに回転させる補正を適用できる。

## 3.5 M4: 形態パラメータ抽出

分割された各リンク STL から、co-design の設計変数の初期値を抽出する（`mesh_to_params.py`）。リンクごとに OBB（Oriented Bounding Box、有向外接直方体）を計算し、

- **リンク長** $L$: OBB の最長辺の長さ。ボーンベクトル bone_offset の大きさとなる
- **カプセル半径** $r$: 残る2辺の長さの平均の半分、$r = (e_2 + e_3)/4$

を得る。OBB を用いることでメッシュの置かれた向きに依存せずに主軸長が取れる。実証実験では、マーカー球がリンク本体と分離して抽出されるため OBB が球に引きずられて太ることがなく、妥当な半径（0.033〜0.045 m）が得られた。抽出された bone_offset はタスク座標の X 軸方向へマッピングされ、設計空間の探索範囲（bone_offset は初期値相対 ±0.5 m、ギア比は [20, 400]）が付与された topology.json として出力される。一方、関節可動域とギア比の初期値はスケッチの幾何情報から一意に定まる量ではなく、現状はパイプラインの既定値を用いている。この既定値の設定根拠は本研究の対象外であり、限界として第6章で扱う。

## 3.6 M5: シミュレーションモデル生成

topology.json は MuJoCo 互換 XML へ変換される（`topology_to_xml.py`）。各リンクはカプセルとして近似され、カプセルの両端は bone_offset から計算される（始端 = 原点近傍、終端 = bone_offset）。子リンクの取り付け位置は親リンクの bone_offset 終端に一致させ、関節（回転軸・可動域）とアクチュエータ（ギア比）を付与する。生成された XML は、2関節の手書きモデル（rrbot_arm）と同一の書式であり、co-design フレームワークからは通常のロボットモデルとして扱われる。実証実験では、3 関節メッシュ由来のモデルが**コード変更ゼロ**で学習系に受理された — 形態を可変長のグラフとして扱う Transformer ベースの方策ネットワークが、関節数の変化を追加ノードとして透過的に処理するためである。

なお、生成メッシュの姿勢に忠実に構築したモデル（後述の tripo_arm_v3）では、根本関節をヨー軸（鉛直軸まわりの回転）、以降の関節をピッチ軸（水平軸まわりの回転）として割り当てている。これは rrbot_arm や上記の水平3関節版（全関節ヨー軸、単一の水平面内で腕が動く）とは異なり、腕の可動平面自体を根本のヨー回転で任意方向へ向けられる構造である。この点は本手法の一般性を示す上で重要である: パイプラインが受理するモデルの自由度構造は入力メッシュの関節姿勢がそのまま決めるため、単一平面内の腕に限らず、根本回転軸を持つ非平面的な構造も**同一のコード経路**で扱える（第6章 限界節・今後の課題で詳述）。

## 3.7 M6: co-design による評価・補正と判定

最後に、生成されたモデルを初期形態として Stackelberg PPO による形態-制御 co-design を実行する。エピソードは3フェーズ — 骨格変換（本システムではスキップ: トポロジーはスケッチが決めるため固定）、属性変換（Leader が bone_offset・ギア比を編集）、実行（Follower が制御を実行しタスク報酬を得る）— から成り、Leader の目的関数には Follower の実行リターンが継承される。したがって学習の進行に伴い、(i) 実行リターンの推移が**その形態系列のタスク達成度の評価**を与え、(ii) Leader による設計パラメータの更新が**スケッチ由来の初期値の補正**を与える。

判定の高速化のため、学習は初期状態からではなく、同一タスクの学習済み run から**制御方策ネットワークのみを転用**（control_prior）して開始する。転用成分の選択は第4章の分解実験（制御のみ・形態のみ・全成分・ゼロスタートの4条件比較）に基づく（空欄: 分解実験の結果）。判定の読み取りは学習曲線の順位に基づき、複数候補の順位確定には約 100 エポック、明らかに筋の悪い候補の除外には約 75 エポックを要する（第4章、L2 vs L2_s2・TP2 vs TP2_s2 の seed 差比較により較正）。（空欄: 前向き検証の結果 — 良い/悪い形態を意図的に用意した判定実験）

なお、パイプライン全体（M3〜M5）は単一のシェルスクリプトで一括実行でき、実証実験では画像 → GLB → XML → 学習開始までを人手の介在なしに通している。（空欄: 生成メッシュでの本格 co-design 学習・手描きスケッチでの E2E 実走の結果。水平3関節版（tripo_arm_v2 系）と、腕の可動平面を回転できる縦型4関節版（tripo_arm_v3）の双方で3タスク識別の再現を確認する予定。前者は rrbot と同一形態クラスでの追試、後者は形態クラスを広げた一般化の検証を兼ねる）

## 3.8 実装環境

再現性のため、実装に用いた計算環境を記す。ホスト OS は Ubuntu 24.04.4 LTS、Python 3.12.3 上に構築する。M3・M4（メッシュ処理・パラメータ抽出）には trimesh 4.12.2 を用い、GLB の読み込み・頂点色復元・OBB 計算を行う。M6（co-design 学習）の方策・価値ネットワークは PyTorch 2.7.0（CUDA 12.8 ビルド）で実装し、数値計算に NumPy 2.4.6 を用いる。物理シミュレーションには Choreonoid 2.3（AIST シミュレータ）を用い、M5 で生成した MuJoCo 互換 XML を内部形式へ変換して実行する。設定管理には Hydra を用いる。

外部生成 AI サービス（M1 の Gemini・M2 の Tripo3D）は、いずれも Web インタフェースを介した対話的利用であり、API 経由でのサンプリングパラメータ指定は行っていない。M1 で使用した固定プロンプトの全文は 3.2 節に記載した通りである。
