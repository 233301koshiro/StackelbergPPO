# 学習中・学習後の欠陥監査チェックリスト

> **このファイルの役割**: 「今の run に何か欠陥はないか」を聞かれたときに使う定型チェック。
> 2026-07-21 のtripo_arm監査（damping・関節可動域・`_check_initial_contact`・workerパス衝突の4件発見）
> で実際に有効だったカテゴリを一般化したもの。全て**学習を止めずに実行できる読み取り専用チェック**。
> 新しいバグが見つかったら、該当カテゴリに一次データへのリンクと一緒に追記する。

---

## 使うタイミング

- 新しいアーム・タスク・cfg を追加したとき（**学習を始める前**に一度）
- 学習が想定より遅い／速い／異常値のとき
- 「今の時点でモデルに欠陥がないか調べたい」と聞かれたとき（**学習を止めずに**実行）
- 大きな成果（過去最高値・異常な高得点）が出たとき — 真っ先に疑う

## ① 報酬・行動の物理的妥当性

**問い**: 得点の伸びは物理的に説明できるか、それとも exploit や環境バグか。

**根拠にした過去の発見**: cube damping confound（tripo v2 の Pusher 844.25 が rrbot の6〜8倍だった件。実験系譜.md 参照）。

**やり方**:
```
EVAL_RESTORE_DIR=single_run/<run> EVAL_CHECKPOINT=best \
USE_CHOREONOID=1 OMP_NUM_THREADS=1 /choreonoid_ws/install/bin/choreonoid --no-window \
  --python scripts/probe_cube_trace.py
```
出力の `final cube_x` / `peak |v|` を、同条件の別 run（できれば rrbot 系の確立済み値）と比較する。
比の説明がつかない（速度比の2乗則でも届かない）場合は環境パラメータ diff に進む。

## ② N関節ハードコードの見落とし

**問い**: 新しいアーム（2関節と違う関節数、または軸構成が違うアーム）向けのコードパスに、2関節・平面アーム専用の前提が残っていないか。

**根拠にした過去の発見**:
- `_check_initial_contact()` が `bodies[1]+bodies[-1]` だけを見て中間リンクを無視していた（Bug 13。3関節で37%、4関節で60%の先端位置過小評価）
- 可視化スクリプトが2関節専用のbody名を決め打ちしていた（Bug 15）
- `_check_initial_contact()`/`compute_reach_bonus()` の Bug 13 修正自体が `bone_offset[:2]`（X,Y成分のみ）を合計しており、**関節数は一般化されたが軸構成（平面 vs 立体）は一般化されていなかった**。全関節Z軸（ヨー）の平面アームでは正しいが、ピッチ軸混在の縦型アーム（tripo_arm_v3）では静止姿勢の長さが全部Z成分に乗るため `link_vec` が恒常的にゼロになり、先端位置を常に肩関節の真上と誤認していた（Bug 16、2026-07-24）

**やり方**: `design_opt/envs/*.py` **および `scripts/eval_*.py`・`scripts/compare_*.py`（可視化・分析スクリプトも同じ地雷を踏む — Bug 15）** を対象に以下を grep し、ヒットした値が「特定のアーム専用の値」でないか一つずつ確認する。関節**数**だけでなく、関節**軸の向き**（全部Z軸=平面内か、Y/Z混在=立体的か）が変わっても壊れないかも別途確認する（Bug 16）。
```
grep -n "env_specs\.get([^)]*,\s*[0-9]" design_opt/envs/*.py
grep -n "reward_specs\.get([^)]*,\s*[0-9]" design_opt/envs/*.py
grep -n "bodies\[1\]\|bodies\[-1\]\|bodies\[0\]" design_opt/envs/*.py
grep -n "'0',\s*'1',\s*'11'\|\['shoulder'\]\|\['elbow'\]" scripts/eval_*.py scripts/compare_*.py
grep -n "bone_offset[^)]*)\[:2\]\|bone_offset\[:2\]" design_opt/envs/*.py
```

## ③ 自分の修正が新しいバグを埋め込んでいないか

**問い**: 今日書いたコードは、変更対象以外の run でも・学習を通しても壊れていないか。

**根拠にした過去の発見**: Bug 13 修正内で `init_xml_str`（bytes）に str 正規表現を使い `TypeError` → Choreonoid が例外を握りつぶし「ハングに見えるクラッシュ」になっていた。

**やり方**:
```
for f in <対象runのlog_train.txtパス...>; do
  grep -ic "nan" "$f"
done
grep -c "Failed to run\|TypeError\|Traceback" <対象runのstdout.log>
```
**「ハングしている」ように見えたら、まず状況証拠（wchan・%CPU）より先にプロセス自身の生ログを見る**（今日15分無駄にした教訓）。

## ④ 形態の物理的妥当性

**問い**: Leader が出している現在の形態は、自己交差・退化（長さ0）・想定外の bounds 貼り付きになっていないか。既存のタスク別分岐パターン（低gear=Reach・高gear=Pusher 等）と整合するか。

**やり方**:
```
COMPARE_RUNS="single_run/<run1>:single_run/<run2>:..." COMPARE_LABELS="A:B:..." \
USE_CHOREONOID=1 OMP_NUM_THREADS=1 /choreonoid_ws/install/bin/choreonoid --no-window \
  --python scripts/compare_morphology.py
```
`range=` が意図した可動域になっているか、`bone_len` が異常値でないか、gear パターンが既存のタスク別傾向と矛盾しないかを確認する。**Bug 10 の教訓**: `control_prior`/`morph_prior` が true のままだと形態がアーティファクトになるので、再評価スクリプトはこれらを強制 False にしていることを確認する（`compare_morphology.py`・`eval_cnoid_visual.py` は対応済み）。

## ⑤ 並列実行由来の汚染

**問い**: 複数 run を同時に走らせているとき、run 間で state（ファイル・一時ディレクトリ・checkpoint）が衝突していないか。

**根拠にした過去の発見**: `ChoreonoidWorkerPool` の worker 一時ディレクトリが `CNOID_WORKER_ID`（run 内 0..n-1 の連番）だけで構成され、複数 run 並列時に全 run の worker0 同士が衝突していた（Bug 14）。

**やり方**:
```
ls -d /tmp/cnoid_worker_*
```
run ごとに別パス（`worker_tag = PID_i` 形式、2026-07-21 修正後）になっているか確認。新しい共有一時リソース（`/tmp/tmpXXXX.body` 等）を追加するコードを書いたときは、複数 run 同時起動でも衝突しないか同様に確認する。

## ⑥ 世代を跨いだ数値比較にコード差分が混入していないか（2026-07-31 追加）
> **世代の境界（2026-08-06 整理）**: 比較したい2 run が同じコード世代かを、次の日付で判定する。
> - **2026-07-06**: exec フェーズの NaN 報酬が 0 → −1000 ペナルティへ（Bug 20）。`exec_R_eps` の意味が変わる
> - **2026-07-15〜24**: Bug 11 / 13 / 14 / 16 の修正、`check_floor_penetration` の追加（9-2）
> これらを跨ぐ run 同士は、**順位は比べてよいが絶対値・比率は比べない**。


**問い**: 「同じ設定で epoch 数（や seed）だけ変えた再実験」として2つの run を比較しようとしているとき、**その2つが同じコードで走っているか**。

**根拠にした過去の発見**: M系 ablation の再実験で、`M1_lenonly`（200ep、2026-07-15 起動）と `M1_lenonly_1000`（1000ep、2026-07-27 起動）は同一 seed・同一 hydra override にもかかわらず **ep0 の時点で既に値が違っていた**（seed0: -0.13 vs -12.76）。原因は乱数ではなく、2つの起動の間に入った `design_opt/`・`khrylib/` の変更（Bug 11/13/14/16 の修正、`check_floor_penetration` の新規追加）だった。「1000ep に延ばしたら下がった」という解釈は誤りで、両者はそもそも別のコードで走った別の実験である（実験系譜.md 第9段 9-2）。

**やり方**:
```
# 2つの run の起動時刻を確認
stat -c '%y %n' single_run/<runA>/.hydra/config.yaml single_run/<runB>/.hydra/config.yaml

# その期間に学習の挙動を変えうるコードが変わっていないか
git log --oneline --since="<runAの日付>" --until="<runBの日付>" -- design_opt/ khrylib/
```
1件でもヒットしたら、その差分が学習の挙動に影響するかを個別に判断する。影響するなら**世代跨ぎの数値比較はしない**（同一世代内の比較に限定する）。特に env の終了条件・ペナルティ経路・観測の計算式を変えるコミットは要注意。

このリポジトリは実験と並行してバグ修正が続いているため、数週間スパンの再実験では**ほぼ必ず**何らかの差分が入っていると考えた方がよい。
