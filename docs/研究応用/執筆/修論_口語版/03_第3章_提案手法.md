# 前提: Stackelberg PPO による形態-制御 co-design（3.1〜3.4）

## 3.1 問題設定: 階層ゲームとしての co-design

Stackelberg PPO は、形と制御を一緒に最適化する問題を、Stackelberg ゲームの一種として定式化します。Stackelberg ゲームは、先に決める側（Leader）が、後から合わせる側（Follower）がどう応じるかを見越して決める、上下関係のあるゲームです。

Leader は形を編集する方策 $\pi^L(\cdot \mid s^L_t; \theta^L)$ です。Follower は、決まった形のもとで制御をする方策 $\pi^F(\cdot \mid s^F_t; s^L_T, \theta^F)$ です。

1 回の試行（エピソード）は、2 つの段階に分かれます。前半（$t = 0, \dots, T-1$）では、Leader が形を編集する行動 $a^L_t$ をとって、最後の形 $s^L_T$ を決めます。後半（$t \ge T$）では、Follower がその形 $s^L_T$ を前提にした制御の行動 $a^F_t$ をとって、タスクの報酬 $R^F$ を受け取ります。

2 人の目的は、次の式で表されます。

$$J^F(\theta^L, \theta^F) = \mathbb{E}\left[\sum_{t=T}^{\infty} \gamma^{t-T} R^F(s^F_t, a^F_t; s^L_T)\right]$$

$$J^L(\theta^L, \theta^F) = \mathbb{E}\left[\sum_{t=0}^{T-1} \gamma^t R^L(s^L_t, a^L_t) + \sum_{t=T}^{\infty} \gamma^{t-T} R^F(s^F_t, a^F_t; s^L_T)\right]$$

この研究にとって大事なのは、$J^L$ の 2 つ目の項です。**Leader の評価には、自分は何も編集しない実行の段階で Follower が稼いだ成績（リターン）が、そのまま引き継がれます。**つまり形は、運動学の理屈の上でどうかではなく、**その形を制御の方策が実際にどれだけ使いこなせたか**で評価されます。この性質が、co-design を形の設計の判定器として使う、この研究の根拠です（第1章）。

Leader の更新には、Follower の最適な応じ方がどれだけ変わるかの感度を織り込んだ「Stackelberg 勾配」を使います。この勾配は Follower 側の損失の Hessian（2 階微分）を含んでいて、共役勾配法による陰関数の微分で近似します。正則化の係数 $\lambda$ を変えると、Stackelberg 勾配（$\lambda \to 0$）と、ふつうの方策勾配（$\lambda \to \infty$）のあいだをなめらかにつなげます。制御の方策と形の方策のどちらの更新にも PPO を使います。詳しくは元の論文にゆずります。

## 3.2 役割別の報酬設計に関する原論文の規定

元の論文の付録は、報酬の項を Leader と Follower に選んで割り当てる「役割ごとの報酬設計」を、はっきり認めています。たとえば、材料のコストや複雑さのペナルティを Leader の更新だけに使って、制御の学習には口を出させない、という使い方です。

大事なのはその境目です。**Leader 専用の報酬の項を $J^L$ に足すのは、枠組みの想定の範囲内です。**でも、$J^L$ の 2 つ目の項（Follower の成績を引き継ぐ部分）を別の量に**置き換える**のはだめです。Leader が Follower の実際の応じ方を見なくなって、Stackelberg の構造の前提が壊れるからです。この研究の報酬の設計（第4章の環境の直し、第5章の考察）は、この決まりに従っています。

## 3.3 方策のアーキテクチャ

方策のネットワークは、形を木の構造（ボディグラフ）として扱う Transformer を土台にした作りで、グラフの構造を意識した位置の符号化を使います。それぞれのボディ（部品）がノードとして観測（深さ、設計のパラメータ、シミュレーションの状態）を持ち、行動（形の編集や制御）もノードごとに出します。

この作りのおかげで、実際の使い勝手として、**リンクの数が違う形を、同じネットワークがそのまま扱えます。**この研究で、生成したメッシュから作った 3 関節の腕が、コードを書き換えずに受け付けられたのは、この性質のためです（第4章 4.2.1 節）。

## 3.4 本研究で用いる実装上の構成

この研究の実験は、上の枠組みに次の設定を加えて行います（どれも元の論文の枠組みの範囲内の設定です）。

- **形の段階の分け方**: 実装では、Leader の段階がさらに「骨格を変える」（リンクを足したり消したりする。最大 5 ステップ）と「性質を変える」（リンクの長さやギア比などの連続的な値を編集する。1 ステップ）に分かれています。この研究では、つながり方をスケッチから来た構造に固定するので、骨格を変える段階は止めて、性質を変える段階だけを使います。
- **設計のパラメータの変換**: 性質を変える行動は、$[-1, 1]$ に正規化した空間で行い、正弦関数を使った変換で実際のパラメータの範囲（bone_offset は初期値から $\pm 0.5$ m、ギア比は $[20, 400]$ など）に直します。⚠️ **ただしこの範囲は、この論文の中心の実験の設定であって、実在の部材から導いたものではありません。**4.6 節では、リンクの密度、アクチュエータの出力の範囲、リンクの長さを探す範囲のどれも、実在の材料と実在のアクチュエータ（UR5e 級）から導き直しました。ギア比 $[20, 150]$、リンクの長さは絶対値ではなく**各リンクの設計の長さに比例する幅** $[0.5\,\text{倍}, 2.93\,\text{倍}]$ とした条件で、同じ確かめをやり直しています（5.3 節 (B) も参照）。1 回の編集の歩幅は係数（robot_param_scale）で決まります。これは探す範囲の制限ではなく、更新の刻み幅です。
  > ⚠️ **（口語版の注）この段落は本文が古いままです。**10-13 から全部の実験を実在の値でやり直したので、いまの中心の実験の条件は第4章 4.1.1 節（表 4.1・表 4.2、ギア比は水平の腕で $[20, 150]$）です。「中心の実験は $[20, 400]$」「4.6 節で再実行した」は、いまの状態と食い違っています。
- ⭐ **設計の段階の報酬**: 骨格を変える段階にも、性質を変える段階にも、**すぐにもらえる報酬はあげません**（$r = 0$）。設計の行動が良かったかどうかは、**同じエピソードの実行の段階で稼いだ成績が、割引を通してさかのぼって割り当てられる**ことで評価されます。⚠️ **ただ 1 つの例外は、Leader 専用の 1 回だけのボーナスです**（腕の届く範囲の輪が、対象を幾何的に覆う形に点を足すもの）。これは幾何だけで決まるので、学習には左右されません。⭐ **この作りの結果、形が良いかどうかの見込みは、価値関数の推定を通してしか得られず、学習がどれだけ進んだかに左右されます**（判定に要る学習量の較正は第4章 4.5.3 節）。

# 第3章 提案手法: スケッチ起点の形態検証パイプライン（3.5〜3.13）

## 3.5 システム全体像

提案するシステムは、手描きのスケッチを入力にして、その形が狙ったタスクに向いているかの判定と、向いていなかったときの直す方向を出します。処理は次の 7 つの工程をこの順に通る、一方通行のデータの流れです（図 3.1）。

**どこまで自動かを、先に話しておきます。**M3 から先（関節の検出から、モデルの生成、学習の開始まで）は、1 本のシェルスクリプトで自動にしています。**M1（絵を整える）と M2（立体を作る）は、外部の生成 AI のサービスに頼っています。**この研究では、その API で呼び出す経路も作りました（3.13 節）。⚠️ **ただし、第4章 4.5 節で報告する、最初から最後まで通した実走 5 件は、API を作る前に、画面を操作する対話のインタフェースで行いました。**なので、この章で「人の手を借りない」と言っている範囲は、**M3 から先の毎回同じ結果になる処理と、M6 の学習**です。生成物を手に入れる工程は入っていません。

**図 3.1**: 提案するシステムの全体の作り

```
手描きスケッチ
  → [M1] 絵を整える（関節の目印の決まりを当てる）        … 生成 AI（プロンプト固定）
  → [M2] 立体の形を作る（image-to-3D）                   … 既存の技術（Tripo3D）
  → [M3] 関節を見つけて、リンクに切り分ける              … 色の検出 + 幾何の処理（毎回同じ結果）
  → [M4] 形のパラメータを取り出す                        … 関節のあいだの距離と断面（毎回同じ結果）
  → [M5] シミュレーション用のモデルを作る                … テンプレートで変換（毎回同じ結果）
  → [M7 第1層] 幾何で先に判定する                        … 向いていなければ拡大の倍率を返す（学習の前）
  → [M6] 形態-制御 co-design で評価・修正する            … Stackelberg PPO
  → [M7 第2・3層] 収束した形と動き方を診断する           … 報告だけ
  → 判定（タスクに向いているかの点数・修正後の形・直し方の指示）
```

設計の考え方は 3 つです。

1 つ目に、動く仕組みを取り出すのに、学習による推定を使いません。上流（M1）での入力の決まりと、下流（M3）での毎回同じ結果になる色の検出に置き換えます。生成モデルの出力の不確かさを、パイプラインの中で後から補うのではありません。入力をしばることで、構造の推定という、答えが 1 つに決まらない問題を避けます。

2 つ目に、M3〜M5 を、乱数も学習も使わない、毎回同じ結果になる処理にします。失敗したときに原因を突き止められて、同じ結果を再現できるようにするためです。

3 つ目に、M5 が、既存の co-design の枠組みと互換な MuJoCo 互換の XML を出すようにします。そうすれば、学習の仕組みの中のコードを書き換えずにつなげます。

## 3.6 M1: 画像整形と関節マーカー規約

入力のスケッチは、画像を生成する AI（Gemini）で、後ろの立体化と色の検出に向いた「機械の設計図ふう」の画像に変えます。このとき、このシステムの中心である**関節の目印の決まり**を、決まったプロンプトとして課します。この決まりは、構造を推定することを生成モデルに任せるのではなく、**構造の境目をはっきり描くことを強制する**ものです。要点は 3 つです。

1. **関節のつなぎ目すべてに、純粋なマゼンタ（#FF00FF）の球を 1 個ずつ描かせる。**マゼンタは、ふつうの写真や工業製品にはめったに出てこない色合いなので、色で見分けやすくなります。
2. **リンクはそれぞれ鮮やかな 1 色で塗り分けさせ、グラデーションとマゼンタを使うのを禁止する。**
3. **関節の位置を場所として並べて書き（「台座と上腕のあいだ」など）、描いた後で球の数を自分で確かめさせる。**場所を並べて書かないと、先端に近い関節が機械の部品として描かれてしまい、目印が抜け落ちます（3 関節と指示したのに 2 個になる）。

こうすることで、M3 の関節の検出は、精度の保証が無い推定の問題から、しきい値つきの色合わせという、答えが決まる問題に変わります。プロンプトの全文は付録A に載せています（ゼロから生成する版の A.1 と、手描きのスケッチを整える版の A.2。4.5 節の、最初から最後まで通した実走 5 件は、すべて A.2 を使いました）。

### 3.6.1 プロンプト規約の遵守における非決定性

この工程は API 経由で実行して（モデルは `gemini-3-pro-image`、サンプリングの温度は 0）、リンクは「両端が平らな円柱」として指示します（端が丸いと関節の球とまぎらわしく、目印が省かれるからです）。

⚠️ **温度を固定しても、決まりがいつも守られるとは限りません。**目印の個数は 1 回目で正しく出ます。でも、向き、寸法線などの禁止、比率を保つことは、個数ほど安定しません（5.3 節 (B)）。腕が傾いて出力されると、関節が近い高さに並んでしまい、Z 座標を境目にした切り分けがうまくいかなくなります。そのため、M1 の出力は人が確かめてから次の工程へ渡します。

## 3.7 M2: 三次元形状生成

整えた画像は、image-to-3D のサービス（Tripo3D）で三次元のメッシュ（GLB 形式、Y 軸が上の座標系）に変えます。API で seed を固定して呼び出します（3.13 節）。

入力の画像の純粋なマゼンタ (255, 0, 255) は、生成の途中でだいたい (211, 75, 169) へと暗くなります。それでも、リンク本体の色とは別のかたまりとして残るので、探す色を自動で合わせ直せば、検出はうまくいきます（3.8 節）。

### 3.7.1 スケールの決まり方

**生成サービスは、出力するメッシュを囲む箱のいちばん長い辺を 1.0（= 1 m）にそろえます**（手元の GLB 4 件すべてで 1.0000 でした）。なので、絶対的な大きさは、入力の画像の画素数や添えた寸法には左右されず、**絵の中の比率だけで決まります。**

手描きの入力 A1 では、線画の上での腕の長さと、絵全体のいちばん大きい寸法の比が 1.01 で、生成したモデルの腕の届く距離の合計（総リーチ）を測ると 1.0102 m でした。利用者が絶対的な大きさを数字で指定する手段はありません。必要なら、生成した後で全体に同じ倍率を掛けます（リンクどうしの比は保たれるので、形を見分けることには影響しません）。

## 3.8 M3: 関節検出とリンク分割

M3 は、GLB のメッシュから関節の位置を見つけて、メッシュをリンクごとに切り分けます（`glb_to_links.py`）。

1. **頂点の色を取り戻す**: UV テクスチャの色を、頂点の色に焼き込みます。
2. **目印の頂点を抜き出す**: 探す色 $c_0$ と許す幅 $\tau$ に対して、色の各成分で $|c_i^{(k)} - c_0^{(k)}| \le \tau$ を満たす頂点を抜き出します。$c_0$ と $\tau$ は、マゼンタの色合いの範囲（285〜345°）にある頂点のかたまりの中央値と広がりから、自動で合わせます。そのかたまりが無ければ、検出の失敗として止まります。
3. **関節の位置**: 目印の頂点を、**三次元で**つながったかたまりに分けて、それぞれの重心を関節にします。目印の頂点全体の 2 % に満たないかたまりは、色のにじみのノイズとして捨てます。つながりを判断する半径（全体の大きさに対して 0.02）と 2 % は、どちらも比率なので、大きさに左右されません（予備の実験にもとづく経験的な値です）。
4. **リンクに切り分ける**: 関節の Z 座標を境目にして、各ポリゴンを重心の Z で振り分けます。境目のあいだにポリゴンが 1 つも無ければ、関節の位置がおかしいとして止まります（おかしいと分かった時点ですぐ止める、フェイルファスト）。
5. 切り分けた各部分を、リンクのローカルな座標へ平行移動して、STL として出力します。先端の部品の向きが意図と違うとき（平らな面が押す向きを向いている、など）は、指定したリンクを骨の軸のまわりに回す補正を、手で与えられます。

## 3.9 M4: 形態パラメータ抽出

切り分けたそれぞれのリンクから、co-design の設計の値の初期値を求めます（`mesh_to_params.py`）。

- **リンクの長さ** $L$: **関節と関節の距離**です（M3 が持っている関節の座標から求めます。先端のリンクは、最後の関節からいちばん遠い点まで）。
- **カプセルの半径** $r$: **骨の軸に垂直な断面**の、2 方向の幅の平均の半分です。

**どちらも OBB（向きを合わせた外接の直方体）を使いません。**OBB のいちばん長い辺は、切り分けた部分に入っている目印の球の半分を拾ってしまい、いつも長めに出ます。OBB の短い辺から半径を求める計算は、いちばん長い辺が骨の軸と一致していることが前提ですが、先端が太い形ではこの前提が崩れます。骨の軸は M3 の関節の座標として分かっているので、それを直接使います。

取り出した値が妥当かは、**カプセルが元のメッシュを覆えているか**で評価しました（「正しい半径」は、柄の太さとも先端の太さとも解釈できますが、覆えているかどうかは 1 通りに決まります）。手描きの入力 5 例・20 リンクで、カプセルの外に出る頂点の割合は平均 21.4 % でした。OBB の短い辺から求めた場合の 29.7 % より小さく、悪くなったリンクはありませんでした。

それでも残る覆いきれなさの主な原因は、傾いた腕を水平な面で切り分けていることです。切る面がリンクの軸に対して斜めになるので、先端の部分に関節より後ろ側が入り込み、半径も小さめに出ます。B1 の手先は頂点の 70.9 % が外に出ますが、はみ出しの量の中央値は 5〜10 mm です（まっすぐ立った A1 の手先は 8.9 %）。限界として 5.3 節に書きます。

関節が動く範囲とギア比の初期値は、スケッチの幾何からは 1 通りに決まらないので、決まった値（ギア比 100、動く範囲 ±90°）を使います。設計の値を探す範囲（ギア比の上限、リンクの長さを伸び縮みさせる幅）と、物理の値（リンクの密度、アクチュエータの回転子の慣性と速度の上限）は、co-design の側の設定で与えます。これらは実在の部材と実在のアクチュエータ（UR5e）から導きます（第4章 表 4.2・4.6 節）。

## 3.10 M5: シミュレーションモデル生成

topology.json は、MuJoCo 互換の XML に変換します（`topology_to_xml.py`）。各リンクをカプセルで近似し、子のリンクの `<body>` を親の中に入れ子にして、その位置を親の骨の長さのところに置きます（つまり親の先端に取り付けます）。関節（回転軸と動く範囲）とアクチュエータ（ギア比）を付けます。学習の側では、読み込むときに Choreonoid のモデルの形式（.body）に変換します。

形を長さの変わるグラフとして扱う Transformer の方策なので、3 関節のメッシュから作ったモデルは、**学習の仕組みのコードを変えずに**受け付けられました。⚠️ ただし、前の工程（M1〜M3）を 3 関節以外で実行した例は無く、**この論文が扱った形はすべて 3 関節です**（5.4 節）。

関節の軸は、関節ごとに x・y・z のどれかの座標軸を割り当てます。決まった設定として、2 つのモードを用意しています。すべての関節をヨー軸（鉛直の軸まわり）にして、骨を X 軸の向きに並べる**平面モード**と、根元をヨー軸、その先をピッチ軸（水平の軸まわり）にして、骨を Z 軸の向きに積む**縦型モード**です。**この論文が報告する実験の大部分は平面モードです。**付録D の、平面にとどまらない 4 関節の腕（`tripo_arm_v3`）は、縦型モードを足す前に、生成したメッシュから人の手で書き起こしたモデルで、パイプラインの出力ではありません。⚠️ **軸の割り当ては入力の形から推定するものではなく、利用者が与えます。**形から軸を推定するのは、これからの課題にします（5.4 節）。

## 3.11 M6: co-design による評価・補正と判定

作ったモデルを最初の形にして、Stackelberg PPO による形態-制御 co-design を実行します。

エピソードは 3 つの段階からなります。骨格を変える段階（このシステムでは飛ばします。つながり方はスケッチが決めるからです）、性質を変える段階（Leader が bone_offset・太さ・ギア比を編集します）、実行の段階（Follower が制御してタスクの報酬を得ます）です。Leader の目的には、Follower の実行の成績が引き継がれます。

そのため、学習が進むにつれて、次の 2 つが得られます。(i) 実行の成績の移り変わりが、**その形の流れのタスクのこなし具合の評価**になります。(ii) Leader による設計の値の更新が、**スケッチから来た初期値の修正**になります。判定は、学習曲線の順位で読みます。要る学習量は 4.5.3 節で較正します。

## 3.12 M7: 形態診断

### 3.12.1 判定から診断へ

M6 が返すのは、「このスケッチはこのタスクに向いているか」という順位か点数です。でも、想定している利用者はロボット設計の専門知識を持っていないので、「向いていません」とだけ言われても、次に何をすればいいか判断できません。**向いていない原因と直す方向を、言葉にして返す**必要があります。

M7 は追加の学習を必要とせず、M6 が作るもの（最初の XML、収束した形のチェックポイント、動きの記録）だけを入力にします。診断に生成 AI は使わず、しきい値と比べて選んだ決まった文に、測った値を差し込んで返します。

### 3.12.2 三層構造

M7 は、計算の手間が違う 3 つの層からなります。上の層ほど、安くて確実です。

**第1層（幾何の診断・学習なし）**: 最初の XML だけを解析して、腕が届く最大の距離と関節の動く範囲のもとで届く範囲を、目標や対象の位置と比べます。かかるのは数秒以内で、シミュレータを立ち上げる必要も、学習もありません。見つけるのは 3 種類です。(i) 目標が届く最大の距離の外にあって届かない。(ii) 止まった姿勢で先端が対象にめり込む。(iii) 関節の軸の向きが、タスクの想定と合っていない。

(i) のときは、**判定をひっくり返すのに必要な最小の拡大の倍率**を数字で返します（例:「腕全体を 1.99 倍に伸ばしてください」）。倍率は切り上げます（四捨五入だと、示した値が必要な量より小さくなって、従っても判定がひっくり返らないことがあります）。最小の変更だけを返すのは、反実仮想説明と実行できる救済の条件に合っています（2.4 節）。

届く最大の距離の計算には、前提が 2 つあります。

1 つは、リンクの長さの合計が届く距離に等しくなるのは、それぞれの関節が 1 つ前のリンクの先端にあるときだけだ、ということです。なので、関節の位置をつないで求めた届く距離と食い違う XML は、つじつまが合わないとして却下します。

もう 1 つは、長さの合計がそのまま水平に届く半径になるのは、平面の腕だけだ、ということです。平面にとどまらない腕では、回る軸と平行なリンクを除いた、水平に届く限界で判定します。

関節が動く範囲による届くかどうかの判定は、動く範囲を格子状に調べて行います。格子の粗さから来るすき間を、順運動学のリプシッツ定数（入力が少し変わったときに出力がどれだけ変わりうるかの上限）で見積もって、**「届かない」という側だけが確実になる**ように作っています。リンクの長さが最適化の対象に入っている設定では、学習の途中で届く最大の距離が伸びうるので、第1層は「届かない」という否定の判定だけをします。

**第2層（収束した形の診断）**: co-design が収束させた設計の値を読んで、探す範囲の端に張り付いていないかを見つけます。ギア比が上限に張り付いていれば力が足りない、下限に張り付いていれば省エネの方向へ収束した、という意味です。

ただし、後者の読み方はタスクによります。到達のタスクでは、弱くて細い設計が、確率的な方策のもとで止まる精度を保つ、正常な最適な答えでもあります。実際、届く形と届かない形が同じ署名（同じ張り付き方）を見せました（4.3.3.1 節）。なので、この署名は、到達のタスクでは警告にとどめます。強い力が有利なはずの押しのタスクでだけ、向いていない兆しとして報告します。

**第3層（動き方の診断）**: 収束した方策を、ばらつきなしで 1 エピソード実行して、その軌跡から戦略を分類します。押しのタスクでは「一撃で吹き飛ばす」「穏やかに押す」「触れられていない」、到達のタスクでは「目標で止まる」「ずれて止まる」「届かない」に分けます。

あわせて、それぞれの関節が、動く範囲のうち実際に何割を使ったかを報告します。10 % を下回る関節については、固定すれば重さと制御の自由度を減らせるかもしれない、と指摘します。第1層の「腕を N 倍に伸ばせ」とは逆の、**設計を減らす向きの指摘**です。

利用者の意図と違う戦略に収束しているとき（例: 狙った場所に止めたいのに、吹き飛ばしている）は、形ではなく**タスクの選び方のまちがい**として、別のタスクを示します。

### 3.12.3 診断の妥当性検証の位置づけ

3 つの層の診断が、実際に測った順位と合うかどうかは、診断の設計の話ではなく、実験の話です。確かめた条件と結果は 4.4.1 節に示します。この節から後では、診断の設計の性質を話します。

### 3.12.4 第3層の閾値は判定規則ではなく候補生成器である

第3層のしきい値（動く範囲の 10 %）は、実験で較正していません（5.3 節 (D)）。**ただし、しきい値が決めるのは「固定してみる価値のある関節」であって、「固定すべき関節」ではありません。**

採るかどうかは、助言どおりに固定した形を学習させて、**元の形と成績の範囲（帯）が重なるかどうか**で決めます。この基準は、この研究が形の順位づけ全般に使っているものと同じです（4.3.3 節）。

### 3.12.5 診断の範囲外とした事項

第1層の「腕全体を N 倍以上に伸ばしてください」は、判定をひっくり返すのに必要な最小の変更を、利用者が動かせる変数の上で示した反実仮想説明です（2.4 節）。**第2層・第3層では、同じような出力を作れていません。**収束した設計や動き方から「何が起きたか」は報告できますが、「設計をどう変えればその結果が変わるか」は、学習をやり直さないと分かりません。第1層でそれができるのは、幾何が支配している層では、必要な変更が運動学から計算で直接求まるからです。

また、意図から報酬の関数を自動で設計する機能は、範囲の外にしました（報酬を複雑にすると、探すための手がかりが消えることがあるからです）。

### 3.12.6 考察: なぜ三層に分ける必要があったか

**層の分け方は、手間ではなく、確実さで決まります。**

第1層が使うのは、リンクの長さと目標の位置という、運動学の量だけです。「届く最大の距離が 0.403 m の腕は、0.800 m 先の目標に届かない」は、学習の結果にも乱数の種にも左右されません。一方、第2層・第3層が使うのは学習の結果で、乱数の種や、どこで打ち切ったかに左右されます。

ここから、設計の原則が出てきます。**確実な層は言い切ってよく、確率的な層は言い切ってはいけない。**実装では、第1層だけが「この形ではタスクをこなせません」という総合の判定を出し、第2層・第3層は観察の報告にとどめます。

**収束した形は「できた」と「あきらめた」を区別しません。**目標に届かない短い腕では、ギア比と太さがどちらも探す範囲の下限に収束しました。でも、目標に 1 mm 未満の精度で届いた中くらいの腕でも、同じ署名が出ました。到達のタスクでは、届かない形は報酬が良くならないので、いちばん弱い設計に落ちます。届く形も、届いた後に止まるために弱い設計を選びます。だからです。

co-design が返す収束した形は「報酬をいちばん大きくした結果」でしかなく、その報酬が高いか低いかは含んでいません。形のパラメータだけからは成否を判断できず、報酬の水準、幾何、動き方のどれかと組み合わせる必要があります。これが、3 つの層の作りにした直接の理由です。

**幾何が学習の代わりになれるのは、タスクの要求を運動学の量に置き換えられる場合だけです。**第1層は、到達のタスクの順位（中くらい ＞ 長い腕 ＞ 短い腕）を学習なしで予測しました。でも、押しのタスクの中くらいと長い腕の優劣は予測できません。押しが求めるのは先端の速さで、アクチュエータの出力と制御の上達がからむからです。なので第1層は、向いていないものを見つけることにとどめ、向いていると判定した形には、学習で性能を確かめるようにはっきり促します。

## 3.13 実装環境

同じ結果を再現できるように、使った計算の環境を書いておきます。

ホストの OS は Ubuntu 24.04.4 LTS で、Python 3.12.3 の上に作っています。M3・M4（メッシュの処理とパラメータの取り出し）には trimesh 4.12.2 を使い、GLB の読み込み、頂点の色の取り戻し、OBB の計算をします。M6（co-design の学習）の方策と価値のネットワークは PyTorch 2.7.0（CUDA 12.8 版）で作り、数値計算には NumPy 2.4.6 を使います。物理のシミュレーションには Choreonoid 2.3（AIST シミュレータ）を使い、M5 で作った MuJoCo 互換の XML を中の形式に変換して実行します。設定の管理には Hydra を使います。

外部の生成 AI のサービスのうち、**M1 の Gemini は API 経由で実行します**（モデルは `gemini-3-pro-image`、温度 0）。**M2 の Tripo3D も API 経由で実行します**（`scripts/tripo_api.py`、seed は固定）。M1 で使った決まったプロンプトの全文は、付録A（A.1 と A.2）に載せています。

手描きのスケッチを入力にした、最初から最後まで通した実走（4.5 節）では、M1 の絵の整形に Gemini 3.1 Pro の拡張機能を使いました。ただし、この論文が報告する `tripo_arm_v2c` 系のモデルは 2026 年 7 月に作ったもので、そのとき使った生成モデルのバージョンは記録していません。外部のサービスはバージョンが更新されることがあるので、そのモデルを作った過程を厳密に再現することはできません。これは実装上の限界で、それ以降に作るものについては、サービスの名前とバージョンを記録するようにしています。
