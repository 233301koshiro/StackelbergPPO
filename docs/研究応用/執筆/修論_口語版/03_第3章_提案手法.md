# 前提: Stackelberg PPO による形態-制御 co-design（3.1〜3.4）

## 3.1 問題設定: 階層ゲームとしての co-design

Stackelberg PPO は、形と制御を一緒に最適化する問題を、Stackelberg ゲームの一種として定式化します。Stackelberg ゲームは、先に決める側（Leader）が、後から合わせる側（Follower）がどう応じるかを見越して決める、上下関係のあるゲームです。

Leader は形を編集する方策 $\pi^L(\cdot \mid s^L_t; \theta^L)$ です。Follower は、決まった形のもとで制御をする方策 $\pi^F(\cdot \mid s^F_t; s^L_T, \theta^F)$ です。

$\pi(\cdot \mid \ldots)$ は、縦棒の右に書いた条件のもとで、それぞれの行動をとる確率を返す関数です。セミコロンの右は、その方策を使っているあいだ固定しておく量です。記号の読み方と意味を、表 3.1 にまとめます。つまり Follower は、形 $s^L_T$ と重み $\theta^F$ を固定したうえで、いまの関節の状態と、手先から見た箱の位置 $s^F_t$ を見て、どう動かすかの確率を返します。実装では、決まった形の設計パラメータが Follower の観測にも入っていて、これで Follower は「その形のもとで」動かすことになります。

**表 3.1**: 方策の記号

| 記号 | 読み | 意味 |
|---|---|---|
| $\pi$ | パイ | 方策。状態を入れると、それぞれの行動をとる確率を返す関数（円周率ではない） |
| 上付きの $L$・$F$ | エル・エフ | Leader 用か Follower 用かの名札（べき乗ではない） |
| $(\cdot \mid \ldots)$ | 点、ギブン … | 条件付き確率の書き方。縦棒の右が与えられたもの（条件）、左の点が確率を割り当てる行動の空欄 |
| $s^L_t$ | エス・エル・ティー | 時刻 $t$ の Leader の状態。いまの形（各リンクの設計パラメータ） |
| $s^L_T$ | エス・エル・大文字ティー | Leader が最後の時刻 $T$ に決めた形 |
| $s^F_t$ | エス・エフ・ティー | 時刻 $t$ の Follower の状態（各関節の角度と角速度、手先から見た箱の位置） |
| $\theta^L$・$\theta^F$ | シータ・エル、シータ・エフ | それぞれの方策ネットワークの重み（学習で更新される数の集まり） |
| セミコロン（;） | — | ここから右は確率変数ではなく、方策を使うあいだ固定しておく量、という区切り |

1 回の試行（エピソード）は、2 つの段階に分かれます。前半（$t = 0, \dots, T-1$）では、Leader が形を編集する行動 $a^L_t$ をとって、最後の形 $s^L_T$ を決め、後半（$t \ge T$）では、Follower がその形 $s^L_T$ を前提にした制御の行動 $a^F_t$ をとって、タスクの報酬 $R^F$ を受け取ります。

2 人の目的は、次の式で表されます。

$$J^F(\theta^L, \theta^F) = \mathbb{E}\left[\sum_{t=T}^{\infty} \gamma^{t-T} R^F(s^F_t, a^F_t; s^L_T)\right]$$

$$J^L(\theta^L, \theta^F) = \mathbb{E}\left[\sum_{t=0}^{T-1} \gamma^t R^L(s^L_t, a^L_t) + \sum_{t=T}^{\infty} \gamma^{t-T} R^F(s^F_t, a^F_t; s^L_T)\right]$$

この研究にとって大事なのは、$J^L$ の 2 つ目の項です。**Leader の評価には、自分は何も編集しない実行の段階で Follower が稼いだ成績（リターン）が、そのまま引き継がれます。**つまり形は、運動学の理屈の上でどうかではなく、**その形を制御の方策が実際にどれだけ使いこなせたか**で評価されます。この性質が、co-design を形の設計の判定器として使う、この研究の根拠です。

Leader の更新には、Follower の最適な応じ方がどれだけ変わるかの感度を織り込んだ「Stackelberg 勾配」を使います。この勾配は Follower 側の損失の Hessian（2 階微分）を含んでいて、共役勾配法による陰関数の微分で近似し、正則化の係数 $\lambda$ を変えると、Stackelberg 勾配（$\lambda \to 0$）と、ふつうの方策勾配（$\lambda \to \infty$）のあいだをなめらかにつなげます。制御の方策と形の方策のどちらの更新にも使うのは、PPO です。詳しくは元の論文にゆずります。

## 3.2 役割別の報酬設計に関する原論文の規定

元の論文の付録は、報酬の項を Leader と Follower に選んで割り当てる「役割ごとの報酬設計」を、はっきり認めています。たとえば、材料のコストや複雑さのペナルティを Leader の更新だけに使って、制御の学習には口を出させない、という使い方です。

大事なのはその境目です。**Leader 専用の報酬の項を $J^L$ に足すのは、枠組みの想定の範囲内です。**でも、$J^L$ の 2 つ目の項（Follower の成績を引き継ぐ部分）を別の量に**置き換えて**はいけません。Leader が Follower の実際の応じ方を見なくなって、Stackelberg の構造の前提が壊れるからです。この研究の報酬の設計（4.1.6 項）は、この決まりに従っています。

## 3.3 方策のアーキテクチャ

方策のネットワークは、形を木の構造（ボディグラフ）として扱う Transformer を土台にした作りで、グラフの構造を意識した位置の符号化を使います。それぞれのボディ（部品）がノードとして観測（深さ、設計のパラメータ、シミュレーションの状態）を持ち、行動（形の編集や制御）もノードごとに出します。

この作りのおかげで、実際の使い勝手として、**リンクの数が違う形を、同じネットワークがそのまま扱えます。**この研究で、生成したメッシュから作った 3 関節の腕が、コードを書き換えずに受け付けられたのは、この性質のためです（4.2.1 項）。

## 3.4 本研究で用いる実装上の構成

この研究の実験は、上の枠組みに次の設定を加えて行います（どれも元の論文の枠組みの範囲内の設定です）。

- **形の段階の分け方**: 実装では、Leader の段階がさらに「骨格を変える」（リンクを足したり消したりする。最大 5 ステップ）と「性質を変える」（リンクの長さやギア比などの連続的な値を編集する。1 ステップ）に分かれています。この研究では、つながり方をスケッチから来た構造に固定するので、骨格を変える段階は止めて、性質を変える段階だけを使います。
- **設計のパラメータの変換**: 性質を変える行動は、$[-1, 1]$ に正規化した空間で行い、正弦関数を使った変換で、実際のパラメータを探す範囲に直します。探す範囲は表 4.1 のとおりで（ギア比は水平の腕で $[20, 150]$、縦型の腕で $[25, 150]$ N·m。縦型の腕のリンクの長さは、**各リンクの設計の長さに比例する幅** $[0.5\,\text{倍}, 2.93\,\text{倍}]$）、実在の部材と実在のアクチュエータ（UR5e）から導きました（表 4.2）。1 回の編集の歩幅は係数（robot_param_scale）で決まります。これは探す範囲の制限ではなく、更新の刻み幅です。
- ⭐ **設計の段階の報酬**: 骨格を変える段階にも、性質を変える段階にも、**すぐにもらえる報酬はあげません**（$r = 0$）。設計の行動が良かったかどうかは、**同じエピソードの実行の段階で稼いだ成績が、割引を通してさかのぼって割り当てられる**ことで評価されます。⚠️ **ただ 1 つの例外は、Leader 専用の 1 回だけのボーナスです**（腕の届く範囲の輪が、対象を幾何的に覆う形に点を足すもの）。これは幾何だけで決まるので、学習には左右されません。⭐ **この作りの結果、形が良いかどうかの見込みは、価値関数の推定を通してしか得られず、学習がどれだけ進んだかに左右されます**。

# 第3章 提案手法: スケッチ起点の形態検証パイプライン（3.5〜3.12）

## 3.5 システム全体像

提案するシステムは、手描きのスケッチを入力にして、その形が狙ったタスクに向いているかの判定と、向いていなかったときの直す方向を出します。全体の作りを図 3.1 に示します。処理は 7 つの工程（M1〜M7）からなります。図では、これを 4 つのフェーズに分けて、上の段にフェーズ 1・2、下の段にフェーズ 3・4 を置いています。

![**図 3.1**: 提案するシステムの全体の作り。上の段は、スケッチから形のパラメータを取り出すまで（フェーズ 1・2）。下の段は、シミュレーション用のモデルを作って、評価と診断をするところ（フェーズ 3・4）です。黄色は人が与える入力、青は処理（M1〜M6）、紫のひし形は判定（M7）、緑は工程のあいだで受け渡すファイル、赤は診断の出力です。黒の矢印はデータの流れ、赤の矢印は診断の出力、赤の破線は、第1層の助言を機械的に当てはめてもう一度判定する閉ループです。{width=1.0}](figures/system_overview.pdf)

人が与える入力は、手描きのスケッチと、狙うタスクの定義です（図の黄色）。それぞれのフェーズがすることは次のとおりです。

- **フェーズ 1（入力と、絵を整える）**: M1 が、決まったプロンプト（関節の目印の決まり）のもとで、スケッチを、白い背景に 1 つの視点から描いた、CAD の画面を模した絵に描き直し、関節にマゼンタの球を描かせます（3.6 節）。
- **フェーズ 2（立体にして、リンクに切り分ける）**: M2 が、絵を色の付いた 1 個のメッシュにします（3.7 節）。M3 が、目印の色から関節を見つけてメッシュをリンクごとに切り分け（3.8 節）、M4 が、関節のあいだの距離と断面から形のパラメータを求めます（3.9 節）。
- **フェーズ 3（シミュレーション用のモデルを作る）**: M5 が、それぞれのリンクをカプセルで近似して、MuJoCo 互換の XML を出します（3.10 節）。
- **フェーズ 4（評価と、形の診断）**: XML は、まず M7 の第1層が幾何だけで判定します。目標に届かない形は学習に進めず、届くのに必要な拡大の倍率をつけて落とします。通った形は、M6 が Stackelberg PPO で形と制御を一緒に最適化し（3.11 節）、その結果を M7 の第2・3層が診断して報告します（3.12 節）。

M7 が M6 の前と後ろに分かれているのは、第1層は学習が要らず、第2・3層は学習の結果を読むからです。データは図の矢印に沿って一方通行で流れます。ただし第1層で落とされたときだけは、助言のとおりにリンクの長さを N 倍した XML を第1層に戻す閉ループがあります（図の破線、4.4.2 項）。

**どこまで自動かを、先に話しておきます。**M3 から先（関節の検出から、モデルの生成、学習の開始まで）は、1 本のシェルスクリプトで動く自動の処理です。**M1（絵を整える）と M2（立体を作る）は、外部の生成 AI のサービスに頼っています。**この研究では、その API で呼び出す経路も作りました（付録D）。なので、この章で「人の手を借りない」と言っている範囲は、**M3 から先の毎回同じ結果になる処理と、M6 の学習**です。生成物を手に入れる工程は入っていません。

設計の考え方は 3 つです。

1 つ目に、動く仕組みを取り出すのに、学習による推定を使いません。上流（M1）での入力の決まりと、下流（M3）での毎回同じ結果になる色の検出に置き換えます。生成モデルの出力の不確かさを、パイプラインの中で後から補うのではありません。入力をしばることで、構造の推定という、答えが 1 つに決まらない問題を避けます。

2 つ目に、M3〜M5 を、乱数も学習も使わない、毎回同じ結果になる処理にします。失敗したときに原因を突き止められて、同じ結果を再現できるようにするためです。

3 つ目に、M5 が、既存の co-design の枠組みと互換な MuJoCo 互換の XML を出すようにします。そうすれば、学習の仕組みの中のコードを書き換えずにつなげます。

## 3.6 M1: 画像整形と関節マーカー規約

入力のスケッチは、画像を生成する AI（Gemini）で、後ろの立体化と色の検出に向いた画像に描き直します（図 3.1 の M1）。描き直した画像は、白い背景の上に、腕を斜め 45 度の 1 つの視点から描いた、CAD ソフトの画面を模した絵です。寸法線や文字は入れず、複数の向きから見た図も描きません。視点を 1 つにするのは、立体化が 1 枚の画像から形を作るからです。寸法線と文字を禁止するのは、立体化がそれも形の一部として拾ってしまうからです。このとき、このシステムの中心である**関節の目印の決まり**を、決まったプロンプトとして課します。この決まりは、構造を推定することを生成モデルに任せるのではなく、**構造の境目をはっきり描くことを強制する**ものです。要点は 3 つです。

1. **関節のつなぎ目すべてに、純粋なマゼンタ（#FF00FF）の球を 1 個ずつ描かせる。**マゼンタは、ふつうの写真や工業製品にはめったに出てこない色合いなので、色で見分けやすくなります。
2. **リンクはそれぞれ鮮やかな 1 色で塗り分けさせ、グラデーションとマゼンタを使うのを禁止する。**
3. **関節の位置を場所として並べて書き（「台座と上腕のあいだ」など）、描いた後で球の数を自分で確かめさせる。**場所を並べて書かないと、先端に近い関節が機械の部品として描かれてしまい、目印が抜け落ちます。

こうすることで、M3 の関節の検出は、精度の保証が無い推定の問題から、しきい値つきの色合わせという、答えが決まる問題に変わります。プロンプトの全文は付録A に載せています（ゼロから生成する版の A.1 と、手描きのスケッチを整える版の A.2。4.5 節の、最初から最後まで通した実走 5 件は、すべて A.2 を使いました）。

リンクは「両端が平らな円柱」として指示します（端が丸いと関節の球とまぎらわしく、目印が省かれるからです）。

⚠️ **出力のばらつきをいちばん小さくする設定（サンプリングの温度 0。いちばん確からしい答えだけを選ぶ指定）にしても、出てきた絵が決まり（向き、寸法線などの禁止、比率を保つこと）を守っているとは限りません（5.3 節 (B)）。**腕が傾いて出力されると、関節が近い高さに並んでしまい、Z 座標を境目にした切り分けがうまくいかなくなります。そのため、M1 の出力は人が確かめてから次の工程へ渡します。

## 3.7 M2: 三次元形状生成

整えた画像は、image-to-3D のサービス（Tripo3D）で三次元のメッシュ（GLB 形式、Y 軸が上の座標系）に変えます（図 3.1 の M2）。API で、生成に使う乱数の初期値（ここからは「生成のシード」と呼びます）を固定して呼び出します。

**生成サービスは、出力するメッシュを囲む箱のいちばん長い辺を 1.0（= 1 m）にそろえます**（手元の GLB 4 件すべてで 1.0000 でした）。なので、絶対的な大きさは、入力の画像の画素数や添えた寸法には左右されず、**絵の中の比率だけで決まります。**

利用者が絶対的な大きさを数字で指定する手段はありません。必要なら、生成した後で全体に同じ倍率を掛けます（リンクどうしの比は保たれるので、形を見分けることには影響しません）。

## 3.8 M3: 関節検出とリンク分割

M3 は、GLB のメッシュから関節の位置を見つけて、メッシュをリンクごとに切り分けます（図 3.1 の M3）。手描きのスケッチ A1（4.5 節）で、途中の様子を図 3.2 に示します。

![**図 3.2**: M3 の途中の様子（手描きのスケッチ A1）。①〜③ は本文の 3 つの段階に対応します。{width=1.0}](figures/pipeline_m3.png)

まず、UV テクスチャの色を頂点に焼き込んで、頂点ごとに色を持たせます（図 3.2 ①）。

次に、目印の頂点を抜き出して、関節を求めます（図 3.2 ②）。探す色 $c_0$ と許す幅 $\tau$ に対して、色の各成分で $|c_i^{(k)} - c_0^{(k)}| \le \tau$ を満たす頂点を、目印の頂点とします。生成の途中で目印の色はもとの色からずれるので、$c_0$ と $\tau$ は固定せず、マゼンタの色合いの範囲（285〜345°）にある頂点のかたまりの中央値と広がりから、自動で合わせます。そのかたまりが無ければ、検出の失敗として止まります。抜き出した頂点を、**三次元で**つながったかたまりに分けて、それぞれの重心を関節にします。目印の頂点全体の 2 % に満たないかたまりは、色のにじみのノイズとして捨てます。つながりを判断する半径（全体の大きさに対して 0.02）と 2 % は、どちらも比率なので、大きさに左右されません（予備の実験にもとづく経験的な値です）。

最後に、関節の Z 座標（図 3.2 ③ の破線）を境目にして、各ポリゴンを重心の Z で振り分けます。境目のあいだにポリゴンが 1 つも無ければ、関節の位置がおかしいとして止まります（おかしいと分かった時点ですぐ止める、フェイルファスト）。切り分けた各部分は、リンクのローカルな座標へ平行移動して、STL として出力します。

## 3.9 M4: 形態パラメータ抽出

切り分けたそれぞれのリンクから、co-design の設計の値の初期値を求めます（図 3.1 の M4）。結果は topology.json に書き出します。

- **リンクの長さ** $L$: **関節と関節の距離**です（M3 が持っている関節の座標から求めます。先端のリンクは、最後の関節からいちばん遠い点まで）。
- **カプセルの半径** $r$: **骨の軸に垂直な断面**の、2 方向の幅の平均の半分です。

**どちらも OBB（向きを合わせた外接の直方体）を使いません。**OBB のいちばん長い辺は、切り分けた部分に入っている目印の球の半分を拾ってしまい、いつも長めに出ます。OBB の短い辺から半径を求める計算は、いちばん長い辺が骨の軸と一致していることが前提ですが、先端が太い形ではこの前提が成り立ちません。骨の軸は M3 の関節の座標として分かっているので、それを直接使います。

取り出した値が妥当かは、**カプセルが元のメッシュを覆えているか**で評価しました（「正しい半径」は、柄の太さとも先端の太さとも解釈できますが、覆えているかどうかは 1 通りに決まります）。手描きの入力 5 例・20 リンクで、カプセルの外に出る頂点の割合は平均 21.4 % でした。OBB の短い辺から求めた場合の 29.7 % より小さく、悪くなったリンクはありませんでした。

それでも残る覆いきれなさの主な原因は、傾いた腕を水平な面で切り分けていることです。切る面がリンクの軸に対して斜めになるので、先端の部分に関節より後ろ側が入り込み、半径も小さめに出ます。B1 の手先は頂点の 70.9 % が外に出ますが、はみ出しの量の中央値は 5〜10 mm です（まっすぐ立った A1 の手先は 8.9 %）。限界として 5.3 節に書きます。

関節が動く範囲とギア比の初期値は、スケッチの幾何からは 1 通りに決まらないので、決まった値（ギア比 100、動く範囲 ±90°）を使います。設計の値を探す範囲（ギア比の上限、リンクの長さを伸び縮みさせる幅）と、物理の値（リンクの密度、アクチュエータの回転子の慣性と速度の上限）は、co-design の側の設定で与えます。これらは実在の部材と実在のアクチュエータ（UR5e）から導きます（表 4.2）。

## 3.10 M5: シミュレーションモデル生成

topology.json は、MuJoCo 互換の XML に変換します（図 3.1 の M5）。各リンクをカプセルで近似し、子のリンクの `<body>` を親の中に入れ子にして、その位置を親の骨の長さのところに置きます（つまり親の先端に取り付けます）。関節（回転軸と動く範囲）とアクチュエータ（ギア比）を付けます。学習の側では、読み込むときに Choreonoid のモデルの形式（.body）に変換します。

形を長さの変わるグラフとして扱う Transformer の方策なので、3 関節のメッシュから作ったモデルは、**学習の仕組みのコードを変えずに**受け付けられました。⚠️ ただし、前の工程（M1〜M3）を 3 関節以外で実行した例は無く、**この論文が扱った形はすべて 3 関節です**。

関節の軸は、関節ごとに x・y・z のどれかの座標軸を割り当てます。決まった設定として、2 つのモードを用意しています。すべての関節をヨー軸（鉛直の軸まわり）にして、骨を X 軸の向きに並べる**平面モード**と、根元をヨー軸、その先をピッチ軸（水平の軸まわり）にして、骨を Z 軸の向きに積む**縦型モード**です。**この論文が報告する実験の大部分は平面モードです。**⚠️ **軸の割り当ては入力の形から推定するものではなく、利用者が与えます。**形から軸を推定するのは、これからの課題にします。

## 3.11 M6: co-design による評価・補正と判定

作ったモデルを最初の形にして、Stackelberg PPO による形態-制御 co-design を実行します（図 3.1 の M6）。

エピソードは 3 つの段階からなります。骨格を変える段階（このシステムでは飛ばします。つながり方はスケッチが決めるからです）、性質を変える段階（Leader が bone_offset・太さ・ギア比を編集します）、実行の段階（Follower が制御してタスクの報酬を得ます）です。Leader の目的には、Follower の実行の成績が引き継がれます。

そのため、学習が進むにつれて得られるのは、次の 2 つです。(i) 実行の成績の移り変わりが、**その形の流れのタスクのこなし具合の評価**になります。(ii) Leader による設計の値の更新が、**スケッチから来た初期値の修正**になります。判定に使うのは、学習曲線の順位です。要る学習量は 4.5.3 節で較正します。

## 3.12 M7: 形態診断

### 3.12.1 判定から診断へ

M6 が返すのは、「このスケッチはこのタスクに向いているか」という順位か点数です。でも、想定している利用者はロボット設計の専門知識を持っていないので、「向いていません」とだけ言われても、次に何をすればいいか判断できません。**向いていない原因と直す方向を、言葉にして返す**必要があります。

M7 は追加の学習を必要とせず、M6 が作るもの（最初の XML、収束した形のチェックポイント、動きの記録）だけを入力にします。診断に生成 AI は使わず、しきい値と比べて選んだ決まった文に、測った値を差し込んで返します。

### 3.12.2 三層構造

M7 は、計算の手間が違う 3 つの層からなります。上の層ほど、安くて確実です。第1層が使うリンクの長さと目標の位置は、学習の結果にも乱数の種にも左右されません。一方、第2層・第3層が使う学習の結果は、乱数の種や、どこで打ち切ったかに左右されます。そこで、「この形ではタスクをこなせません」という総合の判定を出すのは第1層だけにして、第2層・第3層は観察の報告にとどめます。図 3.1 では、学習の前に置く第1層と、学習の後に置く第2・3層を、2 つのひし形として描いています。

**第1層（幾何の診断・学習なし）**: 最初の XML だけを解析して、腕が届く最大の距離と関節の動く範囲のもとで届く範囲を、目標や対象の位置と比べます。かかるのは数秒以内で、シミュレータを立ち上げる必要も、学習もありません。見つけるのは 3 種類です。(i) 目標が届く最大の距離の外にあって届かない。(ii) 止まった姿勢で先端が対象にめり込む。(iii) 関節の軸の向きが、タスクの想定と合っていない。

(i) のときは、**判定をひっくり返すのに必要な最小の拡大の倍率**を数字で返します（例:「腕全体を 1.99 倍に伸ばしてください」）。倍率は切り上げます（四捨五入だと、示した値が必要な量より小さくなって、従っても判定がひっくり返らないことがあります）。最小の変更だけを返すのは、反実仮想説明と実行できるリコースの条件に合っています（2.4 節）。

届く最大の距離の計算には、前提が 2 つあります。

1 つは、リンクの長さの合計が届く距離に等しくなるのは、それぞれの関節が 1 つ前のリンクの先端にあるときだけだ、ということです。なので、関節の位置をつないで求めた届く距離と食い違う XML は、つじつまが合わないとして却下します。

もう 1 つは、長さの合計がそのまま水平に届く半径になるのは、平面の腕だけだ、ということです。平面にとどまらない腕では、回る軸と平行なリンクを除いた、水平に届く限界で判定します。

関節が動く範囲による届くかどうかの判定は、動く範囲を格子状に調べて行い、格子の粗さから来るすき間を、順運動学のリプシッツ定数（入力が少し変わったときに出力がどれだけ変わりうるかの上限）で見積もって、**「届かない」という側だけが確実になる**ように作っています。リンクの長さが最適化の対象に入っている設定では、学習の途中で届く最大の距離が伸びうるので、第1層は「届かない」という否定の判定だけをします。

**第2層（収束した形の診断）**: co-design が収束させた設計の値を読んで、探す範囲の端に張り付いていないかを見つけます。ギア比が上限に張り付いていれば力が足りない、下限に張り付いていれば省エネの方向へ収束した、という意味です。

ただし、後者の読み方はタスクによります。到達のタスクでは、弱くて細い設計が、確率的な方策のもとで止まる精度を保つ、正常な最適な答えでもあります。実際、届く形と届かない形が同じ署名（同じ張り付き方）を見せました（4.3.3.1 節）。なので、この署名は、到達のタスクでは警告にとどめます。強い力が有利なはずの押しのタスクでだけ、向いていない兆しとして報告します。

**第3層（動き方の診断）**: 収束した方策を、ばらつきなしで 1 エピソード実行して、その軌跡から戦略を分類します。押しのタスクでは「一撃で吹き飛ばす」「穏やかに押す」「触れられていない」、到達のタスクでは「目標で止まる」「ずれて止まる」「届かない」に分けます。

あわせて、それぞれの関節が、動く範囲のうち実際に何割を使ったかを報告します。10 % を下回る関節については、固定すれば重さと制御の自由度を減らせるかもしれない、と指摘します。第1層の「腕を N 倍に伸ばせ」とは逆の、**設計を減らす向きの指摘**です。

利用者の意図と違う戦略に収束しているとき（例: 狙った場所に止めたいのに、吹き飛ばしている）は、形ではなく**タスクの選び方のまちがい**として、別のタスクを示します。

### 3.12.3 診断の妥当性検証の位置づけ

3 つの層の診断が、実際に測った順位と合うかどうかは、診断の設計の話ではなく、実験の話です。確かめた条件と結果は 4.4.1 節に示します。この節から後では、診断の設計の性質を話します。

### 3.12.4 第3層の閾値は判定規則ではなく候補生成器である

第3層のしきい値（動く範囲の 10 %）は、実験で較正していません（5.3 節 (D)）。**ただし、しきい値が決めるのは「固定してみる価値のある関節」であって、「固定すべき関節」ではありません。**

採るかどうかは、助言どおりに固定した形を学習させて、**元の形と成績の範囲（帯）が重なるかどうか**で決めます。この基準は、この研究が形の順位づけ全般に使っているものと同じです（4.1.4 項）。

### 3.12.5 診断の範囲外とした事項

第1層の「腕全体を N 倍以上に伸ばしてください」は、判定をひっくり返すのに必要な最小の変更を、利用者が動かせる変数の上で示した反実仮想説明です。**第2層・第3層では、同じような出力を作れていません。**収束した設計や動き方から「何が起きたか」は報告できますが、「設計をどう変えればその結果が変わるか」は、学習をやり直さないと分かりません。第1層でそれができるのは、幾何が支配している層では、必要な変更が運動学から計算で直接求まるからです。

また、意図から報酬の関数を自動で設計する機能は、範囲の外にしました（報酬を複雑にすると、探すための手がかりが消えることがあるからです）。
