# 前提: Stackelberg PPO による形態と制御の同時最適化（3.1〜3.4）

## 3.1 問題設定: 階層ゲームとしての同時最適化

Stackelberg PPO は、形と制御を一緒に最適化する問題を、Stackelberg ゲームの一種として定式化します。Stackelberg ゲームは、先に決める側（Leader）が、後から合わせる側（Follower）がどう応じるかを見越して決める、上下関係のあるゲームです。

Leader は形を編集する方策 $\pi^L(\cdot \mid s^L_t; \theta^L)$ です。Follower は、決まった形のもとで制御をする方策 $\pi^F(\cdot \mid s^F_t; s^L_T, \theta^F)$ です。

$\pi(\cdot \mid \ldots)$ は、縦棒の右に書いた条件のもとで、それぞれの行動をとる確率を返す関数です。セミコロンの右は、その方策を使っているあいだ固定しておく量です。記号の読み方と意味を、表 3.1 にまとめます。つまり Follower は、形 $s^L_T$ と重み $\theta^F$ を固定したうえで、いまの関節の状態と、手先から見た箱の位置 $s^F_t$ を見て、どう動かすかの確率を返します。実装では、決まった形の設計パラメータが Follower の観測にも入っていて、これで Follower は「その形のもとで」動かすことになります。

**表 3.1**: 3.1 節の記号

| 記号 | 読み | 意味 |
|---|---|---|
| $\pi$ | パイ | 方策。状態を入れると、それぞれの行動をとる確率を返す関数（円周率ではない） |
| 上付きの $L$・$F$ | エル・エフ | Leader 用か Follower 用かの名札（べき乗ではない） |
| $(\cdot \mid \ldots)$ | 点、ギブン … | 条件付き確率の書き方。縦棒の右が与えられたもの（条件）、左の点が確率を割り当てる行動の空欄 |
| $s^L_t$ | エス・エル・ティー | 時刻 $t$ の Leader の状態。いまの形（各リンクの設計パラメータ） |
| $s^L_T$ | エス・エル・大文字ティー | Leader が最後の時刻 $T$ に決めた形 |
| $s^F_t$ | エス・エフ・ティー | 時刻 $t$ の Follower の状態（各関節の角度と角速度、手先から見た箱の位置） |
| $\theta^L$・$\theta^F$ | シータ・エル、シータ・エフ | それぞれの方策ネットワークの重み（学習で更新される数の集まり） |
| $T$ | 大文字ティー | Leader が形を決め終える時刻（形を編集するフェーズの長さ） |
| $a^L_t$・$a^F_t$ | エー・エル・ティー、エー・エフ・ティー | 時刻 $t$ の、形を編集する行動と、制御の行動 |
| $R^L$・$R^F$ | アール・エル、アール・エフ | Leader と Follower がそれぞれ受け取る報酬 |
| $\gamma$ | ガンマ | 割引率（0 より大きく 1 より小さい）。先の報酬を、いまの価値に換算する係数 |
| $J^L$・$J^F$ | ジェイ・エル、ジェイ・エフ | Leader と Follower の目的関数（割り引いた報酬の和の期待値 $\mathbb{E}$） |
| セミコロン（;） | — | ここから右は確率変数ではなく、方策を使うあいだ固定しておく量、という区切り |

1 回の試行（エピソード）は、2 つの段階に分かれます。前半（$t = 0, \dots, T-1$）では、Leader が形を編集する行動 $a^L_t$ をとって、最後の形 $s^L_T$ を決め、後半（$t \ge T$）では、Follower がその形 $s^L_T$ を前提にした制御の行動 $a^F_t$ をとって、タスクの報酬 $R^F$ を受け取ります。

2 人の目的は、次の式で表されます。

$$J^F(\theta^L, \theta^F) = \mathbb{E}\left[\sum_{t=T}^{\infty} \gamma^{t-T} R^F(s^F_t, a^F_t; s^L_T)\right]$$

$$J^L(\theta^L, \theta^F) = \mathbb{E}\left[\sum_{t=0}^{T-1} \gamma^t R^L(s^L_t, a^L_t) + \sum_{t=T}^{\infty} \gamma^{t-T} R^F(s^F_t, a^F_t; s^L_T)\right]$$

この研究にとって大事なのは、$J^L$ の 2 つ目の項です。**Leader の評価には、自分は何も編集しない実行の段階で Follower が稼いだ成績（リターン）が、そのまま引き継がれます。**つまり形は、運動学の理屈の上でどうかではなく、**その形を制御の方策が実際にどれだけ使いこなせたか**で評価されます。この性質が、同時最適化を形の設計の判定器として使う、この研究の根拠です。

Leader の更新には、Follower の最適な応じ方がどれだけ変わるかの感度を織り込んだ「Stackelberg 勾配」を使います。この勾配は Follower 側の損失の Hessian（2 階微分）を含んでいて、共役勾配法による陰関数の微分で近似し、正則化の係数 $\lambda$ を変えると、Stackelberg 勾配（$\lambda \to 0$）と、ふつうの方策勾配（$\lambda \to \infty$）のあいだをなめらかにつなげます。制御の方策と形の方策のどちらの更新にも使うのは、PPO です。詳しくは元の論文にゆずります。

## 3.2 役割別の報酬設計に関する原論文の規定

元の論文の付録は、報酬の項を Leader と Follower に選んで割り当てる「役割ごとの報酬設計」を、はっきり認めています。たとえば、材料のコストや複雑さのペナルティを Leader の更新だけに使って、制御の学習には口を出させない、という使い方です。

大事なのはその境目です。**Leader 専用の報酬の項を $J^L$ に足すのは、枠組みの想定の範囲内です。**でも、$J^L$ の 2 つ目の項（Follower の成績を引き継ぐ部分）を別の量に**置き換えて**はいけません。Leader が Follower の実際の応じ方を見なくなって、Stackelberg の構造の前提が壊れるからです。この研究の報酬の設計（4.1.2 項）は、この決まりに従っています。

## 3.3 方策のアーキテクチャ

方策のネットワークは、形を木の構造（ボディグラフ）として扱う Transformer を土台にした作りで、グラフの構造を意識した位置の符号化を使います。それぞれのボディ（部品）がノードとして観測（深さ、設計のパラメータ、シミュレーションの状態）を持ち、行動（形の編集や制御）もノードごとに出します。

この作りのおかげで、実際の使い勝手として、**リンクの数が違う形を、同じネットワークがそのまま扱えます。**この研究で、生成したメッシュから作った 3 関節の腕が、コードを書き換えずに受け付けられたのは、この性質のためです（4.3.1 項）。

## 3.4 本研究で用いる実装上の構成

この研究の実験は、上の枠組みに次の設定を加えて行います（どれも元の論文の枠組みの範囲内の設定です）。

- **形の段階の分け方**: 実装では、Leader の段階がさらに「骨格を変える」（リンクを足したり消したりする）と「性質を変える」（リンクの長さやギア比などの連続的な値を編集する）に分かれています。この研究では、つながり方をスケッチから来た構造に固定するので、骨格を変える段階は止めます。骨格を変える段階は 1 ステップで素通りし、性質を変える編集を 5 回行います。
- **設計のパラメータの変換**: 性質を変える行動は、$[-1, 1]$ に正規化した空間で行い、正弦関数を使った変換で、実際のパラメータを探す範囲に直します。探す範囲は表 4.1・表 4.2 のとおりです。1 回の編集の歩幅は係数で決まります。これは探す範囲の制限ではなく、更新の刻み幅です。
- ⭐ **設計の段階の報酬**: 骨格を変える段階にも、性質を変える段階にも、**すぐにもらえる報酬はあげません**（$r = 0$）。なので、設計の行動は $J^L$ の第2項（3.1 節）だけで評価され、⭐ **形が良いかどうかの見込みは、価値関数の推定を通してしか得られず、学習がどれだけ進んだかに左右されます**。

# 第3章 提案手法: スケッチ起点の形態検証パイプライン（3.5〜3.12）

## 3.5 システム全体像

提案するシステムは、手描きのスケッチを入力にして、その形が狙ったタスクに向いているかの判定と、向いていなかったときの直す方向を出します。全体の作りを図 3.1 に示します。処理は 7 つの工程（M1〜M7）からなります。図では、これを 4 つのフェーズに分けています。

![**図 3.1**: 提案するシステムの全体の作り。上から順にフェーズ 1〜4 です。画像は、手描きのスケッチ A1 での各工程の出力で、図 3.2〜3.5 と同じものです。色と矢印の意味は、図の下の凡例に示します。{width=0.62}](figures/system_overview.pdf)

それぞれのフェーズの工程と、入るものと出るものを表 3.2 に示します。

**表 3.2**: フェーズと工程

| フェーズ | 工程 | 入るもの → 出るもの | 節 |
|---|---|---|---|
| 1. 入力と、絵を整える | M1 | 手描きのスケッチ → 白い背景に 1 つの視点から描き直し、関節にマゼンタの球を描いた絵 | 3.6 |
| 2. 立体にして、リンクに切り分ける | M2・M3・M4 | 絵 → 色の付いた 1 個のメッシュ → リンクごとのメッシュと関節の位置 → 形のパラメータ | 3.7〜3.9 |
| 3. シミュレーション用のモデルを作る | M5 | 形のパラメータ → それぞれのリンクをカプセルで近似した MuJoCo 互換の XML | 3.10 |
| 4. 評価と、形の診断 | M7 第1層 → M6 → M7 第2・3層 | XML → 判定と助言。第1層で落とした形は学習に進めず、届くのに必要な拡大の倍率を示す | 3.11・3.12 |

M7 が M6 の前と後ろに分かれているのは、第1層は学習が要らず、第2・3層は学習の結果を読むからです。データは図の矢印に沿って一方通行で流れます。ただし第1層で落とされたときだけは、助言のとおりにリンクの長さを N 倍した XML を第1層に戻す閉ループがあります（図の破線、4.5.2 項）。

**M1（絵を整える）と M2（立体を作る）は、外部の生成 AI のサービスを API で呼び出します**（使ったサービスと版は付録D）。M3 から先（関節の検出から、モデルの生成、学習の開始まで）は、1 本のシェルスクリプトで動く自動の処理です。

設計の考え方は 3 つです。

1 つ目に、関節の位置を形から推定しません。上流（M1）で描かせた目印を、下流（M3）で色で見つけて求めます。生成モデルの出力の不確かさを、パイプラインの中で後から補うのではありません。入力をしばることで、関節の位置を、毎回同じ結果になる処理で決めます。

2 つ目に、M3〜M5 を、乱数も学習も使わない、毎回同じ結果になる処理にします。失敗したときに原因を突き止められて、同じ結果を再現できるようにするためです。

3 つ目に、M5 が、既存の同時最適化の枠組みと互換な MuJoCo 互換の XML を出すようにします。そうすれば、学習の仕組みの中のコードを書き換えずにつなげます。

## 3.6 M1: 画像整形と関節マーカー規約

3.6〜3.10 節では、手描きのスケッチ A1（4.6.1 項）を例にして、各工程の途中の様子を図 3.2〜3.5 に示します。

![**図 3.2**: M1・M2 の入力と出力（手描きのスケッチ A1）。① 手描きのスケッチ、② M1 が描き直した絵、③ M2 が作った三次元のメッシュを横から見たもの。{width=1.0}](figures/pipeline_m12_paper.png)

入力のスケッチは、画像を生成する AI（Gemini）で、後ろの立体化と色の検出に向いた画像に描き直します（図 3.1 の M1、図 3.2 ①→②）。描き直した絵は、1 つの視点から CAD ソフトの画面を模して描き、寸法線や文字、複数の向きから見た図は入れません。視点を 1 つにするのは、立体化が 1 枚の画像から形を作るからです。寸法線と文字を禁止するのは、立体化がそれも形の一部として拾ってしまうからです。このとき、このシステムの中心である**関節の目印の決まり**を、決まったプロンプトとして課します。この決まりは、構造を推定することを生成モデルに任せるのではなく、**構造の境目をはっきり描くことを強制する**ものです。要点は 3 つです。

1. **関節のつなぎ目すべてに、純粋なマゼンタ（#FF00FF）の球を 1 個ずつ描かせる。**マゼンタは、ふつうの写真や工業製品にはめったに出てこない色合いなので、色で見分けやすくなります。
2. **リンクはそれぞれ鮮やかな 1 色で塗り分けさせ、グラデーションとマゼンタを使うのを禁止する。**
3. **関節の位置を場所として並べて書き（「台座と上腕のあいだ」など）、描いた後で球の数を自分で確かめさせる。**場所を並べて書かないと、先端に近い関節が機械の部品として描かれてしまい、目印が抜け落ちます。

こうすることで、M3 の関節の検出は、精度の保証が無い推定の問題から、しきい値つきの色合わせという、答えが決まる問題に変わります。プロンプトの全文は付録A に載せています。

リンクは「両端が平らな円柱」として指示します（端が丸いと関節の球とまぎらわしく、目印が省かれるからです）。

⚠️ **出力のばらつきをいちばん小さくする設定（サンプリングの温度 0。いちばん確からしい答えだけを選ぶ指定）にしても、目印の数とリンクの長さの比が決まりどおりになるとは限りません。**また、立体にする工程（M2）で腕が寝た姿勢で作られると、関節が近い高さに並んでしまい、Z 座標を境目にした切り分け（3.8 節）がうまくいきません。そこで、M2 の出力で目印の数と関節の高さの広がりを調べ、どちらかが基準に届かなければ M3 へ進めません。リンクの長さの比が保たれることは手描きの 5 例で確かめましたが（表 4.5）、出力 1 つ 1 つに対しては調べていません。

## 3.7 M2: 三次元形状生成

整えた画像は、image-to-3D のサービス（Tripo3D）で三次元のメッシュ（GLB 形式、Y 軸が上の座標系）に変えます（図 3.1 の M2、図 3.2 ③）。API で、生成に使う乱数の初期値（ここからは「生成のシード」と呼びます）を固定して呼び出します。

**生成サービスは、出力するメッシュを囲む箱のいちばん長い辺を 1.0（= 1 m）にそろえます**（手元の GLB 4 件すべてで 1.0000 でした）。なので、絶対的な大きさは、入力の画像の画素数や添えた寸法には左右されず、**絵の中の比率だけで決まります。**

利用者が絶対的な大きさを数字で指定する手段はありません。必要なら、生成した後で全体に同じ倍率を掛けます。

## 3.8 M3: 関節検出とリンク分割

M3 は、GLB のメッシュから関節の位置を見つけて、メッシュをリンクごとに切り分けます（図 3.1 の M3、図 3.3）。

![**図 3.3**: M3 の途中の様子（手描きのスケッチ A1）。①〜③ は本文の 3 つの段階に対応します。{width=1.0}](figures/pipeline_m3_paper.png)

まず、UV テクスチャの色を頂点に焼き込んで、頂点ごとに色を持たせます（図 3.3 ①）。

次に、目印の頂点を抜き出して、関節を求めます（図 3.3 ②）。探す色 $c_0$ と許す幅 $\tau$ に対して、色の各成分で $|c_i^{(k)} - c_0^{(k)}| \le \tau$ を満たす頂点を、目印の頂点とします。生成の途中で目印の色はもとの色からずれるので、$c_0$ と $\tau$ は固定せず、マゼンタの色合いの範囲（285〜345°）にある頂点のかたまりの中央値と広がりから、自動で合わせます。そのかたまりが無ければ、検出の失敗として止まります。抜き出した頂点を、**三次元で**つながったかたまりに分けて（つながりを判断する半径は、全体の大きさの 0.02 倍）、それぞれの重心を関節にします。目印の頂点全体の 2 % に満たないかたまりは、色のにじみのノイズとして捨てます。

最後に、関節の Z 座標（図 3.3 ③ の破線）を境目にして、各ポリゴンを重心の Z で振り分けて、リンクごとの STL にします。境目のあいだにポリゴンが 1 つも無ければ、関節の位置がおかしいとして止まります。

## 3.9 M4: 形態パラメータ抽出

切り分けたそれぞれのリンクから、同時最適化の設計の値の初期値を求め、形のつながりと初期値をまとめた JSON ファイル（このあと topology.json と呼びます）を作ります（図 3.1 の M4）。topology.json は、リンクごとに、名前と親のリンク、関節（種類・軸・動く範囲）、リンクの長さ、カプセルの半径、ギア比を持ちます。A1 での結果を図 3.4 に示します。

![**図 3.4**: M4 で取り出した結果（手描きのスケッチ A1）。各リンクの頂点を、骨の軸に沿った距離（縦）と骨からの距離（横）で描いています。破線が骨の軸、▲がそのリンクの関節、黒い線が取り出した長さと半径のカプセルです。{width=1.0}](figures/pipeline_m4_paper.png)

骨の軸は M3 の関節の座標から決まるので、長さと半径はその軸に沿って測ります。

- **リンクの長さ** $L$: **関節と関節の距離**です（M3 が持っている関節の座標から求めます。先端のリンクは、最後の関節からいちばん遠い点まで。図 3.4 の破線）。
- **カプセルの半径** $r$: **骨の軸に垂直な断面**の、2 方向の幅の平均の半分です（図 3.4 の黒い線の幅）。

半径を断面の幅の平均から求めるので、台座のように断面の幅がそろっていないリンクでは、カプセルはメッシュの一部を覆いません。また、先端のリンクの長さは最後の関節からいちばん遠い点までなので、カプセルの端の半球は、メッシュの先より外へ出ます（図 3.4 の右端）。

関節が動く範囲とギア比の初期値は、スケッチの幾何からは 1 通りに決まらないので、決まった値（ギア比 100、動く範囲 ±90°）を使います。設計の値を探す範囲（ギア比の上限、リンクの長さを伸び縮みさせる幅）と、物理の値（リンクの密度、アクチュエータの回転子の慣性と速度の上限）は、同時最適化の側の設定で与えます（表 4.2）。

## 3.10 M5: シミュレーションモデル生成

topology.json は、MuJoCo 互換の XML に変換します（図 3.1 の M5）。各リンクをカプセルで近似し、子を親の先端に取り付ける入れ子の形にして、関節とアクチュエータ（ギア比）を付けます（図 3.5 の右）。学習の側では、読み込むときに Choreonoid のモデルの形式（.body）に変換します。

⚠️ 学習の仕組みはリンクの数が違う形も扱えますが（第3章前段 3.3 節）、前の工程（M1〜M3）を 3 関節以外で実行した例は無く、**M3 が見つけた関節はどれも 3 つです**。最初の姿勢はすべての関節を 0° にし、スケッチに描いた腕の角度は使いません。

関節の軸は、関節ごとに x・y・z のどれかの座標軸を割り当てます。決まった設定として、2 つのモードを用意しています。すべての関節をヨー軸（鉛直の軸まわり）にして、骨を X 軸の向きに並べる**平面モード**と、根元をヨー軸、その先をピッチ軸（水平の軸まわり）にする**縦型モード**（図 3.5 の左）です。縦型モードでは、根元に回る関節を 1 つ足して 4 関節にします。**この論文が報告する実験の大部分は平面モードです。**⚠️ **軸の割り当ては入力の形から推定するものではなく、利用者が与えます。**形から軸を推定するのは、これからの課題にします。

## 3.11 M6: 同時最適化による評価・補正と判定

作ったモデルを最初の形にして、Stackelberg PPO による形態と制御の同時最適化を実行します（図 3.1 の M6。枠組みは第3章前段、Leader が編集する量は表 4.1）。

学習が進むにつれて得られるのは、次の 2 つです。(i) 実行の成績の移り変わりが、**その形の流れのタスクのこなし具合の評価**になります。(ii) Leader による設計の値の更新が、**スケッチから来た初期値の修正**になります。判定に使うのは、学習曲線の順位です。要る学習量は 4.6.3 節で較正します。

## 3.12 M7: 形態診断

M7 は、向いていない原因と直す方向を、言葉にして返します。追加の学習は要らず、M6 が作るものだけを入力にします。診断は、しきい値と比べて選んだ決まった文に、測った値を差し込んで返します。

### 3.12.1 三層構造

M7 は 3 つの層からなります（表 3.3）。第1層が使うリンクの長さと目標の位置は、学習の結果にも乱数の種にも左右されません。一方、第2層・第3層が使う学習の結果は、乱数の種や、どこで打ち切ったかに左右されます。そこで、「この形ではタスクをこなせません」という総合の判定を出すのは第1層だけにして、第2層・第3層は観察の報告にとどめます。図 3.1 の 2 つのひし形が、学習の前の第1層と、学習の後の第2・3層です。

**表 3.3**: 診断の 3 つの層

| 層 | いつ・入力 | 見つけるもの | 返すもの |
|---|---|---|---|
| 第1層（幾何）・判定 | 学習の前・最初の XML（数秒） | 目標が届く最大の距離の外にある／止まった姿勢で先端が対象にめり込む／関節の軸の向きがタスクの想定と合わない | 判定をひっくり返すのに必要な最小の拡大の倍率（例:「腕全体を 1.99 倍に伸ばしてください」） |
| 第2層（収束した形）・報告 | 学習の後・収束した形 | ギア比が、探す範囲の上限か下限に張り付いているか | 上限なら力が足りない。下限は押しのタスクでだけ、向いていない兆し |
| 第3層（動き方）・報告 | 学習の後・動きの記録（1 エピソード） | 戦略（押し: 一撃で吹き飛ばす／穏やかに押す／触れられていない。到達: 目標で止まる／ずれて止まる／届かない）と、それぞれの関節が動く範囲のうち何割を使ったか | 使用率 10 % 未満の関節を固定する候補。意図と違う戦略なら別のタスク |

第1層が示す倍率 $N$ は、次の式で求めます。

$$N = \left\lceil \frac{d}{L} \right\rceil_{0.01}$$

$L$ は腕の届く半径、$\lceil \cdot \rceil_{0.01}$ は 0.01 刻みの切り上げです。$d$ は、到達のタスクでは根元から目標までの水平の距離です。押しのタスクでは、対象の置かれる範囲の一番奥にある対象に先端が触れる距離 $d_{\mathrm{touch}}$ に、押し込む距離 $d_{\mathrm{push}} = 0.1$ m を足した $d_{\mathrm{touch}} + d_{\mathrm{push}}$ です。$d_{\mathrm{push}}$ を足すのは、触れる距離だけだと、一番奥の対象に触れても押し込めないからです（4.5.4 項）。この値は、押しのタスクができたかを決める対象の動いた量（4.5.4 項）と同じにしています。切り上げるのは、四捨五入だと、示した値が必要な量より小さくなって、従っても判定がひっくり返らないことがあるからです。最小の変更だけを返すのは、反実仮想説明と実行できるリコースの条件に合っています（2.4 節）。リンクの長さの合計が届く半径に等しいのは、それぞれの関節が 1 つ前のリンクの先端にあって、しかも平面の腕のときだけです。なので、前者が破れている XML は却下し、平面にとどまらない腕では、回る軸と平行なリンクを除いた水平の限界で判定します。関節の動く範囲まで考えた届くかどうかの判定は、格子の粗さから来るすき間を順運動学のリプシッツ定数で見積もって、**「届かない」という側だけが確実になる**ように作っています。学習の途中でリンクの長さが伸びうる設定もあるので、第1層は「届かない」という否定の判定だけをします。

第2層で、下限への張り付きを押しのタスクに限るのは、到達のタスクでは、目標に届いた形でも、ギア比が下限に張り付くからです（4.4.3.1 節）。

### 3.12.2 第3層のしきい値の位置づけ

第3層のしきい値（動く範囲の 10 %）は、実験で較正していません（5.3 節の 5）。**このしきい値が決めるのは「固定してみる価値のある関節」であって、「固定すべき関節」ではありません。**採るかどうかは、助言どおりに固定した形を学習させて、元の形と成績の範囲が重なるかどうかで決めます（4.2.2 項の基準。結果は 4.5.5 項）。なので、しきい値が不正確でも、まちがった助言は採られません。ただし、本当に効く助言を見落とす可能性は残ります。この手法が数秒で返すのは候補であって、採用するという結論ではありません。
