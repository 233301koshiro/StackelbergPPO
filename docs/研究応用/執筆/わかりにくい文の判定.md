# わかりにくい文の判定 — 論文らしい硬さと、読めない文の境目

> 2026-10-19 作成（ユーザー「全体的にふんわりとしか理解できない。自分の研究だから、自分が知っている事実に文章を当てはめて理解している感じ。論文らしいかしこまった書き方と、よくわからない文章の境目を言語化したい」）。
> 修論の文章を読むとき・直すときの基準。文の読みやすさの機械的な検査（yomiyasu の lint）は [セカンドオピニオン.md](../../リポジトリ説明/セカンドオピニオン.md) の C。lint はこの md の基準を見ない。

## 1. 二つは別の軸

| 軸 | 何の問題か | 例 |
|---|---|---|
| **論文らしさ（硬さ）** | 語の選び方。である調・正式な漢語・名詞化（〜の実施） | 「内包されていない」「先験的には決定できない」 |
| **わかりにくさ** | 読み手が文から中身を取り出せるか | 「問題群の分析と是正は…設計知見を構成する」 |

**硬くても、「何が・何に・どうした・その結果どうなる」が文から一通りに取り出せれば、わかる文である。**
わかりにくい文は、取り出そうとすると**読み手が自分の知識で穴を埋めないといけない**文である。
⚠️ 書いた本人は穴を自動で埋めてしまうので、自分ではわかりにくさに気づけない（「自分の研究だから、知っている事実に当てはめて理解している」状態）。

## 2. 判定の 4 つのテスト

| テスト | やり方 | わかりにくい文の兆候 |
|---|---|---|
| **1. 具体物に置き換える** | 抽象的な名詞（問題群・関係・知見・情報）を、この研究の具体物（どの現象・どの値・どのリンク）に置き換える | 置き換え先が本文のどこにも無い（書き手の頭の中にしかない） |
| **2. 主語と動詞を取り出す** | 文から「何が」「どうする」の 2 語を抜く | 主語が抽象名詞で、動詞が「構成する・寄与する・担う・変質する」など、何が起きたか見えない語 |
| **3. 前のページだけで答える** | その文より前に書いてあることだけで「つまり何？」に答える | 後の章か書き手の記憶が要る。定義の無い用語・指す先の無い「これ」「この〜」 |
| **4. 反対を言ってみる** | 文を否定したら何が変わるか考える | 反対が想像できない（否定しても何も変わらない）文は中身が薄い |

## 3. 直し方の型（硬さは保つ）

1. **抽象名詞の直後に、具体物を括弧か「例えば」で 1 つ添える**。
   良い例（第1章 1.2）: 「可動構造情報（リンクの分割境界、関節座標、回転軸ベクトル等）」
2. **抽象名詞の主語を、動作主と動作に開く**（「問題群の分析と是正は」→「移植で生じた〜を直すことは」）。
3. **「構成する・寄与する・担う」を、具体的な結果を言う動詞に替える**（「設計知見を構成する」→「別の実験系へ移す人が同じ問題を避ける手がかりになる」）。
4. **指示語（これ・この〜）は、指す先が直前の文にあるときだけ使う**。無ければ名詞で言い直す。

5. **「すなわち／つまり」の重ね言いを疑う**（2026-10-20、ユーザー指摘）。すでに意味が通じる語の直後に言い換えを重ね、その言い換えが**まだ説明していない概念**を持ち込むと、かえって分かりにくい。実例: 「第二は判定に要する学習量、すなわちどれだけ学習すれば候補の順位が定まるかである」（「候補の順位」が第1章で初出）。判定: (a) 言い換えを消しても通じる、かつ (b) 言い換えに初出の概念がある → 消す。抽象的な語を具体に開く言い換え（「妥当性、すなわちタスクの要求に応じて形態を識別する能力」）は逆向きなので残す。

6. **別の分野から借りた用語は、どの分野の何かを 1 文で言う**（2026-10-20、ユーザー指摘「概念設計」）。読み手の分野で別の意味を持つ語（概念設計はデータベースにもある）や、読み手の分野に無い語は、初出で「〇〇の分野では、△△の段階を□□と呼ぶ」の形で定義する。判定: 読み手の分野（ロボット・強化学習）の人がその語を見て、別の意味に取りうるか、意味が浮かばないか。
7. **「〜だけを変えた」と書くなら、何をそろえたかと、何が動きうるかを先に言う**（2026-10-20、ユーザー指摘）。読み手は実験にどんな変数があるかを知らないので、「タスクだけ」と言われても、他に何が変わりえたのかが分からない。そろえたもの（入力の形・物理・学習の条件）と、最適化が動かすもの（ギア比・太さ・長さ）を 1 文ずつ添える。⚠️ 変数を定義した節（4.1 など）より前に出る文、つまり要旨・第1章・各章の冒頭で特に要る。
8. **程度の語（中くらい・大きい・短い）には、何の軸の程度かを付ける**（2026-10-20、ユーザー指摘「中くらいの形」）。形は長さ・太さなど複数の軸を持つので、「中くらいの形」ではどの軸か決まらない。「中くらいの長さの腕」「1.1 倍」のように軸か数を言う。並べる語の軸もそろえる（「中くらいの形と長い腕」は大きさと長さが混ざっている）。
9. **たとえの動詞を、実際の操作の動詞に替える**（2026-10-20、ユーザー指摘「翻訳した」）。「翻訳する」は言語の操作なので、数値から助言を作る操作には合わない。何を入力に何を出したかで言う（「解析して導出した」「〜として提示する」）。同じ型: 「橋渡しする」「つなぐ」「読み解く」も、何をしたかが見えないときは替える。3 の「構成する・担う」と同じ仲間で、3 は動詞が抽象的すぎる型、9 は動詞が別の領域の具体物を指してしまう型。
10. **訳語の定まっていない外来の術語を、日常語として別の意味を持つ語に直訳しない**（2026-10-20、ユーザー指摘「実行可能な救済」）。recourse を辞書どおり「救済」とすると、困っている人を助ける意味に読めて学術の語に見えない。その分野の日本語文献が使う表記（ここでは「リコース」。情報処理学会の論文に「アルゴリズミック・リコース」）にし、原語を添えて 1 文で定義する（6 と組み合わせる）。判定: 訳語だけを見た人が、日常の意味で読んでしまうか。
11. **複数の工程・対象をまとめて性質を言うときは、一つずつ確かめる**（2026-10-20、ユーザー指摘「M1 と M2 は確率的にばらつく」）。性質の違うものをひとまとめにすると、成り立たない側について誤りになる（M2 は seed を固定すれば後段が使う量まで一致する。系譜 9-115）。しかも別の章が正しく書いていると、論文の中で食い違う（表 4.5・5.3 (B) は M1 と M2 を分けて書いていた）。直し方: 対象ごとに 1 文ずつ言い、根拠のある節を指す。これは読みやすさではなく正確さの型だが、ひとまとめの文はどちらにも引っかかるのでここに置く。
12. **全体の流れ・構成を説明する節は、図を置き、文は図の部品の名前で指しながら進める**（2026-10-20、ユーザー指摘「システム図に触れながら説明する」）。工程の羅列（文字の矢印図・箇条書き）だけでは、どこで分岐し、どこへ戻り、何が受け渡されるかが読み取れない。図の区切り（フェーズ）ごとに 1 項目、各工程の節の冒頭には「（図 N の Mx）」を添える。図に描いた分岐や戻り（閉ループ）は、文でも理由とともに 1 回言う。判定: 図を見ずに文だけ読んで、工程の順序と分岐を描き直せるか。描き直せないなら図が要り、図を置いたのに文が図の名前を使っていないなら文を直す。**各工程の節も同じ**（2026-10-21、ユーザー指摘「各フローを図示したあれを使いたい。それに則った説明のほうがわかりやすい。百聞は一見にしかず」）: 工程の中の手順は、その工程の途中経過を実際のデータで描いた図（`render_pipeline_stages.py` の M3〜M5）を置き、手順の段落を図のパネル（①〜③）に 1 つずつ対応させる。番号つきの手順の羅列は、パネルの数に合わせてまとめる（3.8 は 5 手順 → 3 段落）。
13. **読者が尋ねていない、書き手の方針の宣言を置かない**（2026-10-21、ユーザー指摘「誰に断っているの？」）。実例: 1.4「考察は各実験の直後に置き、独立した考察章は設けない」。書き手が別の案（考察章を立てる版）と比べた判断の名残で（9-30 の 50 ページ化で考察章をやめたときに足した文）、読者には比べる相手が見えないので、誰に向けた断りか分からない。判定: (a) 文の主語が書き手の書き方の判断（設けない・置く・まとめる・回す）で、(b) 消しても読者が困らない（本文の場所を探せなくなる・結論を読みすぎる、が起きない）→ 消す。残すもの: 主張の範囲の限定（「〜は主張しない」「範囲外である」）は読者が結論を読みすぎないための根拠、場所の案内（「限界は 5.3 節に集約した」）は読者が探す助けなので、主語が書き手でも残す。CLAUDE.md §4-2「修論に書くもの／書かないもの」の「宣言した時点で経緯である」と同じ根。

14. **節・章への参照は、読者がそこへ行く必要がある初出 1 回だけにする**（2026-10-21、ユーザー指摘「A の話をした後に（A は n 章で述べます）が多い」）。実測で先輩の修論の 3 倍（1000 字あたり 3.2 対 1.0）、括弧書きでは 8 倍（1.6 対 0.2）あった。台帳で主張ごとに出典を付ける書き方が修論に入った癖。残す: 定義・詳細・根拠が別の場所にあり、読者がそこを見ないと文が成り立たないときの初出、図の部品と節の対応（型 12）、限界の場所の案内。消す: 同じ段落・同じ節での 2 回目以降、1.4 の構成の説明と重なる章の羅列（1.3 の貢献ごとの「（第3章・第4章）」）、その場で読者が要らない先送り（「今後の課題とする（5.4 節）」のように文がすでに言っているもの）。「第4章 4.3.2 節」は「4.3.2 節」に縮める。⚠️ 参照先が正しいかも同時に見る（3.12.4 の「順序づけ全般に用いる基準（4.3.3 節）」は定義の場所 4.1.4 項が正しかった）。

15. **修論の本文に、台帳の番号（系譜 N-M・Bug N）や内部の md へのリンクを書かない**（2026-10-21）。審査員はそれらを見られないので、括弧の中が読者にとって空の参照になる。根拠を言いたいなら、その中身（「シードを変えると順位が入れ替わるため」）を 1 句で書く。洗い方: `grep -nE '系譜|9-[0-9]{2,3}|Bug [0-9]|\]\([^)]*\.md'` を執筆メモの外で。D-6 で埋まる空欄の印は例外。

16. **「N 個に分かれる」と予告したら、本文の項目と名前・数・順をそろえる**（2026-10-21、ユーザー指摘「作業空間の解析はガン無視？」）。予告に挙げたのに本文に出ない項目、本文で論じるのに予告に無い項目があると、読者は欠けた方を探す。2.4 は予告 4 つのうち 2 つが本文に無く、本文の反実仮想説明が予告に無かった。表（表 2.1）がある節は、予告・本文・表の 3 つをそろえる。
17. **システムを説明する章（第3章）より前では、システムの内部の番号・式・細部を、読者が知っている前提で書かない**（2026-10-21、ユーザー指摘「第1層の説明がない章なのに急にこんな話をしている」）。第1章・第2章の読者が知っているのは、第1章 1.2 のアプローチで導入した概念の名前（色マーカーの規約、幾何・収束設計・行動の三層、Leader と Follower）までで、工程の番号（M1〜M7）・層の番号（第1層〜第3層）・判定の式（目標距離 ÷ 最大リーチ）・節の中の仕組みは知らない。直し方: 第1章で導入した名前に言い換える（「第1層」→「幾何の層」、「第2層・第3層」→「学習の結果を読む診断」）か、その話が位置づけに要らなければ消す。判定: その語が第1章の本文に定義つきで出ているか。出ていなければ第3章へ回す。
18. **位置づけ・導入・手法の概観では、結果の節や 5.3 の限界で言う粒度の但し書きを先回りして入れない**（2026-10-21、ユーザー指摘「誤解を招く言い方を避けるために、実験結果で報告するレベルの粒度をここで言っているからわかりにくい」）。実例: 2.4「ただし、この性質が成り立つのは形だけで決まる不適合のときだけ。学習の結果を読む診断では反実仮想を作れていない」。誤読を防ぎたい気持ちから入れた但し書きが、その章の筋（ここでは先行研究との違い）を切る。直し方: 主張の文の側で範囲を絞る（「幾何で決まる不適合について、解析的に得る」）か、限界の節へ 1 回だけ置き、ここでは消す。判定: (a) その但し書きは実験・観察の結果か、それを読むのに後の章の知識が要るか (b) 消しても、この章の主張が言い過ぎにならないか（主張の文がすでに範囲を言っていれば言い過ぎにならない）→ 両方なら消すか、限界の節へ移す。残すもの: 先行研究の限界（位置づけの論証そのもの）、研究の範囲の宣言（「シミュレーションに限られる」）、手法の手順の理由になっている但し書き（3.6「規約を満たすとは限らない → だから人手で確認する」）。
19. **関連研究の節は、問いごとに「先行研究は何をする → 何ができない → だから本研究はこうする」を閉じる**（2026-10-21、ユーザー指摘「先行研究では何ができないからこの研究ではこうやる、がなかなか伝わらない。一つの節で複数のことを伝えようとしているから？」）。崩れ方は 3 通りあった: ① 一つの節に問いが二つあるのに分けず、先行研究を横一列に並べる（2.4: 判定の問いと返すものの問い）② 限界を N 個挙げて、本研究の答えが一部にしか無い（2.2: 第二の限界への答えが無かった）③ 「できない」で終わり「だからこうする」が無い（2.1、2.3）。直し方: 冒頭で問いの数を言い、問いごとに段落の組を分け、各組の最後を「本研究は〜」の 1 文で閉じる。借りてくる枠組み（反実仮想説明）は「できないもの」と別の役として、「この形式で返す」と書く。判定: 各段落に「先行研究ができないこと」と「本研究がそれにどう答えるか」が 1 文ずつあるか。⚠️ 型 14 で参照を消すとき、その文が「だからこうする」の役も持っていないか確かめる（2.3 の「第4章ではこの点を評価する」を消して ③ を作った）。
20. **段落の頭に、名詞だけの太字のラベル（「判定。」「返すもの。」）を置かない**（2026-10-21、ユーザー指摘「判定。とか返すもの。とかになっている論文が正しいと思う？」）。英語の論文の段落見出し（`\paragraph{Judgment.}`）を持ち込んだ形で、日本語の論文の本文では見出しにも文にもならない。書き手が冒頭で付けた呼び名（「返すもの」）をラベルにすると、読者には作業メモに見える。直し方: 段落の最初の文を、その段落の問いを言う主題文にする（「適合しない場合に設計者へ何を返すかについては、〜がある」）。段落では収まらないほど長いなら、節（2.4.1）を立てる。残すもの: 予告した列挙の項目名（5.3「次の 4 群」の (A)〜(D)）、用語を定義する箇条（4.1.4「順位の判定: 〜」）。判定: ラベルを消して、段落の最初の文だけで何の段落か分かるか。分からなければ主題文を足す。
21. **先行研究を要約するときは、対象（何に対して）と評価の範囲（何で確かめたか）を書き、推測した限界を事実の形で書かない**（2026-10-21、ユーザー指摘「URDF-Anything はそもそも取っ手やスライドといった関節だけで、ロボットに対して行っていない。もちろんタスク検証も」）。表 2.1 は「密な関節構造で推定誤差が残存」と、論文が試していない対象での結果を断定していた。本文の「〜は示されていない」を表へ縮めたときに、但し書きが落ちて断定になる。直し方: 「対象は〜（規模）で、〜は扱わない。評価は〜までで、〜は行わない」の形にする。本研究との違いは、この対象と範囲の差からそのまま出る（ロボットの形態を扱う・タスクで確かめる）。判定: その限界は、論文が試して出た結果か、試していない範囲への推測か。推測なら「示されていない」「扱っていない」と書く。⚠️ 表と本文は同時に洗う（第1章だけ直して、表 2.1 と 2.2 に同じ言い過ぎが 2 日残った）。
22. **式に出す記号は、初出で何を指すかを定義する。記法（縦棒・セミコロン・上付きの添字）も、読者の分野で読み方が決まっていなければ 1 文で言う**（2026-10-21、ユーザー「数学的なこの項の読み方がわからない」）。3.1 は $\pi^L(\cdot \mid s^L_t; \theta^L)$ を、$s^L_t$・$s^F_t$・$\theta$ も、縦棒とセミコロンの意味も言わずに使っていた。原論文の記法をそのまま写すと、原論文の読者が知っている前提が落ちる。直し方: 記号の表（記号・意味）を置き、具体物は実装で確かめて書く（$s^F_t$ = 各関節の角度と角速度・手先から見た対象物の相対位置。`pusher.py` の `_get_obs`）。判定: 式の直前・直後の文だけで、各記号を言葉に置き換えられるか。
