## 1. ひとことで言うと

**手描きの絵から、ロボットの腕のシミュレーション用モデルを自動で作り、「この形でこのタスクができるか」を判定して、できないなら「どう直せばいいか」まで返すシステムを作りました。**

主役はシステムです。中で使っている学習の手法（Stackelberg PPO という co-design の手法）は、判定に使う部品の一つという扱いです。

## 2. なぜやるのか（第1章）

### 困っていること

生成 AI のおかげで、ロボットを動かすプログラムはすぐ書けるようになりました。ところが、そのプログラムを試すためのシミュレーション用の「機体モデル」は、いまも CAD で作っています。CAD でモデルを作るには、関節がどこまで曲がるか、回転軸の向き、重さの配分など、機械工学の知識が要ります。

中間発表での言い方を借りると、**プログラムは 1 日で書けるのに、それを試すロボットのモデルが 1 週間できない**、という状態です。ソフトの専門家にとっては、ここが開発の詰まりどころになっています。

### スケッチから始めるときの 3 つの壁

専門知識が無くても、作りたいロボットの形を手軽に表す方法の一つが手描きのスケッチです。ただ、スケッチからシミュレーションでの検証まで進もうとすると、壁が 3 つあります。

1. 絵を立体にする技術（image-to-3D）はあるけれど、出てくるのは 1 個のかたまりのメッシュです。どこが関節で、どこで曲がるのかという情報が入っていません。
2. 形が良いかどうかは、形だけ見ても決まりません。同じ形でも、上手に動かせるかどうかで結果が変わるからです。形と動かし方はお互いに影響し合っています。
3. 「この形はダメ」と分かっても、何をどう直せばいいかは、その判定だけからは分かりません。

## 3. どう解いたか（第1章 1.2・第3章）

壁ごとに、次の 3 つの手を打ちました。

| 壁 | 打った手 |
|---|---|
| 1. 関節の情報が無い | 絵を整える段階で、生成 AI に「関節の位置にマゼンタの丸を描いて」と指示します。立体にした後でその色を探せば関節が分かるので、関節を推定するという難しい問題そのものを避けられます |
| 2. 形だけでは良し悪しが決まらない | co-design（形と動かし方を一緒に学習する手法）を使います。ただし「もっと良い形を自動で設計する道具」としてではなく、**人が考えた形を、動かし方の上達まで含めて評価する判定器**として使います |
| 3. 直し方が分からない | 判定の結果を、幾何・収束した設計・動き方の 3 つの層で読み解いて、人が読める直し方に訳します（例:「腕全体を 1.02 倍に伸ばしてください」） |

### システムの流れ（M1〜M7）

| 工程 | やること |
|---|---|
| M1 画像整形 | 手描きの絵を整え、関節に色の丸を描かせる |
| M2 立体化 | 外部サービス（Tripo3D）で三次元メッシュにする |
| M3 関節検出・リンク分割 | 色の丸を見つけて関節の位置を決め、メッシュを腕の部品（リンク）に切り分ける |
| M4 パラメータ抽出 | 各リンクの長さや太さを測る |
| M5 モデル生成 | シミュレーション用のファイル（XML）を作る |
| M6 判定 | co-design で学習させ、その形でタスクがどれだけできるかを測る |
| M7 診断 | ダメだったときに、なぜダメで、どう直せばいいかを返す |

M3〜M5 は全部自動で、2 秒くらいで終わります。M1・M2 は外部サービスを使います。

### 診断の 3 つの層（M7）

| 層 | 見るもの | 学習が要るか |
|---|---|---|
| 第1層 幾何 | 腕の長さと目標の距離だけ。届かないなら「何倍に伸ばせば届くか」を返す | 要らない（数秒） |
| 第2層 収束した設計 | 学習で決まったギア比や太さ | 要る |
| 第3層 動き方 | 実際の動き。たとえば「この関節はほとんど使っていないので固定してよい」 | 要る |

幾何的に届かない形は、学習をせずに数秒で「無理です、こう直してください」と返せます。ここがこのシステムの強みです。

## 4. 何を確かめたか（第4章）

### まず大事な前提: 物理の値をやり直している

10 月の半ばまでの実験は、シミュレーションの物理の値（腕の重さ、モーターの強さなど）に根拠がありませんでした。シミュレータの移植の不具合も重なっていました。そこで 10-13 から、全部の実験を実在の値でやり直しています。腕はアルミの薄いパイプ、モーターは協働ロボット UR5e の関節の値です。

なので、修論の第4章にいま載っている数字の多くは、まだ古い物理のものです（章の冒頭に注意書きがあります）。古い数字は、新しい結果が出しだい差し替えます（D-6）。

### 判定器に求めること（R1〜R4、4.1.5）

| 記号 | ひとことで | 中身 |
|---|---|---|
| R1 | 形を変える意味があるか | 形を固定して動かし方だけ学習したら、同じくらいできてしまうなら、形の良し悪しを論じる意味がありません。それを確かめる前提です |
| R2 | タスクが違えば答えも違うか | 判定器は、タスクごとに違う形を選ばないといけません。どのタスクでも同じ順位なら、ただ大きさを測っているだけです |
| R3 | 渡された形に正しく順位を付けられるか | システムが実際にやるのはこちらです。人が持ち込んだ形を並べて評価します |
| R4 | どれだけ学習すれば順位が決まるか | 1 枚ごとに長く学習していたら、何度も描き直す使い方には向きません |

## 5. わかったこと（第5章 5.2）

1. スケッチから判定・直し方の提示まで、1 本のシステムとしてつながりました。
2. 判定に要る入力は、リンクの本数・長さの比・関節の位置と軸だけです。重さの材料やモーターの型番は与えていません。
3. タスクが違えば、判定器が選ぶ形も違います（R2 は実在の物理で成立しました）。
4. 助言に従えば不適合は直ります。ただし、助言が使えるかどうかは、判定が正しいかどうかとは別に壊れることがあります。これは、助言を適用して入れ直してみるまで分かりません。修論でいちばん伝えたい方法論の話です。
5. 実験は、実在の部材とモーターから導いた条件で行いました。

## 6. 言えないこと（第5章 5.3 の限界）

- シミュレーションだけです。実機での確認はしていません。
- 腕の形はカプセル（円柱の両端に半球）でしか表せません。
- 関節の粘性の値（1）は、元の論文の値をそのまま使っていて、実在の値に基づいていません。
- 多くの条件は 2 seed だけです。統計の検定はしていません。
- 手描きの実走は 5 件だけで、成功率と言える件数ではありません。そのうえ 5 件とも、M1・M2 を外部サービスの画面で手で動かしました。「人手が要らない」と言えるのは関節の検出から後だけです。
- 何分以内なら実用的か、という基準は設けていません。
- 診断の第2層・第3層の閾値（たとえば「使用率 10 % 未満なら固定してよい」）は、較正できていません。

## 7. 言ってはいけない読み（いまの時点）

修論や発表で口にしないように、よく出てくるものだけ挙げます。全部のリストは [知見総括表.md](知見総括表.md) の E 節です。

- 10-13 より前の実験の数字（397 mm → 0.33 mm、−36 %、順位の表の数字など）を、いまの結論として言うこと。これらは古い物理のものです。
- 「順位がタスクで入れ替わることを初めて示した」。先行研究が既に示しています。
- 「関節を固定する助言は、到達で 2 seed とも良くなった」。当時の 2 本は、実は形が少し違う 2 形態 × 1 seed でした（9-105）。
- 「形の違いは慣性で説明できる」。慣性で説明しようとした読みは、3 回とも外れました。
- 「時間的に実用的」。基準を置いていないので言えません。

## 8. 用語ミニ辞典

| 用語 | 意味 |
|---|---|
| co-design（形態-制御 co-design） | 形と動かし方を一緒に学習する方法 |
| Stackelberg PPO | この研究が使う co-design の手法。形を決める役（Leader）と動かし方を学ぶ役（Follower）の 2 人のゲームとして扱う |
| 判定器 | この研究での co-design の使い方。「より良い形を作る」のではなく「この形でできるか」を判定する |
| 到達（Reach） | 腕の先を目標の点に持っていくタスク |
| 押し（Pusher） | 箱を押して遠くへ動かすタスク |
| 固定根本アーム | 根元が床に固定されていて、移動できない腕 |
| ギア比（gear） | 各関節のモーターの強さ（最大トルク）。この研究では設計で決める値 |
| seed | 学習の乱数の種。同じ条件を seed を変えて 2 回回し、結果の幅（帯）を見ます |
| 帯 | 2 seed の結果の範囲。2 つの条件の帯が重ならなければ「区別できた」と言います |
| 実在の物理（`*_phys`） | 10-13 からの、根拠のある物理の値でやり直した実験 |
| 第1層の助言 | 「腕全体を N 倍に伸ばしてください」。判定を覆すのに必要な最小の倍率を返します |
| 閉ループ | 助言を実際に適用した形を作って、もう一度システムに入れ直すこと |
| 検証 | M1〜M7 がそれぞれ想定どおり動いているかを確かめたこと（2026-10-05 のユーザーの定義） |
| 実験 | 作ったシステムを、いろいろなパターンで動かしてみたこと（同上） |
| D-6 | 古い物理の数字を、実在の物理の結果に差し替える作業（進捗.md） |
