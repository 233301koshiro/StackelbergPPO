## 1. 一言でいうと

**「その形、そのタスクに向いてる？」を、絵から数時間で答えるシステムを作った。**

向いていなければ「腕を 2.19 倍に伸ばして」と数値で返す。
判定エンジンには強化学習の形態-制御 co-design（Stackelberg PPO）を使うが、
**より良い形を自動で作らせるためではなく、人が描いた形を採点させるために**使っている。

---

## 2. なぜやるのか — 困っているのは誰か

ロボット開発で、**ソフトは速くなったがモデルが追いつかない。**

- 制御アルゴリズムは生成 AI でさっと書けるようになった
- でもそれを試す**シミュレーション用の機体モデル**を作るには、関節可動域・回転軸・質量特性といった
  機械工学の知識が要る
- ハードが専門でないソフトエンジニアにとって、ここが壁になる

この非対称（速く検証したい ⇔ モデルが出てこない）が開発の律速。
**入口を手描きスケッチにできれば壁は下がる**、というのが出発点。

### 想定ユーザーと工程上の位置

- ユーザー: **ハードが専門でないソフトエンジニア**
- 工程: 量産を見据えた詳細設計（CAD の仕事）の**手前にある概念設計段階**
- やること: 寸法や公差を詰めるのではなく、**「この案、そもそも成立する？」を見極める**

---

## 3. 素直にやろうとすると詰まる三箇所

| # | 詰まりどころ | なぜ詰まるか |
|---|---|---|
| ① | 絵 → 3D は既存技術でできる。**でも関節がない** | image-to-3D の出力は**ひとかたまりの連結メッシュ**。どこがリンクでどこが関節かの情報がゼロ。点群から関節を学習で推定する研究はあるが、ロボットのように関節が密な対象では精度が足りない |
| ② | 形が出ても、**タスクに向くかは形を見ても分からない** | 形態と制御は相互依存。「この形が良いか」は、その形を制御が使いこなせて初めて決まる。静的な幾何からは決まらない |
| ③ | 向かないと分かっても、**どう直せばいいか分からない** | 判定はスコアを返すだけ。専門知識のないユーザーは次の一手が打てず、作っては直すの繰り返しになる |

この3つが、そのまま提案手法の3本柱に対応する。

---

## 4. 全体像 — 7つのモジュールを一方向に流す

```
手描きスケッチ
  ↓
[M1] 画像整形＋関節マーカー規約   … Gemini（固定プロンプト）  ← ①への回答
  ↓
[M2] 3D 形状生成                  … Tripo3D（既存技術に委任）
  ↓
[M3] 関節検出とリンク分割          … 色検出＋幾何処理（決定的）  ← ①への回答
  ↓
[M4] 形態パラメータ抽出            … OBB 近似（決定的）
  ↓
[M5] シミュレーションモデル生成    … テンプレート変換（決定的）
  ↓
[M6] co-design で評価・判定        … Stackelberg PPO           ← ②への回答
  ↓
[M7] 形態診断（三層）              … 幾何／収束設計／行動       ← ③への回答
  ↓
判定 ＋ 修正指示
```

**自動化の実態は正直に言うこと。** M3 以降はシェルスクリプト一発で通る。
**M1・M2 は外部サービスを Web UI で叩いているので手動が入る**（API 全自動は未実装）。
論文で「人手を介さず」と言っているのは **M3 以降の決定的処理と M6 の学習**のこと。

## 5. M1〜M7 — 各ステップの「課題 → 解決」

### M1: 画像整形と関節マーカー規約

- **課題**: 生成された 3D には関節情報がない。後段が構造を読めない
- **解決**: 3D にする**前**の画像の段階で、**関節位置に純マゼンタ #FF00FF の球を描かせる**規約を課す
- **効かせ方**（プロンプトの3要素）
  - 全接続部にマゼンタ球を1個ずつ。マゼンタは自然物・工業製品に稀なので色検出で分離しやすい
  - 各リンクは彩度の高い単色。グラデーション禁止。マゼンタは本体色に使わせない
  - **関節位置を「台座と上腕の間」のように場所で列挙し、描き終わったら個数を自己検査させる**
- **なぜ最後の1つが要るか**: 場所の列挙を抜くと、生成 AI が**先端側の関節をヒンジ金具として描き分けて
  マーカーを落とす**。実測で起きた。3個描かせるには3箇所を名指しするしかない

### M2: 3D 形状生成

- **課題**: 特になし。ここは既存技術に丸投げする
- **実測知見が2つあり、後段の設計に効いている**
  - **色が変わる**。#FF00FF (255,0,255) が概ね (211,75,169) に暗色化する。ただしリンク本体色とは
    独立クラスタとして残るので、**狙う色を実測に合わせれば検出は成立する**
  - スケールは概ねメートル単位で、単位換算は不要だった

### M3: 関節検出とリンク分割

- **課題**: メッシュから関節を見つけてリンクに切る
- **解決**: 学習は使わず、色で探して Z で切る
  1. **頂点色の復元**。GLB は色を UV テクスチャで持つので、まず頂点色に焼き込む。
     これを抜くと頂点色が常に空になり無条件で失敗する
  2. **マーカー頂点の抽出**。目標色±許容幅で拾う。目標色と許容幅は**自動キャリブレーション**
     （マゼンタ色相域の支配クラスタの中央値を目標色、広がりから許容幅）。M2 の色ズレに人手なしで追従する
  3. **3次元でクラスタリング**。マーカー頂点を 3D の連結成分に分け、成分ごとの重心を関節位置とする。
     頂点数が全体の 2% 未満の成分は捨てる（色にじみの迷い頂点 1 個が偽関節になった実測がある）
     - ⚠️ **当初は Z 座標だけを見ていたが、短い腕で壊れた（2026-09-02、Bug 30）。**
       マーカー球には大きさがあるので、**リンクが短く腕が傾いていると隣り合う球の Z 範囲が重なり、
       2 個が 1 個に融合する**（実測: 球の Z 幅 0.14 に対し関節間の Z 差 0.127 → 検出が 3 個ではなく 2 個）
     - 球どうしは **3 次元では必ずリンク長ぶん離れている**（0.24〜0.26 対 球の半径 0.07）ので確実に分離できる。
       連結半径を 0.01〜0.03 と変えても同じ結果で、**閾値に鈍感**
  4. **リンク分割**。関節の Z を境界にフェースを振り分ける（**切るのは今も Z**。3D にしたのは
     関節を「見つける」ところだけ）。境界間にフェースがなければ**即座に例外で停止**
- **正直に書いてあること**: 閾値は理論由来ではなく実験で決めた経験値。
  ただし **2%（棄却率）も連結半径もメッシュの外接寸法に対する割合**なのでスケール不変。
  当初あった「0.05 m という絶対距離」の問題は、3D 化と相対量への変更で解消した（Bug 30）
- **失敗したら止める（フェイルファスト）**。マゼンタ域のクラスタがなければ検出失敗として明示的に停止し、
  関節位置の手動指定へ落とす。黙って変な結果を出さない

### M4: 形態パラメータ抽出

- **課題**: 分割したメッシュから co-design の設計変数の初期値を取る
- **解決**: リンクごとに **OBB（傾いた外接直方体）**を取る。OBB は**メッシュがどっちを向いていても
  ぴったり沿う箱**なので、斜めに置かれた棒でも「長い辺＝棒の長さ、残り2辺＝断面」として読める
  - **半径** = 残り2辺の平均の半分（断面を円と見なす）
  - ⚠️ **リンク長は OBB を使わない（2026-09-02 変更、Bug 27・31）。**
    M3 の切り分け面は**マーカー球の中心**を通るので、リンク片には**両端の半球が半分ずつ**付いてくる。
    腕が傾いているとこの半球が軸方向にもはみ出し、OBB の最長辺が伸びる。
    過大量はだいたい **2 × 半径 × sin(傾き)** で、**リンクが短いほど・太いほど・傾いているほど効く**

    | 形態 | OBB の過大評価 |
    |---|---|
    | B2（細長い） | +12〜14 % |
    | A1（標準・傾き 46°） | +18〜20 % |
    | **B1（短く太い）** | **+48〜132 %** |

    いまは **リンク長＝関節間の距離**（`glb_to_links` が測って `joints.json` で渡す）を使う。
    **半径は OBB のまま**（半径への影響は +0〜6.5 % と小さい）
- **取れないもの**: 関節可動域とギア比は**絵からは決まらない**。既定値（ギア比 100、可動域 ±90°）を使う
  - 妥当性は次数のオーダーで確認してある。押す対象は 2.7 kg・摩擦 0.5 なので必要な水平力は約 13.2 N、
    腕の長さ 0.5 m 換算で約 6.6 N·m。ギア比の下限 20 でもこれは上回るので静止摩擦は超えられる
  - ただし**既定値 100 は探索範囲 [20,400] の下から約 21% の位置**で、中立な出発点ではない。

    ```
    20 ─────●──────────────────────────── 400
            ↑                         ↑
          100                    押しの収束先
       （下から21%）
    ```

    Leader は毎エピソード**この位置から編集を始める**。押しタスクは高ギアが有利で
    実測では 400（上限）に張り付くので、100 から上へ編集し続ける必要がある。
    編集回数には予算があるため、**出発点が遠いと届かないかもしれない**。
    逆に到達タスクは低ギアが有利（下限 20 に収束）なので 100 からだと近い。
    **同じ既定値がタスクによって有利にも不利にもなる。**
    その影響そのものは測っていないので、限界として第3章 3.9 に書いてある

### M5: シミュレーションモデル生成

- **課題**: 抽出したパラメータを学習系が読める形にする
- **解決**: MuJoCo 互換 XML へテンプレート変換。各リンクはカプセル近似。
  子リンクの取り付け位置は親の終端に合わせ、関節とアクチュエータを付ける
- **効いたポイント**: 手書きの 2 関節モデルと**同じ書式**で出すので、学習系からは普通のロボットに見える。
  実際に **3 関節メッシュ由来のモデルがコード変更ゼロで受理された**
  - 理由は方策ネットワークが Transformer ベースで、形態を可変長のグラフとして扱うから。
    関節が増えてもノードが増えるだけ

### M6: co-design による評価・判定

- **課題**: この形がタスクに向くかを、制御の習熟込みで測る
- **解決**: Stackelberg PPO を回す。**Leader = 形態を編集する側、Follower = その形態を操る制御側**
  - 1エピソードは「Leader が形を決める」→「Follower がその形で動いてタスク報酬を得る」の2フェーズ
  - **肝は Leader の目的関数に Follower のリターンがそのまま入ること。**
    形態は運動学的な理屈で評価されるのではなく、**制御が実際にどれだけ使いこなせたか**で評価される。
    ここが「判定器として使える」根拠
- **本研究での使い方の変更点**
  - **骨格変換フェーズは無効化**。トポロジーはスケッチが決めるので固定する
  - 使うのは属性変換（リンク長・ギア比の編集）のみ
- **速くする工夫**: ゼロから学習せず、同じタスクの学習済み重みを転用（warm-start）して始める
  - 分解実験の結果、**形態ネットワークを含む転用（形態のみ／全成分）が転用元を上回り、
    制御方策だけの転用は転用元を下回った**
  - 判定に要するエポック数は候補の隔たり次第。**明確に違う候補なら 30 エポック、
    乱数しか違わない候補まで分けるなら 120 エポック**。実運用は 30 で仮判定して、僅差なら延長

### M7: 形態診断（三層）

- **課題**: スコアだけ返しても、専門知識のないユーザーは次の手が打てない
- **解決**: M6 の既存成果物（初期 XML・収束チェックポイント・行動トレース）だけを入力に、
  **追加学習なしで**人間可読な指摘へ翻訳する

| 層 | 見るもの | 所要 | 出せる判断 |
|---|---|---|---|
| **第1層 幾何** | 初期 XML のリンク長と目標位置 | 約1秒 | **断定してよい**。届かない／貫入する／軸が違う。**必要な拡大倍率を数値で返す** |
| **第2層 収束設計** | co-design が収束させたパラメータ | — | 警告のみ。ギア比の上限／下限張り付きを報告 |
| **第3層 行動** | 収束方策を1エピソード決定論的に実行した軌跡 | 三層で約3秒 | 警告のみ。戦略を分類（吹き飛ばす／穏やかに押す／触れていない 等）＋**各関節が可動域のどれだけを使ったか**（2026-09-02 追加。10% 未満なら「固定してよいかも」と提案） |

## 6. 「なぜそうしたか」— 意思決定のロジック

ここが説明で一番聞かれるところ。要素技術の中身よりこっちを話す。

### なぜ co-design を「最適化ツール」ではなく「判定器」として使うのか

- **課題の構造がそれを要求する。** 形態の補正はタスク性能でしか方向づけられず、
  タスク性能は形態が定まらないと測れない。**この2つは分離して解けない**
- Stackelberg PPO は Leader の評価に Follower の実リターンを継承するので、
  **「この形を制御が使いこなせたか」がそのまま形態の点数になる**。判定器の要件に構造的に合っている
- **用途を変えると要求仕様が変わる**、というのが本研究の主張の一部
  - 設計ツールとしての基準は「最終的にどこまで性能が伸びたか」
  - **判定器としての基準は「与えた形態集合を正しく順位づけられるか」「実用的な時間で返せるか」**
  - **原論文はどちらも検証していない。** 判定器として使うと決めたから初めて検証対象になった
- この立場だと**トポロジー固定は制約ではなく仕様**。骨格はスケッチが決めるべきもの

### なぜ関節マーカー規約を設けたのか

- 素直な代替案は「点群から学習ベースで関節を推定する」。**でも密な関節では精度が足りない**
- 発想の転換: **推定精度を上げるのではなく、推定問題そのものを消す**
  - 生成 AI に「潜在的な構造を推定してくれ」と頼むのをやめ、**「構造を宣言しろ」と強制する**
  - 結果、M3 の関節検出が**精度保証のない推定問題 → 閾値つき色マッチングという決定的問題**に変わる
- **設計思想として一般化できる**: 生成モデルの確率的なブレを**下流で補償する**のではなく、
  **上流で入力空間を拘束して回避する**
- ただし実測で分かったのは、**アルゴリズムが決定的でもシステムが頑健とは限らない**こと。
  生成側が指定色を出さない（最大 86/チャネルずれる）ので、
  **入力ごとに基準色を推定する工程を前に置いて初めて成立した**。
  頑健性は個々のアルゴリズムの決定性ではなく、**外部サービスのばらつきをどこで吸収するか**にある

### なぜ診断を三層に分けたのか（コストの都合ではない）

- 分けた本当の理由は**判断の確定性が層ごとに違う**から
  - 第1層が使うのはリンク長と目標位置だけ。**「0.403 m の腕は 0.800 m 先に届かない」は
    学習結果にもシードにもよらない**。反証されない
  - 第2層・第3層が使うのは学習の帰結。**シードや打ち切りエポックで変わりうる**
- そこから設計原則が出る: **確定的な層は断定してよい。確率的な層は断定してはならない**
  - 実装でも**総合判定を出す権限は第1層だけ**に持たせ、第2・第3層は報告と警告に留めている
- 同じ理由で、**第1層は「届かない」しか断定しない。「届く」とは言わない**
  - リンク長が最適化対象に入る設計モードでは、最大リーチが学習中に伸びうるから
  - リンク長を凍結する判定モード（本システムの標準）でのみ双方向に判定する

### なぜ報酬を複雑にしないのか

- 押しタスクで「一撃で吹き飛ばす」打撃的方策が出た。これを reward hacking とみなして
  報酬を作り込んだ（目標座標化・シェーピング・到達ボーナス）ところ、
  **別の局所解を誘発するか、探索信号そのものが消えた**
- そもそも**打撃的方策は速度報酬に対する固定根本アームの正当な最適解**で、排除すべきものではなかった
- **co-design 固有の事情がある**。普通の強化学習なら報酬の複雑化は「学習が難しくなる」で済む。
  co-design では**報酬が形態の評価関数を兼ねる**ので、制御を誘導するつもりの項が形態の評価を歪める。
  加えて Leader の勾配は Follower 側の Hessian の逆作用を含むため、報酬地形が多峰化すると
  勾配の信頼性まで落ちる。**歪んだ評価関数を、劣化した勾配で最適化する**ことになる
  - ⚠️ ただし後半は定式化からの整合的な説明であって、**Hessian の条件数を測って因果を分離してはいない**。
    実験で示したのは「報酬を複雑にした条件群で形態探索が停止した」という事実まで
- **正しい介入は、報酬をいじるのではなくタスクの定義を変えること。**
  打撃では解けないタスクが欲しいなら Target-Pusher のように**測るものを変える**

### なぜ助言を「閉ループ」で検証したのか

- 判定の正しさを確かめるだけでは足りないと分かったから
- 助言を適用した形態を実際に作って**再入力してみて初めて**、2つの欠陥が出た
  - 助言の倍率が四捨五入で**切り捨て**られ、助言どおり直したのに同じ診断が再び却下した
  - 形態を拡大する工程が**リンクの長さだけ伸ばして関節の取り付け位置を放置**し、
    見た目は伸びたのに実効到達距離が公称の 63% にしかならなかった
- どちらも**判定精度を見る検証では原理的に検出できない**。
  → **助言を返すシステムは、出力の正しさとは別に、出力の実行可能性を検証する手順を持たねばならない**
- これが「システムとして評価したからこそ出た知見」で、修論の主張の一つ

## 7. 境界線 — どこまでやって、どこからやらないか

説明のときに一番曖昧にしてはいけないところ。**「シミュレーション上の幾何モデリング」まで**が本研究。

### やっている: シミュレーション環境における幾何ベースのモデリングと相対評価

| 項目 | 中身 |
|---|---|
| **形状の表現** | 抽出したリンク長・関節位置に基づく**カプセルと球体の幾何プリミティブ**。生成メッシュそのものは使わない |
| **構造の抽出** | 色マーカーの **3次元連結成分**による関節位置の特定と、Z 座標を境界としたリンク分割 |
| **パラメータ** | OBB からのリンク長・半径。質量は**プリミティブの体積 × 一律密度**から出る |
| **評価** | シミュレータ（Choreonoid）上でのタスク実行による**形態間の相対比較** |
| **診断** | 運動学（リンク長の総和と目標距離）による到達可能性と、必要な拡大倍率 |

### やっていない: 物理的・実機ハードウェア的な要素

| 項目 | なぜ外したか |
|---|---|
| **実機の製作** | 概念設計段階の支援が目的。詳細設計・製造は下流工程 |
| **sim-to-real gap の解決** | 実世界の接触力学・アクチュエータ特性・センサノイズは扱わない。**実機での動作は保証しない** |
| **実材料の質量特性** | 質量はプリミティブ体積 × 一律密度で、材料選定も CAD 相当の質量算出もしない |
| **公差・寸法の精緻化** | 「達成しうるか」の妥当性評価に特化。寸法を詰めるのは CAD の仕事 |
| **絶対スケールの制御** | 生成モデルの出力に依存し制御できない。**外すと宣言したうえで、不整合を検出して拡大倍率を助言する立場**を取る |
| **把持・多指ハンド** | 判定軸が「腕の形」から「ハンドの形」へずれる。分岐構造の関節数も誤りやすい |
| **報酬関数の自動設計** | 意図から報酬を自動生成する機能は範囲外。報酬の複雑化が探索を壊すことが分かっているので、第3層は**タスクの選び直し**を提案するに留める |

### 一行で言うなら

> **「シミュレーション上で、co-design がタスクに応じて異なる形態・行動へ収束することを介した、
> 設計適性の相対比較」**が主張の全部。実機での動作を保証するものではない。

## 8. 実験で何が言えたか（代表値だけ）

数字の原本は [実験系譜.md](実験系譜.md)。ここは要点のみ。

1. **パイプラインは通り、条件も分かった。** 生成モデルはコード変更なしで受理され、1000 エポックの学習に耐えた。
   ただし**決定的アルゴリズムを使うだけでは頑健にならない**（M1 の色ズレ、§6 参照）
2. **判定器はタスクの要求を形態に反映する。** 3タスク×2シードの統制実験で収束形態が分離。
   分離は個々のパラメータの一致ではなく、**機能量（ギア比プロファイル・リーチ帯）と行動類型**の水準で現れる
3. **順位はタスクで入れ替わる。** 同じ3形態を Reach と Pusher にかけると**最良形態が反転**
   （Reach は中間 −3.42 > 長腕 −12.48、Pusher は長腕 96.18 > 中間 34.32、2シードで範囲が重ならない）。
   **絶対的な大きさではなくタスクの要求で評価している**証拠
4. **幾何が答えられない領域も埋まる。** 総リーチを固定して質量配分だけ変えた、
   **幾何情報では原理的に区別できない形態対**でも順序づけが成立した
5. **助言は効く。** 不適合と判定された形態に助言を適用しただけで、
   到達タスクの平均残存距離が **397 mm → 0.33 mm（三桁）**
6. **費用は二極化している。** 第1層は約1秒、三層でも約3秒。学習は 30 エポックで約4時間、200 エポックで約20時間。
   → **幾何的に破綻した形は、学習を一切回さずに修正指針つきで差し戻せる**。ここが概念設計段階での貢献

## 9. 突かれそうなところ（先に自分で言う）

| 論点 | 今の答え |
|---|---|
| シード数が少ない | 各条件1〜2シードで統計検定なし。**だから「頑健」という語を使わず**「シード間で初期的な一貫性」に留めている |
| 形態クラスが狭い | 中心は平面2関節。3関節・非平面4関節でも識別は再現したが、**非平面モデルはパイプラインの出力ではなく人手で書き起こしたもの**。パイプラインが非平面を作れる証拠にはならない |
| 前段の成功率が出せない | 規約準拠メッシュが2件のみ。外部サービスの Web UI 経由で入力を量産できないため。**成功率の代わりに色ズレの許容幅で代替**（E2E 手描き5枚で埋める予定） |
| 「余裕 10%」の根拠 | **実験で否定された。** 到達タスクは余裕を広げるほど単調に悪化する。必要な余裕はタスク依存で、一律 10% に実験的根拠はない。**論文は実装をそのまま記述し、再設計が要ると明記している** |
| 第2層は使えるのか | **単独では両方向に誤る。** 「ギア比も太さも下限に張り付く」署名が、失敗した形態と1位の形態の両方に出る。逆に接触すらできていない形態に肯定的報告も出た。**単独の判定根拠にしない**と結論づけた |
| 反実仮想の助言は第1層だけ | 第2層・第3層では「どう変えれば結果が変わるか」を構成できていない。学習し直さないと分からないため。**第1層で可能なのは幾何が支配する層だからで、診断機能全体の性質ではない**と明記 |
| ユーザー研究は？ | していない。**示したのは「入出力の形式が専門知識を要求しない」ことまで**。使いやすさは主張しない |
| 「即時」と言えるのか | 言えない。判定は 30 エポックで約4時間。対話的支援が要求する水準には達していない |

## 10. 用語ミニ辞典

| 用語 | 平たく言うと |
|---|---|
| **co-design（形態-制御 co-design）** | 形と動かし方を同時に決めること。形だけ／制御だけでは決まらないので一緒に解く |
| **Stackelberg PPO** | co-design の一手法。**形を決める側（Leader）と操る側（Follower）を上下関係のあるゲームにする**。Leader の点数に Follower の成績がそのまま入るのが肝 |
| **Leader / Follower** | Leader = 形を編集する方策、Follower = その形で動く制御方策 |
| **判定モード / 設計モード** | 判定モード = リンク長を凍結して採点する（本システムの標準）。設計モード = リンク長も最適化する |
| **warm-start（転用）** | ゼロから学習せず、学習済みの重みを引き継いで始めること。判定を速くするための工夫 |
| **トポロジー** | 何本のリンクがどうつながっているかという骨格の構造。本研究では**スケッチが決めるので固定**する |
| **OBB** | 傾いた外接直方体。メッシュがどの向きでも主軸の長さが取れる |
| **フェイルファスト** | おかしいと分かった時点で黙って進まず即座に止める設計。原因特定と再現性のため |
| **反実仮想説明 / 実行可能な救済** | 「判定を覆すには最小で何をどれだけ変えればいいか」を示すこと。本研究では「腕を N 倍に伸ばせ」がこれ |
| **打撃的方策** | 一撃で対象を吹き飛ばす動き。reward hacking に見えるが、速度報酬に対しては**正当な最適解**だった |
| **sim-to-real gap** | シミュレーションと実機のズレ。**本研究のスコープ外** |
| **ゼロスタート** | 学習を初期状態から始めること。warm-start の対義 |
| **頭打ち** | 学習が伸びなくなって収束すること |
