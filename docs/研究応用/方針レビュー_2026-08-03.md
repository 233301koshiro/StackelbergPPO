## ⑤ `skel_transform_nsteps=5` は属性のみ最適化に適切か — **懸念は的中していた**

### 何が起きているか

`design_opt/envs/pusher.py` の `step()` を追うと、このパラメータが**2つの役割を兼ねている**ことが分かる。
`transit_execution()` の発火条件が `cur_t == skel_transform_nsteps + 1` に固定されているため、
骨格編集をスキップすると、その5ステップ分がまるごと属性編集に化ける。

| 設定 | 骨格編集ステップ | **属性編集ステップ** |
|---|---|---|
| `fix_skeleton=false`（原論文の想定） | 5回 | **1回** |
| `fix_skeleton=true`（本研究の本線） | 0回 | **5回** |

つまり「5」という数字は**骨格探索の回数として決まった値**であり、属性のみを最適化する本研究の設定で
適切かどうかは誰も検証していない。ユーザーの直感（「関節数変化込みで適切なだけで、変化しない研究では不適かも」）は正しい。

### 実測（`tripo_arm_v2c_pusher` の best、2026-08-03）

```
cur_t=2: [ 0.262, -0.496, ...]  |Δ|=1.52
cur_t=3: [ 0.514, -0.931, ...]  |Δ|=1.34
cur_t=4: [ 0.762, -1.000, ...]  |Δ|=1.04
cur_t=5: [ 1.000, -1.000, ...]  |Δ|=0.83   ← 探索範囲の境界に到達
cur_t=6: [ 1.000, -1.000, ...]  |Δ|=0.58   ← まだ動いている
```

Leader は一方向に単調に増やし続けて境界に張り付いている。ここから2点言える。

1. 各所で「境界収束」と呼んできた現象に、**このステップ数が効いている可能性がある**。
   ステップが2回なら `[0.514, -0.931]` という内部解で終わっていた。境界に届くかどうかがステップ数で決まっている
2. ただし**「だから間違い」とは言えない**。Reach（L1）は境界に張り付かず内部解（0.905 m）に収束しており、
   Leader は望めば途中で止まれる。5ステップは「行こうと思えば端まで行ける予算」であって強制ではない

### 決めたこと

**`skel_transform_nsteps=2` で `tripo_arm_v2c_pusher` を1本だけ回し、best と収束形態を比較する。**

- 費用は 1本・約1日。「深追い沼り厳禁」の範囲に収める
- **結果が変わる** → 限界節に「ステップ数が結論に影響する」と正直に書く必要がある
- **結果が変わらない** → 「この設定はステップ数に対して頑健」と積極的に主張できる

どちらでも論文の価値が上がるので費用対効果は良い。**実施は現在の実験（v3・マトリクス）が空いてから。**

## ② 把持を最終タスクにするか — **見送る**

### 判断の理由

**1. 把持は「腕の形」ではなく「ハンドの形」を測る**

既存3タスクが機能したのは、性能を決める量が腕の設計そのものだから（Pusher の先端速度 ∝ リンク長×角速度、
Reach の到達可能性 ∝ 総リーチ）。一方、把持の成否を決めるのは主に指の長さ・開き幅・接触形状である。
しかしパイプラインがメッシュから抽出しているのは**リンク長と関節位置**であり、ハンドの設計は含まれていない。
把持を入れると**判定軸がパイプラインの設計対象外へ移る**ため、主張を強めるどころかずらしてしまう。

**2. カプセル卒業は「欠陥の修正」ではなく「スコープの拡大」**

第6章6.4.1で既に「幾何学的プリミティブで構成される」「sim-to-real はスコープ外」と宣言済み。
カプセル近似は隠している弱点ではなく明示済みの前提である。把持のために卒業するなら
「メッシュ衝突の実装＋接触パラメータの妥当性検証＋ハンド設計の追加」が全部必要で、残り6ヶ月では中途半端になる。

なお `scripts/check_mesh_interference.py` は**静止姿勢の凸包近似**であり、
把持に必要な多点接触・摩擦・力閉合には全く足りない（「載せ替えて壊れないか」の一次スクリーニング用）。

**3. 報酬が複雑になり、この研究が繰り返し失敗した領域に入る**

第5章5.2.1に「報酬の複雑化は co-design の探索信号を壊す」という知見が、複数の失敗run（D5/D6/D7・v2-4・v5-3）を
根拠に書かれている。把持は本質的に多段階（近づく→握る→保つ）で報酬が複雑になる。

### 教授の二段階案（先端を届かせる学習 → 掴む報酬）への評価

**手法としては標準的（curriculum / staged reward）で不当ではない。** ただしこのリポジトリには両方の前例がある。

- ❌ **J1**（Pusher重み → Reach へ転用）は ep380 で崩壊し回復しなかった
- ✅ **TP1**（I1 から `control_prior` で転用）は成功した

つまり「段階学習が効くかは条件次第」で、**成功する前提で計画を立てるのは危険**というのが正確な答え。

### 決めたこと

**把持は第6章6.5「今後の課題」に一文置くに留める。** 新しいタスクは足さず、今の3タスクで判定システムとしての
完成度を上げる方が強い修論になる。この研究の貢献はタスクのレパートリーではなく判定の仕組みであり、
明日出るマトリクス判定（3形態×2タスクで順位が反転するか）の方が、把持を1つ足すより主張を強める。

> 「アームといえば把持」は直感としては自然だが、**論文の主張と接続しない**。
> ユーザー自身が「修論として把持をゴールとするのが適切という話はどこにもない」と述べており、この認識は正しい。

## ③⑦ 修正フローと診断アドバイス — **診断システムを貢献として採用する**

### 問題意識（ユーザーの指摘）

> 「このタスクはうまくいきません」だとシステム側は何も頑張らず、ユーザがひたすらやり直すだけ。
> 専門知識のいらない設計支援システムを目指すなら、今の形状だと何がどうだからどうしなきゃ、
> とまでユーザにアドバイス言えるようになったらいい

この指摘は妥当。そして**システムは既に診断に必要な情報を計算しているのに、報告していないだけ**である。

### 採用する3層の診断

#### 第1層: 幾何だけで即答できる（学習不要・数秒）

| 症状 | 検出方法 | ユーザーへの言葉（専門知識不要） |
|---|---|---|
| 目標に届かない | 総リーチ < 目標距離 | 「腕が短すぎます。総リーチ 0.40 m に対し目標は 0.80 m 先です。1.2倍以上に伸ばしてください」 |
| 対象に最初からめり込む | 静止姿勢の先端が対象のバウンディングボックス内 | 「初期姿勢で対象に接触しています。腕を短くするか対象を遠ざけてください」 |
| **関節軸が意図と違う** | 到達可能な円環に目標が入らない | 「この軸構成では目標が可動範囲の外です。関節の向きが想定と異なる可能性があります」 |

⑦で「未定」としていた**関節軸の問題はここで拾える**。到達可能円環の計算
（`reach_min, reach_max = |L1-L2|, L1+L2`）は `compute_reach_bonus()` 内に既に実装されており、
現在 `reach_bonus_scale=0.0` で休眠しているだけである。

#### 第2層: 収束した形態から読める（学習後、追加計算なし）

| 収束パターン | 意味 | アドバイス |
|---|---|---|
| **gear も太さも下限に全張り付き** | 何をしても報酬が改善しない＝タスクに根本的に不適合 | 「この形状ではタスクを達成できません。形を変えてください」 |
| gear だけ上限に張り付き | 出力が足りていない | 「もっと太く/強くできる余地があります（探索範囲の上限に達しました）」 |
| 内部解に収束 | 必要十分な設計が見つかった | 「この形状は適しています」 |

「gear と太さが揃って下限」が不適合のシグナルだという知見は、2026-08-03 に `tripo_pj_short` の実測で見つけたもの
（実験系譜.md 9-4、形態比較.md「size・ext_start の収束値まとめ」）。

#### 第3層: 行動から読める

`probe_cube_trace.py` が既に出している行動分類（一撃で吹き飛ばす / 押して止める / 静止保持）をそのまま返す。
「意図と違う動きになった」場合、少なくとも**何が起きたかは言葉で返せる**
（例:「一撃で吹き飛ばす戦略に収束しました。狙った位置に止めたいなら Target-Pusher タスクを選んでください」）。

### 位置づけの変化

| | 主張 |
|---|---|
| 現状 | co-design は良い形態と悪い形態を**判別できる**（判定器） |
| 拡張後 | co-design は**なぜ悪いかを説明し、次の一手を示せる**（診断器） |

第1層は学習不要なので、ユーザーは数秒でフィードバックを得られる。
「6時間学習してダメでした」より遥かに実用的である。

### 決めたこと

**修論の貢献の一つとして採用する。**

- 第3章に **M7（診断・助言）** としてモジュールを追加する
- 第4章に、既存の4形態（`tripo_pj_short` / `pj_mid` / `pj_long` / `tripo_arm_v2c`）へ適用した診断レポート例を載せる
- **追加の学習は不要**。既存の checkpoint とログから作れる

### まだ答えが出ていないこと

「**動きが思っていたのと違う**」への対応は保留のまま。これは報酬設計の問題であり、
やりたい動きごとに報酬を考えるなら専門知識が必要になり、「簡単なシステム」ではなくなる。
第3層で「何が起きたか」は返せるが、「どう直すか」は返せない。

> そもそもそのタスクを強化学習でやるべきなのか、という論点も残る（ユーザー指摘）。
> 現時点では**第3層で現象を報告するに留め、報酬の自動設計には踏み込まない**方針とする。

## ① あと何が出ればシステムの論拠になるか

| 主張 | 状態 |
|---|---|
| co-design はタスクに適した形態を識別する | ✅ rrbot 3タスク×2seed |
| パイプライン生成形態でも同じ | ✅ tripo_arm_v2c 3タスク（1 seed） |
| 良い/悪いスケッチを判別できる | ✅ rrbot（4.4.3）+ tripo（4.4.4、2026-08-03 確定） |
| **判定はタスクに依存する（形態の絶対評価ではない）** | 🔄 マトリクス判定で判明予定 |
| 非平面・高自由度でも動く | 🔄 `tripo_arm_v3_pusher` 走行中 |

**残る決定打は「マトリクス判定での順位反転」**。同じ3形態が Reach と Pusher で順位を入れ替えるなら、
「このシステムは形態の良し悪しではなくタスク適合を測っている」を1枚の表で示せる。
これが出れば、システムとしての論拠はほぼ揃う。

## ④ PPO の設計思想を変えずに良くするには

Stackelberg PPO の核は「**Leader が理論上の最適制御ではなく、Follower の実測リターンを見て形態を評価する**」こと。
これを壊さない範囲の改善なら思想と矛盾しない。

**思想に適合する変更（やってよい）**:
- ⑤のステップ数調整 — ステップ数は Leader が設計を練る回数であって、「Follower の実応答で評価する」という
  評価構造には一切触れない。むしろ骨格探索用の値を惰性で使っている現状の方が、思想の実装として不徹底
- 診断レポート（③⑦）— 学習後の出力を解釈するだけで、学習ループには介入しない

**思想を壊す変更（やってはいけない）**:
- 良い形態の事前知識で初期値を与える
- IK で到達可能性を先に判定して足切りする（※ただし**診断の第1層として「学習と並行に」示すのは可**。
  学習の評価に介入せず、ユーザーへの情報提供に留まるため）

いずれも Leader の評価を Follower の実応答から切り離すため、この研究の主張自体を無効化する。

## ⑥ UI について

**アプリのような画面は作らない。** Gemini と Tripo3D が Web インタフェース経由（API 制約）である以上、
完全自動の GUI は現実的でない。成果物は **CLI / スクリプト群**とし、修論では
「システム構成図＋実行例」の形で示す。

## ⑧ タスク環境の動的整備（着手するかは未定）

「ユーザーがやりたいタスクをすぐ準備できたら理想」という構想。③⑦の議論と繋がっており、
マトリクス判定の**縦軸（タスク側）を増やせるか**という話になる。

現状タスクは3つハードコードだが、**Reach は `target_x/y/z` を変えるだけで無限に作れる**。
**まず「Reach の目標位置を変えるだけの簡易タスク生成」から始めるのが、最も安く着手する道**。

優先度は診断システム（③⑦）より低い。修論に入れるかは、診断システムが固まってから判断する。
