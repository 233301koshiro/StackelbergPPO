## ③ 道具と md の監査（① の後に貼る。モデルが替わったとき、スクリプトをまとめて見直すとき）

② が研究の中身を一次資料に当てるのに対し、③ は道具（スクリプト）とその説明（md）の欠陥を探す。

```
このリポジトリのスクリプトと md を監査してほしい。モデルが新しくなったので、前のモデルが書いたものや確かめたものを、新しい目で一度見直したい。私が確認するまで何も直さないこと。

目的は、研究の結論を黙って歪めうる欠陥を見つけること。コードの綺麗さや md の文章の上手さは対象外。この研究は「形態がタスクに妥当かを判定できる」と主張しているので、学習・環境・評価・判定・検査の数字を変えうるものを最優先にする。

根拠にしてよいのは、コード、XML、学習ログ single_run/*/log/log_train.txt、launch_env.json、軌跡、それらを実際に動かした結果。md・コメント・docstring・前のチャットの記述は確かめる対象であって、根拠ではない。

始め方:
- 稼働中の学習とキューを ps で確かめ、それには触らない。
- 監査の対象を棚卸しし、まとまりに分けて優先順位つきで提案して、私の返事を待つ。索引は scripts/README.md、docs/リポジトリ説明/02_コードと実験/評価スクリプト.md、docs/目次.md にある。
- 優先順位は次の順にする。修論の核（表 4.4 の R1〜R4・軸3）の数字を作るコード（学習・環境・cfg の読み込み・評価・判定器）→ 結論の前に回す検査（check_*.py など）→ それらを説明する md。
- 広く読むところはサブエージェントに分けてよい。サブエージェントの報告も確かめる対象として扱い、⛔ と判定するものは自分でコードかログに当ててから表に載せる。

スクリプトで見ること（過去に実際に起きた型で、これに限らない）:
- 渡したはずの設定が効いているか。起動行の引数・環境変数・cfg が途中で捨てられたり、既定値で上書きされたりしていないか。Bug 74 では config.py が +robot_param_scale を捨て、yml の値が効いていた。
- 既定値のまま走らせると、実験とは別の条件を測ることにならないか。
- 名前で掴む処理が、意図した物体やリンクを、意図した数だけ掴んでいるか（CLAUDE.md ⑤-3-2）。
- 検査が既知の失敗を拾えるか。--reproduce の無い検査には壊れた入力を与えて、失敗と出るかを確かめる。通るだけの検査は根拠にならない。
- 検査がそもそも持っていない量は、どの検査も 0 と出す（Bug 72）。何を見ていないかも書く。
- プローブが本番と違うシミュレータ（MuJoCo か Choreonoid か）で回っていないか。
- 例外を握りつぶしていないか。失敗しても成功に見える出力や終了コードにならないか。
- docstring・コメント・--help が今の挙動と合っているか。取り下げた読みが残っていないか。

md で見ること:
- コードの振る舞いについての主張（パス・引数・環境変数・既定値・出力先）が、今のコードと合っているか。
- 取り下げた主張（知見総括表 E 節・実験系譜の訂正）が、別の md に生きたまま残っていないか。
- 派生や状態の md が、台帳に無い値を持っていないか（CLAUDE.md §4-2 の 4 層）。
- 指示として読まれる md（CLAUDE.md・.claude/commands・この「新しいチャットの始め方」・スクリプトの使い方の節）が、互いに食い違っていないか。
既存の検査（check_*.py）で拾えるものは、先に検査を回して結果を使う。人の目で読むのは、検査が拾えないものに絞る。

動かすときの決まり:
- 動かせば分かることは、読んで推測せずに安いものから動かす。
- Choreonoid のプローブは出力をファイルへリダイレクトし、末尾は os._exit(0) にする。timeout はプローブの所要時間から決める（起動は約 2 秒）。
- GPU を使う学習は走らせない。既存の run・XML・キューは上書きせず、要るなら新しい名前で作る。

報告の形:
1. 指摘は表で出す。列は「場所（file:line）・記述・判定・根拠・結論への影響」。判定は ⛔ 誤り／⚠️ 古い／❓ 根拠が無い／✅ 一致 の 4 つで、✅ にも何で確かめたかを書く。
2. 結論への影響は、どの run・どの表の数字が変わりうるかまで書く。影響が無いなら無いと書く。推測と確認済みは分ける。
3. 1 まとまり終えるごとに区切って報告し、次に進むか私に聞く。
4. 直すことになったら、バグはデバッグ戦記で Bug 番号を採番し、影響を受けた過去の結論を grep で洗い、実験系譜に段を書く。直した後は CLAUDE.md §4-2 の自動チェックのうち当たるものを回す。
```

## ⑤ Fable に頼む見直し（2026-11-16 新設）

> 2026-11-16 新設（ユーザー「いつも Opus 5.5 でやっているが、Fable で改めて確認・考察させたい」）。
> **何に使うか**: Fable 5.1 は 1 トークンあたり Opus 5.5 の 2.5 倍かかる（入力 10 対 4、出力 50 対 20 ドル／100 万トークン）。値の照合・節参照・孤立ファイルのように検査スクリプトや ①〜③ で足りるものには使わない。使うのは検査が原理的に拾えないもの（主張の強さ・読み方の変化・物理の抜け穴・審査員の目）に限る。
> **使い方**: 新しいチャットで `/model` を Fable 5.1 に切り替え、「前置き」と依頼を 1 つ、1 通にまとめて貼る。① は貼らない（CLAUDE.md は自動で読まれ、要るものは Fable が自分で読む）。1 回の応答に 10 分以上かかることがあるが、止めずに待つ。
> **①〜③ と書き方を変えてある**: Fable は手順を細かく指定するより、目的・理由・してはいけないことを渡した方がよく働く（Anthropic の Fable 5.1 移行ガイドの「前のモデル向けのプロンプトは指示が細かすぎて質を下げる」）。依頼文に手順の列挙を足さないこと。
> **Opus の見立ては依頼文に書かない**: 先に書くと Fable がそれに引きずられ、独立した見直しにならない（[../05_レビューと監査/セカンドオピニオン.md](../05_レビューと監査/セカンドオピニオン.md) C の「先入観が無いときにしか読者にならない」と同じ理由）。見立てはユーザーが手元に持ち、Fable の報告と突き合わせる。
> **結果の処理**: `/review-in` で一次記録に当てて仕分ける（CLAUDE.md §10）。

| 依頼 | 検査で拾えない理由 | effort の目安 |
|---|---|---|

### ⑤-6 Stackelberg 勾配の実装と効き（effort: xhigh、2026-11-17 新設）

```
依頼: この研究の形態の更新（Leader）が、原論文の Stackelberg 勾配を正しく計算しているか、またこの研究の学習でその勾配の間接の項（Follower の応じ方の感度を織り込む項）がどれだけ効いているかを評価してほしい。

修論は手法の名前に Stackelberg PPO を掲げ、第2章・第3章で Leader の更新に Follower の感度を織り込むと説明しています。審査で「その項は実際に効いているのか。ふつうの同時最適化（形態と制御を同じ PPO で更新）と何が違うのか」と聞かれたとき、実装と数値で答えられるかを知りたい。いまは、勾配の実装を論文の式と突き合わせた記録も、間接の項の大きさを測った記録もありません。

読む物は原論文（Dai et al. 2026、arXiv:2603.15388。repo に PDF は無いので arXiv から取る。式の対応は docs/研究応用/執筆/関連研究_文献ノート.md）、実装（design_opt/agents/genesis_agent.py の ppo_loss_stackelberg と design_opt/utils/stackelberg.py）、修論の第2章・第3章の該当する説明です。間接の項の大きさは、保存してあるチェックポイント（single_run/<run>/models/）と CPU で集めた少量のサンプルで測ってかまいません。対象の run は修論の核から選んでください（実験系譜の 9-318 以降）。押しの核は取り直し中（9-351）なので、到達の核か、取り直しの run でも完走したものを使ってください。取り直しの run の学習ログ（_vp の log_train.txt）の報酬は見ないでください（結果を見る前に決めた読みがあるため）。

知りたいのは次のことです。実装は論文の式（係数・符号・正則化 λ・共役勾配法の打ち切り）と一致しているか、違うならどこで、それが修論の説明と食い違うか。この研究の学習で、間接の項は直接の項に比べてどの程度の大きさで、向きをどれだけ変えているか（学習の序盤と終盤、形態の各変数）。それを踏まえて、修論が Stackelberg について言っていることのうち、いまの証拠で言えること・言えないこと。ふつうの同時最適化との比較実験が要るかどうかの判断材料（要るなら最も安い設計）も書いてください。
```


### ⑤-7 主張の木の論証としての正しさ（effort: xhigh、2026-11-17 新設）

```
依頼: 修論の主張の木（docs/研究応用/執筆/主張の木.drawio）が、論証としていまも正しいかを評価してほしい。

知りたいのは次のことです。
- 各ノードの文が、いまの本文と一次データで言えるか（証拠より強い・古い・本文と違う）。

木は直さないでください（draw.io の手直しは私がします）。報告はノードごとの判定の表（言える／強すぎる／古い／支えが足りない／本文に無い）と、構造の問題の表、読み 57 の対応表に分け、最後に私が直すなら上から順にこれ、という 5 件を挙げてください。
```
