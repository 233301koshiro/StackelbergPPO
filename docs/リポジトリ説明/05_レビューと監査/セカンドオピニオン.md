> ⭐ **CLAUDE.md §10 から移した**（2026-09-25）。
> **ユーザーが別サービスへ貼り付けるための文面**であって、Claude への指示ではない。
> ⭐ **受け取ったレビューの処理は `/review-in`**（CLAUDE.md §10）。

### A. コードレビュー用プロンプト

```
以下のPythonコードは、Claudeが[機能名]のために実装したものです。

次の3点から厳しくレビューし、問題点と具体的な改善案を出してください:
1. バグ・エッジケース漏れ（入力が空・型が違う・境界値など）
2. セキュリティ上の懸念（パス操作・外部入力の扱い・コマンド注入など）
3. パフォーマンス上のボトルネック

[ここにコードを貼り付け]
```

### B. 研究レビュー用プロンプト

実験設計・結論の妥当性を批評させる。コードより優先度が高い。
実験設計の欠陥はコードのバグより修正コストが大きいため。

```
以下は Stackelberg PPO を用いた形態-制御 co-design 研究の[章名 / 実験名]の記述です。
Claudeが整理・執筆したものです。

次の4点から厳しく批評してください:
1. 実験設計の妥当性（交絡変数が制御されているか・比較条件が公平か）
2. 結論の根拠（データから言える範囲を超えた主張をしていないか）
3. 再現性（同条件で他者が再現できるか・記述が十分か）
4. 主張と証拠の整合（「〜を示した」「〜を実証した」という表現が証拠に見合っているか）

「この主張は根拠が弱い」「この条件設定では交絡が残る」のように具体的に指摘してください。
研究の背景: Choreonoid シミュレータ上の2関節固定アーム、3タスク（Pusher/Reach/Target-Pusher）、seed×2による再現性確認。

[ここに対象テキストを貼り付け]
```

### D. 予備審査のスライドと論文を、別の会社のモデルに審査員の目で見せる（2026-11-20、ユーザー判断）

新しいチャットの始め方 ⑤-8 の代わり。伝わるか・言い過ぎかは書いたモデルの癖から来る誤りで、同じ Opus では消せないので、GPT か Gemini に見せる。リポジトリは渡さず、**PDF 2 本だけ**を添付する（審査員と同じく PDF しか見ない状態にするため）。いつ回すか: 押しの数値を差し替えた後（系譜 9-351 の読み 57 の判定の後）、予備審査の前。

添付するもの: 予備審査論文の最新の PDF（`docs/pdf/予備審査論文_<日付>.pdf`）と、Google スライド「予備審査_秋田」を発表者ノート付きで PDF に書き出したもの。Claude の見立ては依頼文に書かない（C の「先入観が無いときにしか読者にならない」と同じ理由）。

```
私は修士 2 年で、12 月頭に修論の予備審査があります（発表 15 分・質疑 15 分。聴衆にはロボット以外の分野の教授もいます）。研究は、スケッチから作ったロボットの形がタスクに合うかを、形と制御の同時最適化で判定するシステムです。添付は、審査員に配る予備審査論文と、発表スライド（発表者ノート付き）です。どちらも AI（Claude）と一緒に作りました。

予備審査の審査員のつもりで評価してください。知りたいのは次のことです。
- 15 分の発表として話の筋が通るか（各枚の役割、論理の飛び、順番）
- ロボット以外の分野の教授が説明なしではつまずく枚・語・図
- 図の値・軸・凡例が本文と合うか
- 証拠より強く言っている所
- スライドと論文のあいだで、主張や言い方がずれている所
- 質疑で聞かれそうな問いと、今の資料でそれに答えられるか

報告は、スライドは枚の番号ごと、論文は節かページごとの表にしてください。最後に、直すなら上から順にこれ、という 5 件を挙げてください。
```

結果は `/review-in` で一次記録に当てて仕分ける（CLAUDE.md §10）。

### C. 修論の文章を yomiyasu に読ませる（2026-10-19、ユーザー判断）

[yomiyasu](https://github.com/nanaism/yomiyasu)（日本語の推敲スキル、MIT、Python の標準ライブラリだけで動く）を、**文章を書き換える道具ではなく、いまの文章を通すとどんな指摘が出るかを見る「もう一人の読者」として使う。**
理由: 書き換えを任せると、どの直しを採ったかが見えなくなる。指摘だけをもらえば、採るかどうかをユーザーが決められる。

| 手順 | 中身 |
|---|---|
| 1. 本文だけを取り出す | 章ごとに、PDF に入る本文だけにする（`build_thesis_pdf.py` と同じく「## 執筆メモ」以降と、行頭が `>` の引用ブロックをすべて落とす。2026-10-23 から PDF はそうしている）。メモの ⭐⛔ や太字が混ざると指摘が雑音だらけになる |
| 2. lint を論文モードで通す | `python3 tools/yomiyasu/scripts/yomiyasu_lint.py <本文.md> --doc-type paper`。文章は変えない |
| 3. ユーザーが一覧から採るものを選ぶ | 直すのは Claude でもよいが、採否はユーザー。直したら修論の検査（`check_section_refs`・`check_stale_claims`・`check_docs_consistency`・`check_citations`）と PDF のビルド |

⚠️ 知っておくこと:
- **lint が見るのは書式と言い回しだけ**（太字の多さ・太字が表示されない書き方・読点・「AではなくB」・AI らしい語）。2026-10-19 に要旨で試すと、ユーザーが読んで感じた構成の違和感 4 点（話の飛び・用語の説明の要否・新規性の書き方・障壁と解決策の距離）は 1 つも拾わなかった。**人の読みの代わりではなく補い。**
- 論文モードでは、慎重な言い方・引用の印・数値・専門用語・「である」調を直さない決まり（`references/doc-types/paper.md`）。そのぶん中身の正しさ（数値とログの一致・取り下げた読み・章をまたぐ主張）は見ない。そこはこのリポジトリの検査とファクトチェック ②（[../01_開始と運用/新しいチャットの始め方.md](../01_開始と運用/新しいチャットの始め方.md)）が担う。
- **スキル本体の AI の部分（「書き手に確かめたい点」を出す部分）は、先入観が無いときにしか読者にならない。**ユーザーの指摘を読んだ後の Claude が規則どおりに読むと、指摘に引きずられる。使うなら、ユーザーが読む前に通すか、指摘を知らないエージェントに通す。
- 「AではなくB」で否定が意味を担っている文や、場面の枠を示す読点（「評価では、」）の指摘は、規則の上でも残してよい。
- 置き場所: **`tools/yomiyasu/`**（リポジトリの直下、`.gitignore` 済み。ユーザー判断 10-19）。docs の外なので docs の検査には触れない。他人のコードなので公開リポジトリへは出さない。取ってきた版は `79d15a6`（2026-10-19、v2.0.2）。更新するときは `cd tools/yomiyasu && git pull`。⚠️ `.gitignore` の対象なので、コンテナを作り直しても `/userdir` に残るが、別の場所へ clone し直した環境には無い（`git clone https://github.com/nanaism/yomiyasu.git tools/yomiyasu`）。⚠️ `yomiyasu_check.py`（推敲の前後を比べる検査）を使うと、記録を git の最上位の `.yomiyasu/` に書く（中に自分で `.gitignore` を置く作り）。lint だけなら何も書かない。

### E. 研究の方針と行動が伴っているかを、定期的に別の会社のモデルに見せる（2026-11-28、ユーザー判断）

決まり・周期（週に 1 回など）・履歴は [外部の方針レビュー記録.md](../../研究応用/方針/外部の方針レビュー記録.md)。一式（方針の説明・方針と行動の対応表・この依頼文）は Claude が `/review-out` で `out/review_<MMDD>/` に作る。リポジトリは渡さない。Claude の見立ても渡さない（D と同じ理由）。
本文は毎回変えない（回をまたいで同じ問いで比べられるように）。`[ ]` だけを埋める。

```
私は修士 2 年で、研究は、スケッチから作ったロボットの形がタスクに合うかを、形と制御の同時最適化（強化学習）で判定するシステムです。[予備審査・実験の凍結・提出までの残りの時間]。

添付は 2 つです。
- 「方針の説明」: いま進めている方針を 1 枚にまとめたもの
- 「方針と行動の対応表」: 前回のレビュー（[前回の日付]）から今日までに、方針ごとに実際に何をしたか（計算・実装・実験の設定・事前に書いた予測・結果）
コードと実験の設定、この 2 つの文書の下書きは AI（Claude）が書きました。方針を決めた者と実行した者が同じなので、ずれに気づきにくい状態です。文書に書いてある数値や事実は正しいものとして、その上で批判的に見てください。

知りたいこと:
1. 方針と行動のずれ: 各方針について、実際の行動（実験の設定・比べる相手・設計変数・seed の数・学習量）が、その方針の問いに答えられる形になっているか。特に、予測に使った計算の前提と、学習の実験の設定が一致しているか。
2. 予測と判定: 事前に書いた予測について、当たったとき・外れたときにそれぞれ何が言えて何が言えないか。結果を見てから基準を動かした形跡は無いか。
3. 行動の無い方針と、方針の無い行動: 決めたのに手を付けていない方針。どの方針にも紐づかない作業に時間を使っていないか。
4. 前回のレビューで採用した指摘が、実際の行動に反映されているか。
5. 研究の主張（判定器として正しい答えを出すこと）に効かないのに時間を使っているもの。残りの時間に対して、優先順位は妥当か。やめる・後回しにする・足すべきものは何か。
6. 審査員（ロボット以外の分野の教授もいる）が質疑で聞きそうな問い。

報告の形:
- 方針ごとに「評価（伴っている／一部ずれている／ずれている）・根拠（文書のどこから読んだか）・具体的な直し方」の表。
- 「この文書の情報だけでは判断できない事項」を別の節にまとめ、それぞれ何が分かれば判断できるかを書いてください。推測で埋めないでください。この節を重視しています。
- 伴っている点は伴っていると書いてください。無理に批判を作る必要はありません。
- 最後に、直すなら優先度の高い順にこれ、という 5 件。
```

結果は `/review-in` で一次記録に当てて仕分ける（CLAUDE.md §10）。
